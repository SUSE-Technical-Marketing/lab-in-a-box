lab-in-a-box 根据单个 JSON 或 YAML 文件构建完整的实验室：包括您描述的虚拟机、DNS、Kubernetes 集群和附加组件。虚拟机可以运行在您自己的 KVM 主机、Harvester 或八个公有云中的任意一个上，同一个文件在它们之间通用。

为什么选择 lab-in-a-box？

  • 一个文件，一条命令。以声明方式描述虚拟机、Kubernetes 集群（RKE2 或 K3s）和附加组件。setup_lab.py 按依赖顺序构建它们，无需您手动运行 virt-install 或 Ansible。
  • 家庭实验室或云端，同一份定义。实验室虚拟机运行在您自己的 KVM 主机、Harvester HCI，或 AWS、Google Cloud、Alibaba Cloud、Hetzner、Scaleway、UpCloud、OVHcloud、Exoscale 上。一个实验室可以跨越多台 KVM 主机，并可通过跨云 WireGuard 覆盖网络组合多个云和站点。
  • 71 个现成的附加组件。Rancher、Longhorn、NeuVector、Harbor、Keycloak、Jenkins、Argo CD、SUSE Multi-Linux Manager/Uyuni、Nextcloud 等，另有用于安全培训的故意存在漏洞的演示应用。
  • 与代码同步的 Web 界面。lab-builder 根据附加组件自身的架构生成每个表单，因此脚本中新增的字段无需修改前端即可显示在界面中。
  • 可插拔的预配方式。SLE Micro 使用 Ignition 和 Combustion，openSUSE 和 Ubuntu 使用 cloud-init，旧镜像使用 virt-customize，也可以从安装程序 ISO 进行自动安装（AutoYaST、Kickstart、Preseed 或 AutoInstall）。
  • 凭据不放在实验室文件中。云和服务的凭据可以保存在按账户加密的文件中（使用 Argon2id 派生密钥，再级联使用 AES-256-GCM 和 ChaCha20-Poly1305）。
  • 容器化测试。每项检查都在一次性的 podman 容器中运行，pre-commit 钩子会运行相关检查。

虚拟化主机节点

一台或多台运行 KVM/QEMU 的物理机。每台主机托管实验室虚拟机，并在 /var/lib/libvirt/images/sources/ 中保存 QCOW2 源镜像。NUC、工作站或任何能运行 KVM 的 x86_64 机器都可以。需要超过一台机器容量的实验室可以跨越多台 KVM 主机，请参阅下文的多主机实验室。

自动化虚拟机

运行在虚拟化主机上的一台小型虚拟机，充当整个实验室的控制平面。它提供：

  • DNS：BIND（named）提供实验室域并转发外部查询，因此任何指向它的客户端都能解析所有实验室主机名
  • HTTP：在 /srv/www/htdocs/lab_creation/ 提供预配文件（Ignition、Combustion、cloud-init）
  • 脚本：所有实验室管理命令，安装在 /usr/local/bin/
  • Web 界面（可选）：lab-builder，在浏览器中设计 lab.json 的工具

所有用户命令都在自动化虚拟机上运行。它通过 SSH 连接到虚拟化主机和已创建的虚拟机。完成初始设置后，无需直接访问虚拟化主机。

内部实现

命令行工具和所有附加组件均使用 Python 3.11 编写，位于 libs/ 和 scripts/，安装到 /usr/local/lib/lab_creation/。它们围绕一小组共享库模块（lab_creation.py、backends.py、services.py、spacecmd_common.py 等）组织，而不是相互依赖。虚拟机创建位于可插拔的 VMBackend 接口之后，共有十种实现：libvirt、Harvester 和八个公有云（请参阅计算后端），因此附加组件和编排代码在它们之间无需改动。被替换的 bash 时代实现存档在 legacy_bash/ 中，包括原始的 install_ds389。

工作原理

部署流程

setup_lab.py 按固定顺序运行各个阶段；对于只有虚拟机的实验室（没有 kclusters 部分），两个 Kubernetes 专用阶段会被完全跳过：

    C --> D["phase_create_vms"]
    D -->|"has kclusters"| F["phase_reboot_and_wait_kept_nodes"]
    D -->|"no kclusters"| H["phase_vm_addons"]
    F --> G["phase_install_k8s_and_addons"]
    G --> H["phase_vm_addons"]

虚拟机预配

每台虚拟机的创建步骤如下： 1. 确定它所在的 KVM 主机（显式的 kvm_host 字段，或按空闲容量自动选择；请参阅多主机实验室） 2. 在该主机上复制 QCOW2 源镜像并调整大小 3. 根据其 config_method，用模板生成预配文件 4. 在 BIND 中注册 DNS 记录 5. 通过 SSH 在虚拟化主机上运行 virt-install 6. 等待 SSH 可用

预配方式由实验室 JSON 中的 config_method 控制（按节点或在 common 中设置）：

值 方式 适用于
（空，默认） Ignition + Combustion SLE Micro
cloud-init cloud-init ISO openSUSE Leap、Ubuntu
virt_customize 直接在虚拟化主机上修改 QCOW2（virt-customize），客户机无需支持 Ignition 或 cloud-init CentOS 7、旧版 Debian/RHEL，或任何不支持 Ignition/cloud-init 的镜像
install_iso 从真实的安装程序 ISO 自动安装（由 install_type 选择 AutoYaST、Kickstart、Preseed 或 AutoInstall） 没有其他预配方式的发行版

Kubernetes 设置

虚拟机启动后，setup_lab.py 根据 JSON 的 kclusters 部分在每个节点上安装 Kubernetes，支持 RKE2 和 K3s。集群就绪后，其附加组件依次运行；虚拟机级附加组件（关联到单个节点而非集群）在该节点预配完成后运行。

多主机实验室

实验室并不局限于一台虚拟化主机。在自动化虚拟机的 /etc/lab_creation.cfg 中设置 KVM_HOSTS（以空格分隔），即可使用多台虚拟化主机：

KVM_HOSTS="hv1.mydemo.lab hv2.mydemo.lab hv3.mydemo.lab"

然后，对实验室 JSON 中的每个节点，可以： - 显式固定：在该节点配置中写入 "kvm_host": "hv2.mydemo.lab"，或 - 自动选择：省略 kvm_host，节点会被放到当前有足够空闲 CPU/内存/磁盘的已配置主机上（通过 SSH 实时检测）。

未指定 kvm_host 的节点以及只配置了一台主机的环境，其行为与此功能出现之前完全相同：单虚拟化主机的实验室没有任何变化。

跨云 WireGuard 覆盖网络

云上的实验室节点通常根本无法通过网络访问另一个云账户的私有网络或家里的 libvirt 实验室：它们各自是独立隔离的 VPC 或网络。在实验室 JSON 中设置 common.overlay: true，会通过星型 WireGuard 覆盖网络（libs/overlay.py），按真实子网把此实验室的各个站点彼此路由起来：

graph TD
    Hub["Overlay hub<br/>(gateway VM, stable public IP)"]
    HomeGW["Home automation VM<br/>(site gateway)"]
    GWB["Site gateway VM<br/>(account B)"]
    HomeNode["home lab node"]
    NodeA["node — account A (hub's own site)"]
    NodeB["node — account B"]
    HomeGW -- "wg0 spoke" --> Hub
    GWB -- "wg0 spoke" --> Hub
    HomeNode -. "local route" .-> HomeGW
    NodeB -. "local route" .-> GWB
    NodeA -. "on the hub's own subnet" .-> Hub

只有每个站点的网关会加入覆盖网络，单个实验室节点从不加入。“站点”指家里的 libvirt 实验室或一个云账户；其网关要么是家庭站点自己的自动化虚拟机（/etc/lab_creation.cfg 中的 mysource），要么是在云账户中自动创建或复用的一台小型专用虚拟机（lab-overlay-gw-<backend>[-<account>]，与云 DNS 虚拟机命名规则相同）。所有其他节点只会获得一条经由本站点网关、通往其他各站点真实子网的持久本地路由：整个机制就是这样，节点本身不加入 WireGuard。

OVERLAY_HUB_ACCOUNT（必填，位于 /etc/lab_creation.cfg）指定网关虚拟机作为中心的云账户，即拥有固定公网 IP、所有其他站点都连接到它的那个站点。OVERLAY_CIDR（默认 10.99.0.0/16）只用于网关在隧道上的地址，不用于路由实际流量；OVERLAY_WG_PORT（默认 51820）是中心的监听端口。加入、退出和路由下发都在 setup_vm.py 中自动完成，无需手动运行其他命令。

已知限制：不会修改 DNS（只有当节点名称解析到已路由的子网后，才能通过真实主机名访问它）；之后有新的远程站点加入时，站点中已预配的节点不会被追溯更新路由，只会在各节点自己预配时刷新；AWS 需要禁用站点网关的“源/目标检查”才能转发流量（会自动处理），其他 7 个云后端尚无对应处理。

库加载顺序

每个脚本按以下顺序加载配置：

  1. /etc/lab_creation.defaults：系统默认值、路径、软件包列表
  2. /usr/local/lib/lab_creation/primary.py：输入校验、配置加载
  3. /etc/lab_creation.cfg：节点特定设置（REMOTE_HOST、ROOT_SSH_KEY、VIRT_SRV、KVM_HOSTS 等）
  4. /usr/local/lib/lab_creation/lab_creation.py：虚拟机、DNS 和编排函数
  5. /usr/local/lib/lab_creation/k8s.py：Kubernetes 集群函数

步骤 2：运行设置命令

在虚拟化主机上以 root 身份运行：

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash

它会安装 git 和 Python，将 lab-in-a-box 获取到 /var/tmp/setup_demo_server/，然后运行 setup_demo_server/setup_kvm_node.py。该脚本从选项和本主机的值获取实验室设置；使用 --interactive 时会逐项询问，并以这些值作为默认值：

  • 实验室网络：bridge 将实验室虚拟机放到主机所在的局域网；nat 则改用 libvirt 私有网络（适用于笔记本电脑或单网卡主机）
  • 实验室 DNS 域（默认 mydemo.lab）、自动化虚拟机的 IP 地址（会建议实验室网络上的一个空闲地址）及其 root 密码
  • 在 SLES 上还有注册码

网络、网关、DNS 服务器、时区和 SSH 密钥（~/.ssh/id_ed25519.pub，不存在时会创建）取自主机。答案写入 setup_demo_server/lab.cfg；在显示摘要（使用 --interactive 时还需确认）后，设置过程会：

  1. 为检测到的发行版安装虚拟化主机软件包（在 RHEL 系列主机上启用 EPEL 和 CRB）；
  2. 在 bridge 模式下，把承载默认路由的网卡变成 br0 的端口，并保留主机地址。支持 NetworkManager、netplan、wicked、systemd-networkd 和 ifupdown。如果网关无法通过网桥响应，计时器会恢复之前的网络配置，因此失败的更改不会让主机无法访问；
  3. 配置 libvirt 并创建自动化虚拟机。

每项设置都可以作为选项传入，例如从 cloud-init 无人值守运行时：

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh \
  | sudo bash -s -- --domain mydemo.lab --automation-ip 192.168.8.71 --root-password 'secret'

未指定 --root-password（或 LAB_ROOT_PASSWORD）时，会生成一个密码并在最后显示，除非使用 --interactive 询问密码。运行 python3 /var/tmp/setup_demo_server/setup_demo_server/setup_kvm_node.py --help 查看所有选项。

步骤 3：重新运行或更改设置

再次运行该命令会直接使用现有的 lab.cfg；对应其设置的选项（例如 --network-mode nat）会先更新这些设置，--reconfigure 则会重新询问所有内容。若要在做任何更改之前查看或编辑 lab.cfg，可以只获取代码：

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash -s -- --fetch-only

模式版本与迁移

每个模式都有一个 MAJOR.MINOR 形式的版本：实验室定义、每个附加组件的部分以及每个配置文件（lab_creation.cfg, lab_creation.defaults, lab.cfg、harvester-cluster JSON 和凭据文件）。新的 MAJOR 表示为上一版本编写的文件可能无法工作，或会产生不同的行为。schemas/compatibility.json 列出了每个版本及其变更。

实验室定义在其顶层 schema_versions 对象中记录编写时所针对的版本；Web UI 会写入该对象。未记录任何版本的定义视为每个模式的 1.0 版本。

"schema_versions": {"lab": "1.0", "addon:rancher": "2.0", "addon:longhorn": "1.0"}

migrate_config.py --check lab.json   # list the changes lab.json needs; exit 1 when there are any
migrate_config.py lab.json           # write the migrated copy to lab.json.system_modified.json

原始文件永远不会被修改。migrate_config.py 还会迁移 lab_creation.cfg, lab_creation.defaults, lab.cfg、harvester-cluster JSON 文件和凭据文件；这些文件在 # Schema version: 行或 schema_version 键中记录其版本。

部署旧镜像（CentOS 7）

CentOS 7（以及同样老旧的预构建 .qcow2 镜像）既没有内置 Ignition/Combustion，也没有 cloud-init，因此 config_method 必须为 virt_customize（请参阅 虚拟机预配）：它直接编辑 qcow2 文件系统，而不依赖客户机内的代理。 对于这么旧的镜像，还有两个覆盖设置很重要：

  • VM_BOOT: "bios"：CentOS 7 的 GRUB 需要传统 BIOS，而不是本项目默认的 UEFI。
  • VM_MACHINE: "pc"：适用于 2015 年的 CentOS 7 GenericCloud 镜像（内核 3.10.0-229）。使用 virt-install 默认的机器类型（目前为 q35）启动时，它会一直卡在 dracut 紧急 shell（Not all disks have been found）：在 Q35 的 PCIe 拓扑下，其 virtio-blk 根磁盘 始终无法及时出现。同一磁盘在传统 i440fx 芯片组（"pc"）下可以正常启动。这是芯片组与旧内核的不兼容， 并非本项目特有：同样的覆盖设置适用于任何足够老旧的客户机。
{
  "nodes": {
    "legacy1.mydemo.lab": {
      "myip": "192.168.88.120",
      "config_method": "virt_customize",
      "ISO_IMAGE": "CentOS-7-x86_64-GenericCloud-20150628_01.qcow2",
      "VM_BOOT": "bios",
      "VM_MACHINE": "pc"
    }
  },
  "common": { "VM_MEM": "2048", "VM_DSK": "30", "VM_CPU": "1", "VM_ROOT_PASS": "12345678" }
}

setup_lab.py legacy.json

VM_ROOT_PASS（在 common 中或按节点设置）指定 virt_customize 直接写入镜像的 root 密码；省略时改用 lab_creation.cfg 中的 ROOT_PWD_HASH，与 cloud-init 和 Ignition 的回退方式相同。

指南 3：NAT 下的自动化虚拟机（以单网卡笔记本电脑作为虚拟化主机）

目标：在没有空闲网卡可做网桥的主机上引导自动化虚拟机，改用 libvirt 管理的私有网络，并从主机自身的真实 IP 通过 DNAT 转发特定端口。已在一次性嵌套虚拟机上端到端实测。

如果不启用，默认快速入门流程不会有任何变化：_network_mode 默认为 "bridge"，与所有现有安装完全相同。

  1. 在 lab.cfg 中（快速入门步骤 3）设置：
_network_mode="nat"
_nat_network_name="labnat"          # default shown — a new libvirt virtual network, not your host's real LAN
_nat_network_cidr="192.168.150.0/24" # default shown
_nat_forwarded_ports="22:22/TCP 80:80/TCP 443:443/TCP"  # default shown — "<port on the HYPERVISOR's real IP>:<port on the AUTOMATION VM>/<protocol>"

这会把虚拟化主机自身可从外部访问的真实 IP（<external>）上的 22/80/443 端口转发到自动化虚拟机私有 NAT 地址（<internal>）的相同端口；此时私有网络上只有自动化虚拟机在监听，因此这里的“internal”始终指“在自动化虚拟机上”。（下面的步骤 5 在实验室虚拟机存在后，使用完全相同的 <external>:<internal>/<protocol> 语法转发到实验室虚拟机；在那里，“internal”指该虚拟机自己的私有 NAT 地址，而不是自动化虚拟机的地址。）

  1. 照常运行设置：
./setup_kvm_node.py

这会定义 libvirt 网络 labnat（NAT，DHCP 和网关由 libvirt 自身处理，与 libvirt 内置的 default 网络机制相同，只是使用本项目的名称和 CIDR）来代替网桥，然后在其上用该私有范围内的静态 IP 创建自动化虚拟机，再从主机的真实 IP 通过 DNAT 转发上述三个端口。

  1. 在虚拟化主机上验证网络和转发规则已存在：
virsh net-list                              # labnat: active
iptables -t nat -L LAB_PORTFWD -n -v         # DNAT rules to the automation VM's private IP
iptables -L LAB_PORTFWD_FWD -n -v            # matching FORWARD-chain ACCEPT rules
  1. 从虚拟化主机外部访问自动化虚拟机，使用虚拟化主机自身的真实 IP，而不是自动化虚拟机的私有地址 192.168.150.x（从其他任何地方都无法路由到它）：
ssh root@<hypervisor-real-ip>          # DNAT'd to the automation VM's SSH, port 22

端口 80 和 443 默认也会转发（预配文件的 HTTP 服务器，以及在设置 Web 界面后其 HTTPS 监听），同样通过虚拟化主机的真实 IP 访问。

  1. 为实验室虚拟机添加转发，而不仅是自动化虚拟机：为该节点添加 forwarded_ports 字段，并在 common.services 中启用一次 portforward 服务：
{
  "nodes": {
    "app1.mydemo.lab": {
      "myip": "192.168.150.20",
      "forwarded_ports": ["8080:80/TCP", "8443:443/TCP"]
    }
  },
  "common": { "services": ["portforward"], "...": "…rest of common as usual" }
}

当实验室中任意节点首次声明 forwarded_ports 时，setup_lab.py/setup_vm.py 会以同样方式从虚拟化主机的真实 IP 通过 DNAT 转发这两个端口。

计算后端

实验室虚拟机默认使用 libvirt（上面的 KVM 虚拟化主机）。设置 common.backend（或优先级更高的按节点 backend）即可改用其他后端；当前完整列表请参阅 backend 字段的 enum。每个非默认后端都需要在 /etc/lab_creation.cfg 中配置自己的凭据：

libvirt 上的控制台图形：实验室虚拟机使用 SPICE 显示（--graphics spice,listen=0.0.0.0），除非虚拟化主机的 QEMU 不支持 SPICE（例如 SLES 16），此时改用 VNC。lab-in-a-box 每次运行时从 virsh domcapabilities 读取一次该信息；查询失败时使用 SPICE。

多个云账户，与 KVM_HOSTS 提供多台虚拟化主机的方式相同：把每个云账户放到 /etc/lab_creation/credentials/（路径可通过 lab_creation.cfg 的 CREDENTIALS_PATH 配置）下单独的文件 <name>.yaml 中（也可以是 .json/.cfg：扩展名决定解析器；只有 .yaml/.json 支持下文的加密形式，因为 .cfg 的扁平 KEY=value 格式无法容纳它）。每个文件声明 cloudtype（aws/gcp/hetzner/…）以及该提供商的常用连接键，与后端已经从 lab_creation.cfg 读取的键完全相同（AWS_REGION、AWS_PROFILE、AWS_SUBNET_ID 等）。节点（或 common）用 "cloud_account": "<name>" 选择一个账户，与 "kvm_host": "<host>" 完全相同：

// /etc/lab_creation/credentials/aws-sandbox.yaml  (built with setup_credentials.py, below)
"nodes": {
  "jupiter.mydemo.lab": { "cloud_account": "aws-sandbox" },
  "saturn.mydemo.lab":  { "cloud_account": "aws-prod" }
}

设置 cloud_account 后，其 cloudtype 就是后端（因此 backend 字段变为可选；如果两者都设置且不一致，预检会报错），账户文件中的键只针对该节点叠加在 lab_creation.cfg 之上。在所有地方省略 cloud_account，即保持目前的单账户行为不变。每个账户都是隔离的网络，因此下文的云 DNS 虚拟机按账户区分（lab-dns-aws-sandbox、lab-dns-aws-prod 等）；未命名的默认账户保留简单的 lab-dns-<backend> 名称。

凭据文件默认以加密形式存储。用以下命令创建：

setup_credentials.py                              # interactive: pick a provider, fill in its fields
setup_credentials.py --encrypt-existing myfile.yaml  # encrypt an already-written plaintext file's sensitive fields

加密方式（请参阅 libs/crypto_store.py）：口令先经过 Argon2id（一种故意设计得缓慢且耗内存的 KDF；对于用口令加密的文件，真正的安全边界是它，而不是密码算法）派生出 512 位主密钥；随后 HKDF-SHA512 派生出两个独立的 256 位子密钥（按标签进行域分离，而不只是一分为二）；数据先用 AES-256-GCM、再用 ChaCha20-Poly1305 级联加密，这是两种结构不同、密钥独立的 AEAD 算法，因此即使其中一种算法被彻底攻破，单靠它也不够。任何需要凭据的工具（setup_lab.py、setup_vm.py 等）都会通过 libs/primary.py 的 try_load_cloud_account()（所有调用都经过的唯一函数）在每次运行时询问一次口令（只缓存在进程内存中，从不写入任何地方）。

文件可以在顶层设置 unencrypted: true 来放弃加密（这不是默认设置，setup_credentials.py 在写入这种文件前会询问）。--encrypt-existing 只就地加密看起来敏感的字段（名称像密钥、密码或令牌的字段），让 AWS_REGION/AWS_PROFILE 等保持可读，并且从不覆盖输入文件：它会在旁边写出 <name>.encrypted.yaml，供您检查后放到正确位置。需要在自动化虚拟机上安装 Python 包 cryptography（python311-cryptography，或 pip install cryptography，Argon2id 需要 ≥41）；它只在实际处理加密文件时才会被导入，因此从不设置 cloud_account 的实验室不需要任何新依赖。

外部服务凭据（SCC、SUSE Application Collection、Hermes 等）。同一个 /etc/lab_creation/credentials/ 存储、同样的加密和同一个 setup_credentials.py 工具也适用于非云的外部服务凭据，而不仅限于云提供商。这类文件用 credential_kind（例如 scc、appcollection、hermes）而非 cloudtype 标记，因此两种概念共用目录和格式，但永不冲突。每个需要外部服务凭据的附加组件都会说明自己的可选字段 <field>_account（例如 smlm_scc_account、suse_ai_registry_account、hermes_account），用于显式指定凭据；未设置时，与 cloud_account 一样，会自动使用唯一匹配该 credential_kind 的文件。在实验室 JSON 中写明文凭据仍然完全有效：此存储只是凭据的可选替代方案，绝非必需；即使您从不使用凭据存储，每个附加组件自己的明文字段（smlm_scc_user、suse_ai_registry_user、hermes_llm_api_key 等）也照常工作。

setup_credentials.py   # interactive — now asks "cloud provider or external service?" first

每种类型一个凭据文件，即可供所有需要该类型的附加组件重复使用（例如一个 scc 文件即可涵盖任意附加组件的 SCC 凭据），与各附加组件 JSON 字段的前缀无关；底层机制请参阅 libs/addon_common.py 的 resolve_credential()/Validator.vreq_or_credential() 以及 libs/primary.py 的 *_service_credential* 函数。

云后端（Hetzner/AWS/GCP/Alibaba/Scaleway/UpCloud/OVHcloud/Exoscale）与 myip：在实验室 JSON 中让云后端节点的 myip 保持为空：真实 IP 只有在创建时由提供商分配后才能知道，不能像 libvirt/Harvester 的静态 IP 那样预先决定。setup_vm.py 从 create_vm() 的返回值获取真实 IP，并在节点真正存在之后（而不是之前）将其注册到 DNS（这是在实测 AWSBackend 时发现的真实缺陷，2026-09-06；请参阅 TODO）。mymac 对云后端同样没有意义：请不要设置；它会被忽略，而不是被生成或做冲突检查。

云 DNS 虚拟机：实验室中任何节点首次使用某个云后端时，setup_vm.py 还会在同一云网络中预配（如果已存在则复用）一台运行 BIND 的小型低成本 DNS 虚拟机 lab-dns-<backend>，例如 lab-dns-aws。之所以需要它，是因为云节点通常根本无法访问 automation.mydemo.lab 的 BIND 服务器（它位于家庭实验室的 NAT/路由器之后，无法从 Internet 访问）；一个真实的多节点云集群需要在同一云网络中拥有自己的 DNS 服务器，节点之间才能相互解析。每个云节点的 DNS 记录会同时注册到这台 DNS 虚拟机和 automation.mydemo.lab 的中央区域中。已知限制：(1) 新创建的云节点尚不会自动把这台 DNS 虚拟机用于自身的名称解析，因此在没有进一步配置的情况下，同一实验室中的第二个云节点还无法通过主机名解析第一个；(2) 节点通过私有 IP 查询这台 DNS 虚拟机；从云外部向其公网 IP 发出的 DNS 查询可能被路径上的网络拦截，因为一些 ISP 和路由器会自行应答所有 DNS 流量。请参阅 libs/backends.py 中 ensure_cloud_dns_vm() 的文档字符串。

云实例规格：每个云后端都会根据一个小型内置表（每行的“备注”列说明使用哪一个），把 VM_CPU/VM_MEM 映射为提供商满足要求的最小实例类型、服务器类型、套餐或规格；该表从来不是上限。有两种覆盖方式，按优先级排列： 1. cloud_instance_type（在 common 中或按节点设置，节点优先）：实例类型、服务器类型、套餐或规格的确切名称，原样使用，完全不做自动选择。在所有云后端上用法相同，包括 OVHcloud（跳过实时查询规格列表的 API 调用）和 GCP（不创建自定义类型 e2-custom-<cpu>-<mem>；请改为指定真实的预定义类型，如 n2-standard-4）。 2. *_INSTANCE_TYPES/*_SERVER_TYPES/*_PLANS 配置键（见下表中各提供商所在行）：完整替换内置表，因此基于 VM_CPU/VM_MEM 的自动选择仍然有效，但改为针对您自己的列表。格式：name:cores:mem_gb,name:cores:mem_gb,...，例如 HETZNER_SERVER_TYPES=cx22:2:4,cx32:4:8,cx42:8:16。它会整体替换而不是合并该表：如需保留内置条目，请重复写出。GCP 和 OVHcloud 没有此键：GCP 直接根据 VM_CPU/VM_MEM 构建真实的自定义机器类型（没有可替换的目录），OVHcloud 则在创建时实时查询其真实的规格列表（见其所在行）。

一次性 git 设置

克隆仓库后运行：

git config core.hooksPath .githooks

这会启用 .githooks/ 中的钩子，它们会： - 在每次提交前运行完整的测试套件 - 管理每个脚本的版本标记（见下文）

版本管理的工作方式

这完全由上面的 git 钩子处理，您永远不需要手动编辑 __LABVERSION__。

每个脚本都包含占位符：

__LABVERSION__ = "__LABVERSION__"

.githooks/ 中的钩子会自动展开和还原该占位符：

钩子 触发时机 操作
post-checkout git checkout / git switch 把每个脚本中的 __LABVERSION__ 替换为最后一次修改该文件的提交的哈希值
post-merge git pull / git merge 同上
post-rewrite git rebase / git commit --amend 同上
pre-commit git commit 在写入提交之前，还原已暂存脚本中的 __LABVERSION__，因此哈希值永远不会存入仓库

结果：工作树中的每个脚本都能通过 --version 显示自己的版本，而仓库本身始终保存干净的占位符。通过 install_automation_node_scripts.sh 安装脚本时，也会在安装时用 git log -1 --format=%h 进行相同的逐文件哈希替换。

将脚本安装到自动化虚拟机

在自动化虚拟机（或任何克隆了仓库的机器）上，从仓库根目录运行：

./install_automation_node_scripts.sh

这会备份现有安装（既保存到它自己的带时间戳的 tarball，也另外保留在您自己的备份流程中），把每个脚本、库和模板复制到其系统路径，并为每个已安装文件标记版本哈希。
