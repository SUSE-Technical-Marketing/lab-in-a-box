lab-in-a-box cria laboratórios completos a partir de um único arquivo JSON ou YAML: as máquinas virtuais, DNS, clusters Kubernetes e complementos que você descreve. As máquinas virtuais podem ser executadas em seus próprios hosts KVM, em Harvester ou em uma das oito nuvens públicas, e o mesmo arquivo funciona em todas elas.

Por que lab-in-a-box?

  • Um arquivo, um comando. Descreva máquinas virtuais, clusters Kubernetes (RKE2 ou K3s) e complementos de forma declarativa. setup_lab.py os cria em ordem de dependências, sem necessidade de executar virt-install ou Ansible manualmente.
  • Lab em casa ou na nuvem, mesma definição. As máquinas virtuais do laboratório são executadas em seus hosts KVM pessoais, no Harvester HCI ou em AWS, Google Cloud, Alibaba Cloud, Hetzner, Scaleway, UpCloud, OVHcloud ou Exoscale. Os laboratórios podem se estender por múltiplos hosts KVM, e um único laboratório pode combinar nuvens e locais por meio de uma sobreposição WireGuard entre nuvens.
  • 72 complementos pré-integrados. Rancher, Longhorn, NeuVector, Harbor, Keycloak, Jenkins, Argo CD, SUSE Multi-Linux Manager/Uyuni, Nextcloud e muito mais, além de aplicações de demonstração intencionalmente vulneráveis para treinamento de segurança.
  • Uma interface web que segue o código. lab-builder renderiza cada formulário diretamente do esquema do complemento. Um novo campo em um script aparece na interface de usuário sem alterações no frontend.
  • Provisionamento intercambiável. Ignition e Combustion para SLE Micro, cloud-init para openSUSE e Ubuntu, virt-customize para imagens antigas, ou instalação orientada por script de um ISO de instalação real (AutoYaST, Kickstart, Preseed ou AutoInstall).
  • Credenciais fora do arquivo de laboratório. As credenciais de nuvem e serviço podem residir em arquivos criptografados por conta (derivação de chave com Argon2id seguida por AES-256-GCM e ChaCha20-Poly1305 em cascata).
  • Testes conteinerizados. Cada verificação é executada em seu próprio contêiner podman descartável independente, e um gancho de pré-commit executa as verificações relevantes.

Arquitetura

O sistema é baseado em uma arquitetura de dois níveis:

Nós hipervisor

Uma ou mais máquinas físicas (bare metal) com KVM/QEMU. Cada uma hospeda máquinas virtuais de laboratório e mantém imagens de origem QCOW2 em /var/lib/libvirt/images/sources/. Um NUC, estação de trabalho ou qualquer máquina x86_64 executando KVM é suficiente. Laboratórios que requerem mais capacidade do que uma única máquina pode oferecer podem se estender em múltiplos hosts KVM — veja Laboratórios multi-host abaixo.

VM de automação

Uma pequena máquina virtual no hipervisor atuando como plano de controle para todo o laboratório. Fornece:

  • DNS — BIND (named) atende o domínio do laboratório e encaminha consultas externas, de modo que todos os nomes de host do laboratório sejam resolvidos de qualquer cliente que o aponte
  • HTTP — fornece arquivos de provisionamento (Ignition, Combustion, cloud-init) em /srv/www/htdocs/lab_creation/
  • Scripts — todos os comandos de gerenciamento de laboratório, instalados em /usr/local/bin/
  • Interface web (opcional) — lab-builder, um designer baseado em navegador para arquivos lab.json

Todos os comandos do usuário são executados na VM de automação. Conecta via SSH com o hipervisor ou hipervisores, e com as máquinas virtuais criadas. Após a configuração inicial, nenhum acesso direto ao hipervisor é necessário.

Sob o capô

As ferramentas de linha de comando e cada complemento estão em Python 3.11, residindo em libs/ e scripts/, e instalados em /usr/local/lib/lab_creation/. Estão organizados em torno de um pequeno conjunto de módulos de biblioteca compartilhada (lab_creation.py, backends.py, services.py, spacecmd_common.py, …) que não dependem uns dos outros. A criação de máquinas virtuais é realizada através de uma interface VMBackend intercambiável com dez implementações: libvirt, Harvester e oito nuvens públicas (veja Backends de computação). Complementos e código de orquestração não mudam entre eles. As implementações em Bash que foram substituídas estão arquivadas em legacy_bash/ — incluindo o install_ds389 original.

Como funciona

Pipeline de implantação

setup_lab.py executa uma sequência fixa de fases. As duas fases específicas de Kubernetes são completamente ignoradas para um laboratório sem a seção kclusters:

Provisionamento de máquinas virtuais

Cada máquina virtual é criada assim: 1. Determinar qual host KVM a hospeda (o campo explícito kvm_host ou seleção automática por capacidade livre — veja Laboratórios multi-host) 2. Copiar e expandir uma imagem de origem QCOW2 nesse host 3. Gerar arquivos de provisionamento a partir de modelos de acordo com seu config_method 4. Registrar uma entrada DNS em BIND 5. Executar virt-install no hipervisor via SSH 6. Aguardar SSH estar disponível

O método de provisionamento é controlado por config_method no JSON do laboratório (por nó ou em common):

Valor Método Usado para
(vazio, padrão) Ignition + Combustion SLE Micro
cloud-init ISO cloud-init openSUSE Leap, Ubuntu
virt_customize Modifica QCOW2 diretamente no hipervisor (virt-customize) — nenhum suporte Ignition/cloud-init necessário no sistema convidado CentOS 7, RHEL/Debian antigos ou qualquer imagem sem Ignition/cloud-init
install_iso Instalação orientada por script de um ISO de instalação real (AutoYaST, Kickstart, Preseed ou AutoInstall, selecionado via install_type) Distribuições sem outro caminho de provisionamento

Backends de computação

Uma interface VMBackend intercambiável determina onde a máquina virtual de um nó é criada. Ela é resolvida uma vez por nó a partir de seu campo backend (ou de cloud_account, que implica o backend). O padrão é libvirt. Cada complemento e script de orquestração fala com o backend resolvido da mesma forma, não importa qual seja:

Backend Onde a VM é executada
libvirt Um hipervisor KVM/QEMU que você opera (padrão)
harvester Um cluster Harvester HCI, como KubeVirt VirtualMachines
aws Amazon EC2
gcp Google Compute Engine
alibaba Alibaba Cloud ECS
hetzner Hetzner Cloud
scaleway Scaleway Instances
upcloud UpCloud
ovhcloud OVHcloud Public Cloud
exoscale Exoscale

Configuração de Kubernetes

Uma vez que as máquinas virtuais estão em execução, setup_lab.py instala Kubernetes em cada nó de acordo com a seção kclusters do JSON. RKE2 e K3s são ambos suportados. Uma vez que um cluster esteja pronto, seus complementos são executados sequencialmente. Os complementos em nível de VM (designados a um nó individual em vez de um cluster) são executados posteriormente uma vez que esse nó está provisionado.

Ordem de carregamento de bibliotecas

Cada script lê a configuração nesta ordem:

  1. /etc/lab_creation.defaults — valores padrão do sistema, caminhos, listas de pacotes
  2. /usr/local/lib/lab_creation/primary.py — validação de entrada, carregamento de configuração
  3. /etc/lab_creation.cfg — configurações específicas do nó (REMOTE_HOST, ROOT_SSH_KEY, VIRT_SRV, KVM_HOSTS, etc.)
  4. /usr/local/lib/lab_creation/lab_creation.py — funções de VM, DNS e orquestração
  5. /usr/local/lib/lab_creation/k8s.py — funções de cluster Kubernetes

Início rápido

Requisitos

  • Uma máquina capaz de executar KVM (Intel VT-x ou AMD-V ativado)
  • Acesso à Internet (ou espelho local) para baixar pacotes e imagens
  • Uma imagem QCOW2 para o SO escolhido em /var/lib/libvirt/images/sources/ no hipervisor

A VM de automação especificamente requer python3.11 — a cadeia de ferramentas é explicitamente fixada nela. A maioria das distribuições fornece um python3 padrão mais antigo além disso. O script de instalação é interrompido se python3.11 está faltando.

Imagens testadas: - SLE Micro — recomendada, usada com Ignition+Combustion - openSUSE Leap Micro — suportada, usada com cloud-init

Etapa 1 — Preparar o SO do hipervisor

Instale SLES (ou outra distribuição Linux capaz de KVM) no seu hardware. Durante a instalação, selecione: - Rede: criar uma ponte (br0) conectada à sua NIC principal, com um IP fixo - Papel do sistema: Host de virtualização KVM

Etapa 2 — Inicializar os scripts de configuração

De qualquer máquina Linux com acesso SSH ao hipervisor:

curl https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | bash -

Isso baixa os scripts de configuração para /var/tmp/setup_demo_server/.

Etapa 3 — Configurar e executar a configuração do nó KVM

cd /var/tmp/setup_demo_server/setup_demo_server/
vim lab.cfg

Então execute a configuração (substitua <IP> pelo IP do seu hipervisor, ou omita para local):

./setup_kvm_node.py <IP>

Isso provisiona a VM de automação e inicia todos os serviços necessários.

Etapa 4 — Configurar a VM de automação

Conecte via SSH à VM de automação e instale os scripts do laboratório:

ssh <AUTOMATION_HOSTNAME>
./install_automation_node_scripts.sh

cp /etc/lab_creation.cfg.example /etc/lab_creation.cfg
vim /etc/lab_creation.cfg

Etapa 5 — Apontar o DNS do cliente para a VM de automação

Para que os nomes de host sejam resolvidos a partir de sua área de trabalho:

# Linux (NetworkManager):
nmcli con mod <connection> ipv4.dns <AUTOMATION_IP>

# Ou adicione a /etc/resolv.conf:
nameserver <AUTOMATION_IP>

Etapa 6 — Construir seu primeiro laboratório

setup_lab.py examples/cluster.json.template

Você encontrará mais pontos de partida abaixo em Exemplos. Alternativamente, você pode abrir a interface web em vez de escrever JSON manualmente.

Interface web (lab-builder)

Um designer de arquivos lab.json baseado em navegador que avalia as próprias bibliotecas Python do projeto em tempo de execução. Não possui conhecimento integrado de nenhum complemento. Selecione um componente e um formulário será renderizado diretamente de seu esquema. Adicione um campo a um script e a interface de usuário o exibirá sem alterações no frontend.

# A maneira mais rápida de tentar — zero dependências além de Python:
python3.11 webui/run-local.py            # → http://localhost:8677/

Para produção (Apache ou serviço systemd/init autônomo, mais HTTPS sobre certificado autoassinado criado de forma idempotente) veja README.webui.md. Lá estão descritos os três modos de operação, a API HTTP e solução de problemas.
