lab-in-a-box を使う理由

  • 1 つのファイル、1 つのコマンド。VM、Kubernetes クラスター（RKE2 または K3s）、アドオンを宣言的に記述します。setup_lab.py が依存関係の順に構築するので、virt-install や Ansible を手動で実行する必要はありません。
  • ホームラボでもクラウドでも同じ定義。ラボの VM は自前の KVM ホスト、Harvester HCI、または AWS、Google Cloud、Alibaba Cloud、Hetzner、Scaleway、UpCloud、OVHcloud、Exoscale で実行されます。ラボは複数の KVM ホストにまたがることができ、クラウド間 WireGuard オーバーレイによって 1 つのラボで複数のクラウドや拠点を組み合わせられます。
  • 71 個の既製アドオン。Rancher、Longhorn、NeuVector、Harbor、Keycloak、Jenkins、Argo CD、SUSE Multi-Linux Manager/Uyuni、Nextcloud などに加え、セキュリティトレーニング用に意図的に脆弱にしたデモアプリもあります。
  • コードに追従する Web UI。lab-builder はアドオン自身のスキーマから各フォームを生成するため、スクリプトに追加したフィールドはフロントエンドを変更しなくても UI に表示されます。
  • 差し替え可能なプロビジョニング。SLE Micro には Ignition と Combustion、openSUSE と Ubuntu には cloud-init、古いイメージには virt-customize、またはインストーラー ISO からの自動インストール（AutoYaST、Kickstart、Preseed、AutoInstall）を使います。
  • 認証情報はラボファイルの外に。クラウドやサービスの認証情報は、アカウントごとの暗号化ファイルに保存できます（Argon2id で鍵を導出し、AES-256-GCM と ChaCha20-Poly1305 をカスケードで適用）。
  • コンテナ化されたテスト。すべてのチェックは使い捨ての podman コンテナで実行され、pre-commit フックが関連するチェックを実行します。

アーキテクチャ

システムは2 層アーキテクチャで構成されています。

ハイパーバイザーノード

KVM/QEMU を実行する 1 台以上の物理マシンです。各マシンはラボの VM をホストし、QCOW2 のソースイメージを /var/lib/libvirt/images/sources/ に保持します。NUC、ワークステーション、KVM を実行できる x86_64 マシンであれば何でも構いません。1 台では容量が足りないラボは複数の KVM ホストにまたがることができます。後述のマルチホストラボを参照してください。

オートメーション VM

ハイパーバイザー上で動作する小さな VM で、ラボ全体のコントロールプレーンとして機能します。次の機能を提供します。

  • DNS：BIND（named）がラボのドメインを提供し、外部への問い合わせを転送するため、これを参照する任意のクライアントからラボのホスト名をすべて解決できます
  • HTTP：プロビジョニング用ファイル（Ignition、Combustion、cloud-init）を /srv/www/htdocs/lab_creation/ で提供します
  • スクリプト：ラボ管理コマンドがすべて /usr/local/bin/ にインストールされます
  • Web UI（任意）：lab-builder、ブラウザーで lab.json を設計するツール

ユーザーのコマンドはすべてオートメーション VM 上で実行します。オートメーション VM は SSH でハイパーバイザーや作成した VM に接続します。初期セットアップ後は、ハイパーバイザーに直接アクセスする必要はありません。

内部構造

コマンドラインツールとすべてのアドオンは Python 3.11 で書かれており、libs/ と scripts/ にあり、/usr/local/lib/lab_creation/ にインストールされます。互いに依存するのではなく、少数の共有ライブラリモジュール（lab_creation.py、backends.py、services.py、spacecmd_common.py など）を中心に構成されています。VM の作成は差し替え可能な VMBackend インターフェースの背後にあり、libvirt、Harvester、8 つのパブリッククラウドの 10 個の実装があります（コンピュートバックエンドを参照）。そのため、アドオンやオーケストレーションのコードはどの実装でも変わりません。置き換えられた bash 時代の実装は、元の install_ds389 を含め、legacy_bash/ にアーカイブされています。

仕組み

デプロイの流れ

setup_lab.py は決まった順序でフェーズを実行します。VM だけのラボ（kclusters セクションなし）では、Kubernetes 専用の 2 つのフェーズは完全にスキップされます。

VM のプロビジョニング

各 VM は次の手順で作成されます。 1. 配置する KVM ホストを決定します（明示的な kvm_host フィールド、または空き容量による自動選択。マルチホストラボを参照） 2. そのホストで QCOW2 ソースイメージをコピーしてサイズを変更します 3. config_method に従い、テンプレートからプロビジョニング用ファイルを生成します 4. BIND に DNS エントリーを登録します 5. SSH 経由でハイパーバイザー上の virt-install を実行します 6. SSH が使えるようになるまで待ちます

プロビジョニング方法は、ラボ JSON の config_method（ノードごと、または common）で指定します。

値 方法 用途
（空、デフォルト） Ignition + Combustion SLE Micro
cloud-init cloud-init ISO openSUSE Leap、Ubuntu
virt_customize ハイパーバイザー上で QCOW2 を直接変更します（virt-customize）。ゲスト側で Ignition や cloud-init をサポートしている必要はありません CentOS 7、古い Debian/RHEL、Ignition/cloud-init を持たない任意のイメージ
install_iso 本物のインストーラー ISO からの自動インストール（install_type で AutoYaST、Kickstart、Preseed、AutoInstall を選択） 他にプロビジョニング手段がないディストリビューション

コンピュートバックエンド

ノードの VM をどこに作成するかは、差し替え可能な VMBackend インターフェースが決定します。ノードごとに一度、backend フィールド（またはバックエンドを暗黙に決める cloud_account）から解決されます。デフォルトは libvirt です。すべてのアドオンとオーケストレーションスクリプトは、どのバックエンドでも同じ方法で解決済みのバックエンドとやり取りします。

Backend VM の実行場所
libvirt 自分で運用する KVM/QEMU ハイパーバイザー（デフォルト）
harvester Harvester HCI クラスター（KubeVirt の VirtualMachine として）
aws Amazon EC2
gcp Google Compute Engine
alibaba Alibaba Cloud ECS
hetzner Hetzner Cloud
scaleway Scaleway Instances
upcloud UpCloud
ovhcloud OVHcloud Public Cloud
exoscale Exoscale

Kubernetes のセットアップ

VM が起動すると、setup_lab.py は JSON の kclusters セクションに従って各ノードに Kubernetes をインストールします。RKE2 と K3s の両方に対応しています。クラスターの準備ができると、そのアドオンが順に実行されます。VM レベルのアドオン（クラスターではなく単一ノードに紐づくもの）は、そのノードのプロビジョニング後に実行されます。

マルチホストラボ

ラボは 1 台のハイパーバイザーに限定されません。オートメーション VM の /etc/lab_creation.cfg に KVM_HOSTS（スペース区切り）を設定すると、複数のハイパーバイザーを使えます。

KVM_HOSTS="hv1.mydemo.lab hv2.mydemo.lab hv3.mydemo.lab"

そのうえで、ラボ JSON の各ノードについて次のどちらかを選びます。 - 明示的に固定する：そのノードの設定に "kvm_host": "hv2.mydemo.lab" を記述する - 自動選択に任せる：kvm_host を省略すると、その時点で CPU、RAM、ディスクの空きが十分な設定済みホストに配置されます（SSH でその場で確認）。

kvm_host を指定しないノードや、ホストが 1 台だけの構成は、この機能が導入される前とまったく同じように動作します。ハイパーバイザーが 1 台のラボでは何も変わりません。

クラウド間 WireGuard オーバーレイ

クラウド上のラボノードは通常、別のクラウドアカウントのプライベートネットワークや自宅の libvirt ラボにネットワーク経由で到達できません。それぞれが独立した VPC やネットワークだからです。ラボ JSON に common.overlay: true を設定すると、このラボの各サイトを実際のサブネット単位でサイト間接続し、ハブアンドスポーク型の WireGuard オーバーレイ（libs/overlay.py）で相互にルーティングします。

オーバーレイに参加するのは各サイトのゲートウェイだけで、個々のラボノードは参加しません。「サイト」とは自宅の libvirt ラボ、または 1 つのクラウドアカウントです。ゲートウェイは、自宅サイトではそのオートメーション VM（/etc/lab_creation.cfg の mysource）、クラウドアカウントではそこに自動作成または再利用される小さな専用 VM（lab-overlay-gw-<backend>[-<account>]、クラウド DNS VM と同じ命名規則）です。それ以外のノードは、自サイトのゲートウェイ経由で他の各サイトの実サブネットへの永続的なローカルルートを受け取るだけです。仕組みはこれだけで、ノード単位の WireGuard 参加はありません。

OVERLAY_HUB_ACCOUNT（必須、/etc/lab_creation.cfg）は、ゲートウェイ VM がハブになるクラウドアカウントを指定します。ハブは、他のすべてのサイトが接続する固定パブリック IP を持つ唯一のサイトです。OVERLAY_CIDR（デフォルト 10.99.0.0/16）はトンネル上のゲートウェイ自身のアドレスにのみ使われ、実際のトラフィックのルーティングには使われません。OVERLAY_WG_PORT（デフォルト 51820）はハブの待ち受けポートです。参加、離脱、ルートの配布は setup_vm.py の中で自動的に行われ、手動で実行するものはありません。

既知の制限：DNS は変更されません（ノードの実ホスト名で到達できるのは、その名前がルーティング済みのサブネットに解決されるようになってからです）。後から新しいリモートサイトが参加しても、サイト内の既存ノードのルートはさかのぼって更新されず、各ノードのプロビジョニング時にのみ更新されます。AWS ではトラフィックを転送するためにサイトゲートウェイの「送信元/送信先チェック」を無効にする必要があり（自動で処理されます）、他の 7 つのクラウドバックエンドにはまだ同等の処理がありません。

ライブラリの読み込み順序

各スクリプトは次の順序で設定を読み込みます。

  1. /etc/lab_creation.defaults：システムのデフォルト、パス、パッケージ一覧
  2. /usr/local/lib/lab_creation/primary.py：入力の検証、設定の読み込み
  3. /etc/lab_creation.cfg：ノード固有の設定（REMOTE_HOST、ROOT_SSH_KEY、VIRT_SRV、KVM_HOSTS など）
  4. /usr/local/lib/lab_creation/lab_creation.py：VM、DNS、オーケストレーションの関数
  5. /usr/local/lib/lab_creation/k8s.py：Kubernetes クラスターの関数

クイックスタート

要件

  • KVM を実行できるマシン（Intel VT-x または AMD-V が有効）
  • パッケージとイメージをダウンロードするためのインターネット接続（またはローカルミラー）
  • 使用する OS の QCOW2 イメージを、ハイパーバイザーの /var/lib/libvirt/images/sources/ に配置

ハイパーバイザーに事前に Python をインストールしておく必要はありません。セットアップコマンドは、openSUSE Leap / SLES 15 では python311 を、それ以外ではディストリビューション標準の python3（3.9 以降）をインストールします。

動作確認済みのイメージ： - SLE Micro：推奨。Ignition+Combustion で使用 - openSUSE Leap Micro：サポート対象。cloud-init で使用

ステップ 1：ハイパーバイザーの OS をインストールする

次のいずれかをハードウェアにインストールします。最小構成またはサーバー構成で十分で、ブリッジや追加パッケージを事前に用意する必要はありません。

ファミリー バージョン
openSUSE Leap, SLES 15 (SP6+), 16
Debian, Ubuntu Debian 12、13；Ubuntu 22.04、24.04
RHEL, Rocky Linux, AlmaLinux, CentOS Stream, Fedora 9、10；最新の Fedora

これらのファミリーの他のバージョンには、一致する最新のパッケージ一覧が使われ、そのバージョンでは未検証である旨の警告が表示されます。SLES では、ホストが登録済みでない限り登録コードが必要です（セットアップ中に尋ねられます）。

RHEL ファミリーと Fedora のハイパーバイザーではホストのセットアップは完了しますが、オートメーション VM はまだ作成できません。これらのシステムの libguestfs は、openSUSE Leap イメージの btrfs ファイルシステムを読めないためです。当面は、別のファミリーのホストでオートメーションノードを作成してください。

Linux から起動用 USB を作成する 
# Before inserting USB:
cat /proc/partitions > /tmp/partb4

# Insert USB, then:
cat /proc/partitions > /tmp/parta

# Find the new device:
diff /tmp/part*

次のコマンドは、対象デバイスのデータをすべて消去します。実行する前に、sdX が上の diff の出力と一致しているか再確認してください。

# Write the ISO (replace sdX with your device):
dd if=SLE-15-SP6-Online-x86_64-GM-Media1.iso of=/dev/sdX bs=4k && sync

ステップ 2：セットアップコマンドを実行する

ハイパーバイザー上で root として実行します。

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash

このコマンドは git と Python をインストールし、lab-in-a-box を /var/tmp/setup_demo_server/ に取得して setup_demo_server/setup_kvm_node.py を実行します。このスクリプトはラボの設定をオプションとこのホストの値から取得します。--interactive を付けると、それらの値をデフォルトとして 1 つずつ尋ねます。

  • ラボネットワーク：bridge はラボの VM をホストの LAN に配置し、nat は代わりに libvirt のプライベートネットワークを使います（ノート PC や NIC が 1 つのホスト向け）
  • ラボの DNS ドメイン（デフォルトは mydemo.lab）、オートメーション VM の IP アドレス（ラボネットワーク上の空きアドレスが提案されます）とその root パスワード
  • SLES では登録コード

ネットワーク、ゲートウェイ、DNS サーバー、タイムゾーン、SSH 鍵（~/.ssh/id_ed25519.pub、なければ作成）はホストから取得します。回答は setup_demo_server/lab.cfg に書き込まれ、概要の表示（--interactive の場合は確認も）の後、セットアップは次を行います。

  1. 検出したディストリビューション用のハイパーバイザーパッケージをインストールします（RHEL ファミリーのホストでは EPEL と CRB を有効化）。
  2. bridge モードでは、デフォルトルートを持つ NIC を br0 のポートにし、ホストのアドレスはそのまま維持します。NetworkManager、netplan、wicked、systemd-networkd、ifupdown に対応しています。ブリッジ経由でゲートウェイが応答しない場合はタイマーが以前のネットワーク設定を復元するため、変更に失敗してもホストに到達できなくなることはありません。
  3. libvirt を設定し、オートメーション VM を作成します。

すべての設定はオプションで指定できます。たとえば cloud-init からの無人実行では次のようにします。

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh \
  | sudo bash -s -- --domain mydemo.lab --automation-ip 192.168.8.71 --root-password 'secret'

--root-password（または LAB_ROOT_PASSWORD）を指定しない場合、--interactive で尋ねない限り、パスワードが生成され最後に表示されます。すべてのオプションは python3 /var/tmp/setup_demo_server/setup_demo_server/setup_kvm_node.py --help で確認できます。

ステップ 3：セットアップの再実行と変更

コマンドを再実行すると、既存の lab.cfg がそのまま使われます。設定に対応するオプション（例：--network-mode nat）を指定すると先にその設定を更新し、--reconfigure を指定するとすべてを改めて尋ねます。何かを変更する前に lab.cfg を確認・編集したい場合は、コードだけを取得します。

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash -s -- --fetch-only

このマシンから別のマシンをセットアップするには、そのアドレスを指定します。コードは SSH でコピーされ、同じオプションが適用されます。

python3 /var/tmp/setup_demo_server/setup_demo_server/setup_kvm_node.py <IP>

lab.cfg の主な設定：

設定 説明
_network_mode, _bridge_name, _bridge_nic ブリッジまたは NAT のネットワーク。ラボの VM が接続するブリッジと、そのポートになる NIC
_mynet, _mygw, _mydns, _myip ラボネットワーク、ゲートウェイ、上位 DNS、オートメーション VM のアドレス
ROOT_PWD_HASH, ROOT_SSH_PUB_KEY オートメーション VM の root パスワードのハッシュと、ログインを許可する SSH 鍵
AUTOMATION_HOSTNAME オートメーション VM のホスト名（例：automation.mydemo.lab）
_QCOW_IMAGE ソース QCOW2 イメージのファイル名

ステップ 4：オートメーション VM を設定する

オートメーション VM に SSH で接続し、ラボのスクリプトをインストールします。

ssh <AUTOMATION_HOSTNAME>
./install_automation_node_scripts.sh

cp /etc/lab_creation.cfg.example /etc/lab_creation.cfg
vim /etc/lab_creation.cfg

lab_creation.cfg の主な設定：

設定 説明
REMOTE_HOST （プライマリ）KVM ハイパーバイザーのホスト名または IP
KVM_HOSTS （任意）マルチホストラボ用の追加ハイパーバイザーのスペース区切りリスト
ROOT_SSH_KEY VM に注入する SSH 公開鍵の内容
VIRT_SRV libvirt の接続 URI（例：qemu+ssh://root@hypervisor/system）
NETWORK VM のデフォルトの libvirt ネットワーク（例：bridge=br0）

HTTPとHTTPS。オートメーションVMは、ファイルをポート80（HTTP）とポート443（HTTPS、自己署名証明書は/etc/lab_creation/tls/）の両方で提供します。インストーラー（AutoYaST、kickstart、preseed）とHelmはHTTPSで取得し、自己署名証明書を受け入れます。証明書を検証するにはPROVISIONING_TLS_VERIFY=1を、別のアドレスを使うかHTTPに戻すにはPROVISIONING_BASE_URL（例：http://192.168.88.250）を設定します。HarvesterのiPXEネットワークブートは常にHTTPを使用します。iPXEは自己署名証明書を受け入れられないためです。

ステップ 5：クライアントの DNS をオートメーション VM に向ける

デスクトップからホスト名を解決するには：

# Linux (NetworkManager):
nmcli con mod <connection> ipv4.dns <AUTOMATION_IP>

# Or add to /etc/resolv.conf:
nameserver <AUTOMATION_IP>

Web UI（lab-builder）

lab.json ファイルをブラウザーで設計するツールで、実行時にプロジェクト自身の Python ライブラリを調べます。どのアドオンについても固定の知識を持っていません。コンポーネントを選ぶと、そのスキーマから直接フォームが生成されます。スクリプトにフィールドを追加すれば、フロントエンドを一切変更せずに UI に表示されます。

ノードレベルの任意フィールド：

フィールド 説明
addons この VM でのみ実行するアドオンの一覧。ノードごとの設定の上書きについては後述
config_method プロビジョニング方法の上書き（cloud-init、virt_customize、install_iso）
kvm_host マルチホストラボで、この VM を特定のハイパーバイザーに固定
extra_dsk 追加で接続するディスク。"/dev/sdb"、またはディスクごとにデフォルトのバスを変える場合は "/dev/sdb,bus=scsi"
salt_states 適用する Salt ステート（cloud-init 方式のみ）
VM_MACHINE virt-install のマシンタイプの上書き。""（デフォルト。virt-install の選択で、現在は q35）または "pc"（旧来の i440fx）。q35 ではカーネルや GRUB がルートディスクを見つけられない古いゲスト向けです。古いイメージのデプロイ（CentOS 7）を参照

ノードごとのアドオン設定の上書き：各アドオンには、addons にそれを列挙するすべてのノードが使う、 最上位の共有設定セクションが 1 つあります（例：前述の SMLM の例の client_registration）。同じアドオンに対して ノードごとに本当に異なる値が必要な場合（きっかけとなった例：1 台の共有 Uyuni/SMLM サーバーに多数の異なる OS を登録するラボで、 各ノードに固有の client_registration_activation_key が必要な場合）は、そのノードの addons[] のエントリーを単純な文字列ではなく、入れ子の上書きにします。

"nodes": {
  "mercury.mydemo.lab": {
    "addons": [
      { "client_registration": { "client_registration_activation_key": "1-sles15sp7" } }
    ]
  },
  "callisto.mydemo.lab": {
    "addons": [
      "mariadb",
      { "client_registration": { "client_registration_activation_key": "1-debian13" } }
    ]
  }
}

単純な文字列 "mariadb" のエントリーは従来どおりに動作します（共有の最上位セクション mariadb だけが適用されます）。 {"client_registration": {...}} の形式は、そのノードについてのみ、指定したフィールドだけを上書きします。 上書きで指定していない項目（サーバー、管理ユーザーなど）は、引き続き共有の client_registration セクションから取得されます。 これは client_registration に限らず、どのアドオンでも同じように機能します。各 install_<addon>.py は、 definition.get("<addon>", {}) を直接使う代わりに k8s.addon_node_config(definition, "<addon>", vm_name) で設定を読み込むことで対応します。addons[] リストを扱うすべての処理が共通で使う解析については、 libs/apps.py の addon_entry_name()/addon_entry_overrides() を参照してください。

kcluster の任意フィールド：

フィールド 説明
mgm_node クラスターのアドオンインストーラーを実行するノードのホスト名。デフォルトは最初のサーバーノード

すべてのアドオンスクリプトは --schema（--input-definition の別名）も受け付け、自身の設定キーを機械可読な JSON または YAML で出力します。Web UI がフォームを作るために読むのと同じスキーマです。

setup_lab.py --input-definition yaml   # base topology schema (common/nodes/kclusters)

古いイメージのデプロイ（CentOS 7）

CentOS 7（および同程度に古い既製の .qcow2 イメージ）には Ignition/Combustion も cloud-init も組み込まれていないため、config_method は virt_customize にする必要があります （VM のプロビジョニングを参照）。ゲスト内のエージェントに頼らず、qcow2 のファイルシステムを直接編集します。 これほど古いイメージでは、さらに 2 つの上書きが重要です。

  • VM_BOOT: "bios"：CentOS 7 の GRUB は、このプロジェクトのデフォルトである UEFI ではなく従来の BIOS を前提としています。
  • VM_MACHINE: "pc"：2015 年の CentOS 7 GenericCloud イメージ（カーネル 3.10.0-229）で動作します。virt-install のデフォルトのマシンタイプ（現在は q35）で起動すると、 dracut の緊急シェル（Not all disks have been found）で止まったままになります。Q35 の PCIe トポロジーでは、 virtio-blk のルートディスクが時間内に現れないためです。同じディスクは従来の i440fx チップセット（"pc"）では 問題なく起動します。これはチップセットと古いカーネルの非互換であり、このプロジェクト固有の問題ではありません。 十分に古いゲストには同じ上書きが使えます。
{
  "nodes": {
    "legacy1.mydemo.lab": {
      "myip": "192.168.88.120",
      "config_method": "virt_customize",
      "ISO_IMAGE": "CentOS-7-x86_64-GenericCloud-20150628_01.qcow2",
      "VM_BOOT": "bios",
      "VM_MACHINE": "pc"
    }
  },
  "common": { "VM_MEM": "2048", "VM_DSK": "30", "VM_CPU": "1", "VM_ROOT_PASS": "12345678" }
}

setup_lab.py legacy.json

VM_ROOT_PASS（common またはノードごと）は、virt_customize がイメージに直接書き込む root パスワードを設定します。省略すると、cloud-init や Ignition と同じく lab_creation.cfg の ROOT_PWD_HASH が使われます。

その他のディストリビューション（AlmaLinux、Debian、Rocky Linux、Alibaba Cloud Linux、および まだ動作しない Raspberry Pi OS の試みの記録）は EXAMPLES.md にあります。 このセクションが際限なく長くならないよう分けています。

ステップバイステップガイド

前述の例はコピー＆ペースト用の出発点です。ここでは 3 つの実際のシナリオを最初から最後まで通して説明します。何を実行するか、各ステップで何が起きるか、実際に動作したことをどう確認するかを扱います。以下の JSON フィールドとコマンドの形式は、すべてこのプロジェクト自身のテストスイート（tests/run_tests.sh）とソースコードに一致しています。

ガイド 1：最初のクラスター（RKE2 + Rancher + Longhorn）

目標：2 台の SLE Micro VM、RKE2 クラスター、管理用の Rancher、ストレージ用の Longhorn を作り、最後にブラウザーからアクセスできるようにします。

    }
  },
  "common": {
    "ISO_IMAGE": "SL-Micro.x86_64-6.1-Default-qcow-GM.qcow2",
    "VM_MEM": "24576", "VM_DSK": "80", "VM_CPU": "6",

      "addons": ["rancher", "longhorn"]
    }

  }
}
  1. 構築します：
setup_lab.py rancher-cluster.json

setup_lab.py は何かを行う前に自動でファイルを事前チェックします。誤った IP、存在しない kcluster の参照、ISO_IMAGE の欠落などは、途中で失敗するのではなく、何も作成しないまま検出されて表示されます（✗ Preflight FAILED — N error(s)）。問題のないファイルでは ✓ Preflight passed と表示され、そのまま構築に進みます。

処理の順序：両ノードを DNS に登録 → 両 VM を作成（QCOW2 イメージをコピーし、Combustion ファイルを生成して起動し、SSH を待つ）→ node101 にサーバーとして、続いて node102 にエージェントとして RKE2 をインストール → クラスターの管理ノード（mgm_node、デフォルトは最初のサーバーノードで、ここでは node101）に rancher と longhorn をインストール。Rancher 付きの 2 ノードクラスターは通常 15～25 分かかり、その大半は RKE2 の起動と Rancher の Helm インストールです。

  1. DNS の解決を確認します（自分のデスクトップをオートメーション VM の DNS に向けた後で）：
dig +short node101.mydemo.lab rancher.mydemo.lab

どちらも 192.168.88.101 を返すはずです（Rancher の ingress のホスト名は、クラスターの mydomain 配下の rancher_shorthn の値 rancher です）。

  1. ログインします。https://rancher.mydemo.lab を開き（自己署名証明書のため、ブラウザーが一度警告します）、オートメーション VM の /etc/lab_creation.cfg にある rancher_initial_pwd でログインします。

  2. すべてを作り直さずに繰り返します。ノードの設定を変えた、または VM がクラッシュした場合は、--keep を付けて再実行します。既に存在し、定義どおりの IP/MAC で、SSH で到達できる VM はそのまま残り、実際に欠けているものや壊れているものだけが（再）作成されます。

setup_lab.py --keep rancher-cluster.json
  1. 終わったら削除します：
destroy_lab.py rancher-cluster.json

上流の既知の問題（このプロジェクトのバグではありませんが、遭遇した場合に備えて記載します）：salt-transactional-update パッケージの更新スクリプトレットが、クライアントの /etc/salt/minion.d/transactional_update.conf に重複した YAML キーを残すことがあり、手作業で重複を削除するまで salt-minion が再起動を繰り返します。このリポジトリはそのファイルに一切触れません。

ガイド 3：NAT 配下のオートメーション VM（NIC が 1 つのノート PC をハイパーバイザーにする）

目標：ブリッジに使える空き NIC がないホストでオートメーション VM を構築します。代わりに libvirt が管理するプライベートネットワークを使い、ホスト自身の実 IP から特定のポートを DNAT で転送します。使い捨てのネストされた VM 上で最初から最後まで実機テスト済みです。

有効にしなければ、デフォルトのクイックスタートの流れは何も変わりません。_network_mode のデフォルトは "bridge" で、既存のどのセットアップともまったく同じです。

  1. lab.cfg で（クイックスタートのステップ 3）、次を設定します：
_network_mode="nat"
_nat_network_name="labnat"          # default shown — a new libvirt virtual network, not your host's real LAN
_nat_network_cidr="192.168.150.0/24" # default shown
_nat_forwarded_ports="22:22/TCP 80:80/TCP 443:443/TCP"  # default shown — "<port on the HYPERVISOR's real IP>:<port on the AUTOMATION VM>/<protocol>"

これにより、外部から到達できるハイパーバイザー自身の実 IP（<external>）のポート 22/80/443 が、オートメーション VM のプライベート NAT アドレス（<internal>）の同じポートへ転送されます。この時点でこのプライベートネットワークで待ち受けているのはオートメーション VM だけなので、ここでの「internal」は常に「オートメーション VM 上」を意味します。（後述のステップ 5 では、ラボの VM が存在するようになった後、まったく同じ <external>:<internal>/<protocol> 構文でラボの VM へ転送します。その場合「internal」はオートメーション VM ではなく、その VM のプライベート NAT アドレスを指します。）

  1. いつもどおりセットアップを実行します：
./setup_kvm_node.py

これにより、ブリッジの代わりに libvirt ネットワーク labnat（NAT。DHCP とゲートウェイは libvirt 自身が担当し、libvirt 組み込みの default ネットワークと同じ仕組みを、このプロジェクトの名前と CIDR で使います）が定義され、そのプライベート範囲内の固定 IP でオートメーション VM が作成され、上記の 3 つのポートがホストの実 IP から DNAT で転送されます。

  1. ハイパーバイザー上で、ネットワークと転送ルールが存在することを確認します：
virsh net-list                              # labnat: active
iptables -t nat -L LAB_PORTFWD -n -v         # DNAT rules to the automation VM's private IP
iptables -L LAB_PORTFWD_FWD -n -v            # matching FORWARD-chain ACCEPT rules
  1. ハイパーバイザーの外からオートメーション VM に接続します。オートメーション VM のプライベートアドレス 192.168.150.x（他のどこからもルーティングできません）ではなく、ハイパーバイザー自身の実 IP を使います：
ssh root@<hypervisor-real-ip>          # DNAT'd to the automation VM's SSH, port 22

ポート 80 と 443 もデフォルトで転送されます（プロビジョニングファイル用の HTTP サーバーと、Web UI をセットアップした場合はその HTTPS）。同じようにハイパーバイザーの実 IP 経由でアクセスできます。

  1. オートメーション VM だけでなくラボの VM にも転送を追加します。そのノードに forwarded_ports フィールドを与え、common.services で portforward サービスを一度有効にします：
{
  "nodes": {
    "app1.mydemo.lab": {
      "myip": "192.168.150.20",
      "forwarded_ports": ["8080:80/TCP", "8443:443/TCP"]
    }
  },
  "common": { "services": ["portforward"], "...": "…rest of common as usual" }
}

ラボ内のいずれかのノードが初めて forwarded_ports を宣言した時点で、setup_lab.py/setup_vm.py は同じ方法でそれら 2 つのポートをハイパーバイザーの実 IP から DNAT で転送します。

コンピュートバックエンド

ラボの VM はデフォルトで libvirt（前述の KVM ハイパーバイザー）を使います。別のバックエンドを使うには common.backend（またはそれより優先されるノードごとの backend）を設定します。現在の全一覧は backend フィールドの enum を参照してください。デフォルト以外の各バックエンドには、/etc/lab_creation.cfg に独自の認証情報が必要です。

libvirt でのコンソール表示：ラボの VM には SPICE ディスプレイ（--graphics spice,listen=0.0.0.0）が割り当てられますが、ハイパーバイザーの QEMU が SPICE に対応していない場合（SLES 16 など）は VNC になります。lab-in-a-box は実行ごとに一度 virsh domcapabilities からこれを読み取り、問い合わせに失敗した場合は SPICE を使います。

複数のクラウドアカウント（KVM_HOSTS で複数のハイパーバイザーを使うのと同じ方法）：各クラウドアカウントを /etc/lab_creation/credentials/（パスは lab_creation.cfg の CREDENTIALS_PATH で変更可能）配下の個別ファイル <name>.yaml に置きます（.json/.cfg も可。拡張子でパーサーが決まります。後述の暗号化形式に対応するのは .yaml/.json だけで、.cfg の平坦な KEY=value 形式では表現できません）。各ファイルは cloudtype（aws/gcp/hetzner/…）と、そのプロバイダーの通常の接続キーを宣言します。これはバックエンドが既に lab_creation.cfg から読み取っているキーとまったく同じです（AWS_REGION、AWS_PROFILE、AWS_SUBNET_ID など）。ノード（または common）は、"kvm_host": "<host>" とまったく同じように "cloud_account": "<name>" でアカウントを選びます。

// /etc/lab_creation/credentials/aws-sandbox.yaml  (built with setup_credentials.py, below)
"nodes": {
  "jupiter.mydemo.lab": { "cloud_account": "aws-sandbox" },
  "saturn.mydemo.lab":  { "cloud_account": "aws-prod" }
}

cloud_account を設定すると、その cloudtype がバックエンドになります（そのため backend フィールドは任意になり、両方を設定して食い違うと事前チェックがエラーになります）。また、アカウントファイルのキーが、そのノードについてだけ lab_creation.cfg に重ねて適用されます。すべての場所で cloud_account を省略すれば、現在の単一アカウントの動作は変わりません。各アカウントは独立したネットワークなので、後述のクラウド DNS VM はアカウントごとになります（lab-dns-aws-sandbox、lab-dns-aws-prod など）。名前のないデフォルトアカウントは単純な lab-dns-<backend> という名前のままです。

認証情報ファイルはデフォルトで暗号化して保存されます。次のコマンドで作成します。

setup_credentials.py                              # interactive: pick a provider, fill in its fields
setup_credentials.py --encrypt-existing myfile.yaml  # encrypt an already-written plaintext file's sensitive fields

暗号方式（libs/crypto_store.py を参照）：パスフレーズは Argon2id（意図的に遅くメモリを多く使う KDF。パスフレーズで暗号化したファイルの本当の安全性の境界は、暗号ではなくこの KDF です）を通して 512 ビットのマスターシークレットを導出します。続いて HKDF-SHA512 が独立した 256 ビットのサブキーを 2 つ導出します（単に半分に分けるのではなく、ラベルでドメインを分離）。データは AES-256-GCM の後に ChaCha20-Poly1305 をカスケードで適用して暗号化します。構造の異なる、独立した鍵を持つ 2 つの AEAD 暗号なので、どちらか一方のアルゴリズムが完全に破られても、それだけでは足りません。認証情報を必要とするツール（setup_lab.py、setup_vm.py など）は、すべてが通る唯一の関数である libs/primary.py の try_load_cloud_account() を通じて、実行ごとに一度パスフレーズを尋ねます（プロセスのメモリにのみ保持され、どこにも書き込まれません）。

ファイルは最上位に unencrypted: true を書くことで暗号化をしないこともできます（デフォルトではなく、setup_credentials.py はそのように書き込む前に確認します）。--encrypt-existing は機密に見えるフィールド（シークレット、パスワード、トークンらしい名前）だけをその場で暗号化し、たとえば AWS_REGION/AWS_PROFILE は読める状態のまま残します。入力ファイルは上書きせず、確認して配置できるように隣に <name>.encrypted.yaml を書き出します。オートメーション VM に Python パッケージ cryptography（python311-cryptography、または pip install cryptography。Argon2id には 41 以上）が必要です。実際に暗号化されたファイルを扱うときにだけ読み込まれるので、cloud_account を一度も設定しないラボでは新たな依存関係は不要です。

外部サービスの認証情報（SCC、SUSE Application Collection、Hermes など）。同じ /etc/lab_creation/credentials/ のストア、同じ暗号化、同じ setup_credentials.py ツールで、クラウドプロバイダー以外の外部サービスの認証情報も扱えます。ファイルには cloudtype の代わりに credential_kind（例：scc、appcollection、hermes）を記述するので、2 つの概念はディレクトリと形式を共有しながら衝突しません。外部サービスの認証情報を必要とする各アドオンは、それを明示的に指定するための任意フィールド <field>_account（例：smlm_scc_account、suse_ai_registry_account、hermes_account）を文書化しています。未設定の場合は、cloud_account と同じく、該当する credential_kind のファイルが 1 つだけあればそれが自動で使われます。ラボ JSON に平文で書く方法も引き続き完全に有効です。このストアは認証情報の任意の代替手段であり、必須ではありません。認証情報ストアを一切使わなくても、各アドオンの平文のフィールド（smlm_scc_user、suse_ai_registry_user、hermes_llm_api_key など）はそのまま動作します。

setup_credentials.py   # interactive — now asks "cloud provider or external service?" first

種類ごとの認証情報ファイル 1 つを、その種類を必要とするすべてのアドオンで再利用できます（例：1 つの scc ファイルで、どのアドオンの SCC 認証情報もまかなえます）。各アドオンの JSON フィールドの接頭辞には関係ありません。仕組みについては libs/addon_common.py の resolve_credential()/Validator.vreq_or_credential() と、libs/primary.py の *_service_credential* 関数を参照してください。

クラウドバックエンド（Hetzner/AWS/GCP/Alibaba/Scaleway/UpCloud/OVHcloud/Exoscale）と myip：クラウドバックエンドのノードでは、ラボ JSON の myip を空にしておきます。実際の IP は作成時にプロバイダーが割り当てて初めてわかるもので、libvirt/Harvester の固定 IP のように事前に決められるものではありません。setup_vm.py は create_vm() の戻り値から実際の IP を受け取り、ノードが実際に存在するようになった後で DNS に登録します（AWSBackend の実機テストで見つかった実際のバグ、2026-09-06。TODO を参照）。mymac もクラウドバックエンドでは意味がないので未設定のままにします。生成や重複チェックはされず、無視されます。

クラウド DNS VM：ラボのノードが特定のクラウドバックエンドを初めて使うとき、setup_vm.py は同じクラウドネットワーク内に、BIND を実行する小さく安価な DNS 用 VM（lab-dns-<backend>、例：lab-dns-aws）もプロビジョニングします（既にあれば再利用します）。クラウドのノードは通常 automation.mydemo.lab の BIND サーバーにまったく到達できない（自宅ラボの NAT/ルーターの内側にあり、インターネットから到達できない）ためです。複数ノードからなる実際のクラウドクラスターでは、ノード同士が名前解決できるよう、同じクラウドネットワーク内に独自の DNS サーバーが必要です。各クラウドノードの DNS エントリーは、この DNS VM と中央の automation.mydemo.lab のゾーンの両方に登録されます。既知の制限：(1) 新しく作成したクラウドノードは、まだ自動ではこの DNS VM を名前解決に使わないため、同じラボの 2 台目のクラウドノードは追加の設定なしでは 1 台目をホスト名で解決できません。(2) ノードはこの DNS VM にプライベート IP 経由で問い合わせます。クラウドの外からパブリック IP への DNS 問い合わせは、経路上のネットワークに横取りされることがあります。一部の ISP やルーターはすべての DNS 通信に自ら応答するためです。libs/backends.py の ensure_cloud_dns_vm() の docstring を参照してください。

クラウドインスタンスのサイズ：各クラウドバックエンドは、小さな組み込みテーブル（各行の「備考」列に記載）から、VM_CPU/VM_MEM を満たすプロバイダーの最小のインスタンスタイプ、サーバータイプ、プラン、フレーバーを選びます。このテーブルは上限として意図されたものではありません。優先順位の順に、2 つの方法で上書きできます。 1. cloud_instance_type（common またはノードごと。ノードの値が優先）：インスタンスタイプ、サーバータイプ、プラン、フレーバーの正確な名前で、自動選択は行わずそのまま使われます。OVHcloud（フレーバー一覧 API のその場での呼び出しを省略）や GCP（カスタムタイプ e2-custom-<cpu>-<mem> を作らない。代わりに n2-standard-4 のような実在の事前定義タイプを指定）を含め、すべてのクラウドバックエンドで同じように機能します。 2. *_INSTANCE_TYPES/*_SERVER_TYPES/*_PLANS 設定キー（下の各プロバイダーの行を参照）：組み込みテーブル自体を完全に置き換えます。VM_CPU/VM_MEM による自動選択は引き続き機能しますが、対象は独自のリストになります。形式：name:cores:mem_gb,name:cores:mem_gb,...（例：HETZNER_SERVER_TYPES=cx22:2:4,cx32:4:8,cx42:8:16）。テーブルはマージされず丸ごと置き換わるので、残したい組み込みエントリーも書き直してください。GCP と OVHcloud にはこのキーがありません。GCP は VM_CPU/VM_MEM から実際のカスタムマシンタイプを直接作り（置き換えるカタログがない）、OVHcloud は作成時に実際のフレーバー一覧をその場で問い合わせるためです（各行を参照）。

各チェックはそれぞれ独立した使い捨ての podman コンテナで実行されます。あるチェックのクラッシュ、ハング、残った状態が他のチェックに影響することはありません。

git の初回設定

リポジトリをクローンした後、次を実行します。

git config core.hooksPath .githooks

これにより .githooks/ のフックが有効になり、次のことを行います。 - 毎回のコミット前にテストスイート全体を実行する - スクリプトごとのバージョン埋め込みを管理する（後述）

バージョン管理の仕組み

これは上記の git フックがすべて処理します。__LABVERSION__ を手で編集することはありません。

すべてのスクリプトには次のプレースホルダーが含まれています。

__LABVERSION__ = "__LABVERSION__"

.githooks/ のフックが、このプレースホルダーを自動で展開・復元します。

フック 契機 動作
post-checkout git checkout / git switch 各スクリプトの __LABVERSION__ を、そのファイルを最後に変更したコミットのハッシュに置き換えます
post-merge git pull / git merge 上と同じ
post-rewrite git rebase / git commit --amend 上と同じ
pre-commit git commit コミットが書き込まれる前に、ステージされたスクリプトの __LABVERSION__ を復元します。そのため、ハッシュがリポジトリに保存されることはありません

結果として、作業ツリーの各スクリプトは --version で自身のバージョンを表示し、リポジトリには常に元のプレースホルダーが保存されます。install_automation_node_scripts.sh でスクリプトをインストールするときも、git log -1 --format=%h を使って同じファイルごとのハッシュ置換が行われます。

オートメーション VM へのスクリプトのインストール

オートメーション VM（またはリポジトリをクローンした任意のマシン）上で、リポジトリのルートから実行します。
