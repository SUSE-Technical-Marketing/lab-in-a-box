Pourquoi lab-in-a-box ?

  • Un fichier, une commande. Décrivez les machines virtuelles, les clusters Kubernetes (RKE2 ou K3s) et les extensions de manière déclarative. setup_lab.py les crée dans l'ordre des dépendances, sans avoir besoin d'exécuter virt-install ou Ansible manuellement.
  • Lab à la maison ou dans le cloud, la même définition. Les machines virtuelles du laboratoire s'exécutent sur vos hôtes KVM personnels, sur Harvester HCI ou sur AWS, Google Cloud, Alibaba Cloud, Hetzner, Scaleway, UpCloud, OVHcloud ou Exoscale. Les laboratoires peuvent s'étendre sur plusieurs hôtes KVM, et un seul laboratoire peut combiner les clouds et les emplacements via une superposition WireGuard inter-cloud.
  • 71 extensions pré-intégrées. Rancher, Longhorn, NeuVector, Harbor, Keycloak, Jenkins, Argo CD, SUSE Multi-Linux Manager/Uyuni, Nextcloud et bien d'autres, ainsi que des applications de démonstration intentionnellement vulnérables pour la formation à la sécurité.
  • Une interface web qui suit le code. lab-builder affiche chaque formulaire directement à partir du schéma de l'extension. Un nouveau champ dans un script apparaît dans l'interface utilisateur sans modifications du frontend.
  • Provisionnement interchangeable. Ignition et Combustion pour SLE Micro, cloud-init pour openSUSE et Ubuntu, virt-customize pour les anciennes images, ou installation guidée par script à partir d'une ISO d'installation réelle (AutoYaST, Kickstart, Preseed ou AutoInstall).
  • Identifiants en dehors du fichier de laboratoire. Les identifiants des services cloud et tiers peuvent résider dans des fichiers chiffrés par compte (dérivation de clé avec Argon2id, suivi de AES-256-GCM et ChaCha20-Poly1305 en cascade).
  • Tests conteneurisés. Chaque vérification s'exécute dans son propre conteneur podman jetable indépendant, et un crochet de pré-commit exécute les vérifications pertinentes.

Architecture

Le système est basé sur une architecture à deux niveaux :

Nœuds hyperviseur

Une ou plusieurs machines physiques (bare metal) avec KVM/QEMU. Chacun héberge les machines virtuelles du laboratoire et conserve les images sources QCOW2 dans /var/lib/libvirt/images/sources/. Un NUC, une station de travail ou toute machine x86_64 exécutant KVM suffit. Les laboratoires nécessitant plus de capacité qu'une seule machine ne peut en offrir peuvent s'étendre sur plusieurs hôtes KVM — voir Laboratoires multi-hôtes ci-dessous.

VM d'automatisation

Une petite machine virtuelle sur l'hyperviseur agissant comme plan de contrôle pour tout le laboratoire. Elle fournit :

  • DNS — BIND (named) sert le domaine du laboratoire et transfère les requêtes externes, de sorte que tous les noms d'hôte du laboratoire se résolvent depuis n'importe quel client qui le pointe
  • HTTP — sert les fichiers de provisionnement (Ignition, Combustion, cloud-init) dans /srv/www/htdocs/lab_creation/
  • Scripts — toutes les commandes de gestion du laboratoire, installées dans /usr/local/bin/
  • Interface web (optionnelle) — lab-builder, un concepteur basé sur navigateur pour les fichiers lab.json

Toutes les commandes de l'utilisateur s'exécutent sur la VM d'automatisation. Elle se connecte via SSH à l'hyperviseur ou aux hyperviseurs et aux machines virtuelles créées. Après la configuration initiale, aucun accès direct à l'hyperviseur n'est requis.

Sous le capot

Les outils de ligne de commande et chaque extension sont en Python 3.11, résidant dans libs/ et scripts/, et installés dans /usr/local/lib/lab_creation/. Elles sont organisées autour d'un petit ensemble de modules de bibliothèque partagée (lab_creation.py, backends.py, services.py, spacecmd_common.py, …) qui ne dépendent pas les uns des autres. La création de machines virtuelles s'effectue via une interface VMBackend interchangeable avec dix implémentations : libvirt, Harvester et huit clouds publics (voir Backends de calcul). Les extensions et le code d'orchestration ne changent pas entre eux. Les implémentations Bash qu'elles ont remplacées sont archivées sous legacy_bash/ — y compris le install_ds389 d'origine.

Fonctionnement

Pipeline de déploiement

setup_lab.py exécute une séquence fixe de phases. Les deux phases spécifiques à Kubernetes sont complètement ignorées pour un laboratoire sans section kclusters :

Provisionnement des machines virtuelles

Chaque machine virtuelle est créée comme suit : 1. Déterminer quel hôte KVM l'héberge (le champ explicite kvm_host ou sélection automatique par capacité libre — voir Laboratoires multi-hôtes) 2. Copier et agrandir une image source QCOW2 sur cet hôte 3. Générer les fichiers de provisionnement à partir de modèles selon sa config_method 4. Enregistrer une entrée DNS dans BIND 5. Exécuter virt-install sur l'hyperviseur via SSH 6. Attendre que SSH soit disponible

La méthode de provisionnement est contrôlée par config_method dans le JSON du laboratoire (par nœud ou dans common) :

Valeur Méthode Utilisée pour
(vide, défaut) Ignition + Combustion SLE Micro
cloud-init ISO cloud-init openSUSE Leap, Ubuntu
virt_customize Modifie QCOW2 directement sur l'hyperviseur (virt-customize) — aucun support Ignition/cloud-init requis sur le système invité CentOS 7, RHEL/Debian anciens ou toute image sans Ignition/cloud-init
install_iso Installation guidée par script à partir d'une ISO d'installation réelle (AutoYaST, Kickstart, Preseed ou AutoInstall, sélectionnée via install_type) Distributions sans autre voie de provisionnement

Backends de calcul

L'interface VMBackend interchangeable détermine où la machine virtuelle d'un nœud est créée. Elle est résolue une fois par nœud à partir de son champ backend (ou de cloud_account, qui implique le backend). Le défaut est libvirt. Chaque extension et script d'orchestration parle au backend résolu de la même manière, peu importe lequel c'est :

Backend Où s'exécute la machine virtuelle
libvirt Un hyperviseur KVM/QEMU que vous exploitez (défaut)
harvester Un cluster Harvester HCI, en tant que KubeVirt VirtualMachines
aws Amazon EC2
gcp Google Compute Engine
alibaba Alibaba Cloud ECS
hetzner Hetzner Cloud
scaleway Scaleway Instances
upcloud UpCloud
ovhcloud OVHcloud Public Cloud
exoscale Exoscale

Configuration de Kubernetes

Une fois les machines virtuelles en cours d'exécution, setup_lab.py installe Kubernetes sur chaque nœud conformément à la section kclusters du JSON. RKE2 et K3s sont tous deux pris en charge. Une fois qu'un cluster est prêt, ses extensions s'exécutent séquentiellement. Les extensions au niveau des machines virtuelles (assignées à un nœud individuel plutôt qu'à un cluster) s'exécutent plus tard une fois ce nœud provisionné.

Ordre de chargement des bibliothèques

Chaque script lit la configuration dans cet ordre :

  1. /etc/lab_creation.defaults — valeurs par défaut du système, chemins, listes de paquets
  2. /usr/local/lib/lab_creation/primary.py — validation d'entrée, chargement de configuration
  3. /etc/lab_creation.cfg — paramètres spécifiques au nœud (REMOTE_HOST, ROOT_SSH_KEY, VIRT_SRV, KVM_HOSTS, etc.)
  4. /usr/local/lib/lab_creation/lab_creation.py — fonctions de machine virtuelle, DNS et orchestration
  5. /usr/local/lib/lab_creation/k8s.py — fonctions de cluster Kubernetes

Démarrage rapide

Prérequis

  • Une machine capable de exécuter KVM (Intel VT-x ou AMD-V activé)
  • Accès Internet (ou un miroir local) pour télécharger les paquets et images
  • Une image QCOW2 pour le système d'exploitation choisi dans /var/lib/libvirt/images/sources/ sur l'hyperviseur

La VM d'automatisation nécessite spécifiquement python3.11 — la chaîne d'outils y est explicitement fixée. La plupart des distributions fournissent un python3 standard plus ancien en sus. Le script d'installation s'arrête si python3.11 manque.

Images testées : - SLE Micro — recommandée, utilisée avec Ignition+Combustion - openSUSE Leap Micro — prise en charge, utilisée avec cloud-init

Étape 1 — Préparer le système d'exploitation de l'hyperviseur

Installez SLES (ou une autre distribution Linux capable de KVM) sur votre matériel. Pendant l'installation, sélectionnez : - Réseautage : créer un pont (br0) connecté à votre NIC principal, avec une IP fixe - Rôle du système : Hôte de virtualisation KVM

Étape 2 — Amorcer les scripts de configuration

À partir de n'importe quelle machine Linux ayant accès SSH à l'hyperviseur :

curl https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | bash -

Cela télécharge les scripts de configuration dans /var/tmp/setup_demo_server/.

Étape 3 — Configurer et exécuter la configuration du nœud KVM

cd /var/tmp/setup_demo_server/setup_demo_server/
vim lab.cfg

Puis exécutez la configuration (remplacez <IP> par l'IP de votre hyperviseur, ou omettez pour local) :

./setup_kvm_node.py <IP>

Cela provisionne la VM d'automatisation et démarre tous les services requis.

Étape 4 — Configurer la VM d'automatisation

Connectez-vous via SSH à la VM d'automatisation et installez les scripts du laboratoire :

ssh <AUTOMATION_HOSTNAME>
./install_automation_node_scripts.sh

cp /etc/lab_creation.cfg.example /etc/lab_creation.cfg
vim /etc/lab_creation.cfg

Étape 5 — Pointer le DNS du client vers la VM d'automatisation

Pour que les noms d'hôte se résolvent depuis votre bureau :

# Linux (NetworkManager):
nmcli con mod <connection> ipv4.dns <AUTOMATION_IP>

# Ou ajoutez à /etc/resolv.conf:
nameserver <AUTOMATION_IP>

Étape 6 — Créer votre premier laboratoire

setup_lab.py examples/cluster.json.template

Vous trouverez d'autres points de départ ci-dessous dans Exemples. Alternativement, vous pouvez ouvrir l'interface web au lieu d'écrire JSON manuellement.

Interface web (lab-builder)

Un concepteur de fichiers lab.json basé sur navigateur qui évalue les propres bibliothèques Python du projet au moment de l'exécution. Il n'a aucune connaissance intégrée de toute extension. Sélectionnez un composant et un formulaire sera rendu directement à partir de son schéma. Ajoutez un champ à un script et l'interface utilisateur l'affichera sans modifications du frontend.

# Le moyen le plus rapide de l'essayer — zéro dépendance au-delà de Python:
python3.11 webui/run-local.py            # → http://localhost:8677/

Pour la production (Apache ou un service systemd/init autonome, plus HTTPS sur un certificat auto-signé créé de manière idempotente) voir README.webui.md. Là sont décrits les trois modes d'exploitation, l'API HTTP et la résolution des problèmes.

Format de définition du laboratoire

Les laboratoires sont définis en tant que fichiers JSON ou YAML (détection automatique, voir la remarque ci-dessous). Le format actuel prend en charge plusieurs clusters Kubernetes par laboratoire (kclusters). Le format pour un seul cluster (cluster) se trouve dans examples/cluster.json.template.

De nombreuses autres sections (procédures détaillées, références et exemples) se trouvent dans la documentation complète sur GitHub.
