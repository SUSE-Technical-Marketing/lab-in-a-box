Warum lab-in-a-box?

  • Eine Datei, ein Befehl. Beschreiben Sie VMs, Kubernetes-Cluster (RKE2 oder K3s) und Add-ons deklarativ. setup_lab.py baut sie in Abhängigkeitsreihenfolge auf, ohne dass Sie virt-install oder Ansible von Hand ausführen müssen.
  • Home-Lab oder Cloud, dieselbe Definition. Lab-VMs laufen auf KVM-Hosts, die Ihnen gehören, auf Harvester HCI oder auf AWS, Google Cloud, Alibaba Cloud, Hetzner, Scaleway, UpCloud, OVHcloud oder Exoscale. Labs können sich über mehrere KVM-Hosts erstrecken, und ein einzelnes Lab kann über ein Cross-Cloud-WireGuard-Overlay Clouds und Standorte kombinieren.
  • 72 vorgefertigte Add-ons. Rancher, Longhorn, NeuVector, Harbor, Keycloak, Jenkins, Argo CD, SUSE Multi-Linux Manager/Uyuni, Nextcloud und weitere, dazu bewusst verwundbare Demo-Anwendungen für Security-Schulungen.
  • Eine Web-UI, die dem Code folgt. lab-builder rendert jedes Formular aus dem eigenen Schema des Add-ons. Ein neues Feld in einem Skript erscheint deshalb in der UI, ohne dass am Frontend etwas geändert werden muss.
  • Austauschbare Bereitstellung. Ignition und Combustion für SLE Micro, cloud-init für openSUSE und Ubuntu, virt-customize für ältere Images oder eine skriptgesteuerte Installation von einem Installations-ISO (AutoYaST, Kickstart, Preseed oder AutoInstall).
  • Zugangsdaten außerhalb der Lab-Datei. Cloud- und Service-Zugangsdaten können in verschlüsselten Dateien pro Konto liegen (Schlüsselableitung mit Argon2id, danach AES-256-GCM und ChaCha20-Poly1305 hintereinandergeschaltet).
  • Containerisierte Tests. Jede Prüfung läuft in einem Wegwerf-Podman-Container, und ein Pre-Commit-Hook führt die relevanten Prüfungen aus.

Architektur

Das System basiert auf einer zweistufigen Architektur:

Hypervisor-Knoten

Eine oder mehrere physische Maschinen (Bare Metal) mit KVM/QEMU. Jeder hostet Lab-VMs und hält QCOW2-Quellimages in /var/lib/libvirt/images/sources/. Ein NUC, eine Workstation oder jede x86_64-Maschine, die KVM ausführen kann, reicht aus. Labs, die mehr Kapazität brauchen als eine Maschine bietet, können sich über mehrere KVM-Hosts erstrecken — siehe unten Multi-Host-Labs.

Automatisierungs-VM

Eine kleine VM auf dem Hypervisor, die als Steuerungsebene für das gesamte Lab dient. Sie stellt bereit:

  • DNS — BIND (named) bedient die Lab-Domäne und leitet externe Anfragen weiter, sodass alle Lab-Hostnamen von jedem Client aufgelöst werden, der darauf zeigt
  • HTTP — liefert Bereitstellungsdateien (Ignition, Combustion, cloud-init) unter /srv/www/htdocs/lab_creation/
  • Skripte — alle Lab-Verwaltungsbefehle, installiert unter /usr/local/bin/
  • Web-UI (optional) — lab-builder, ein browserbasierter Designer für lab.json-Dateien

Alle Benutzerbefehle werden auf der Automatisierungs-VM ausgeführt. Sie verbindet sich per SSH mit dem Hypervisor bzw. den Hypervisoren und mit den erstellten VMs. Nach der Ersteinrichtung ist kein direkter Hypervisor-Zugriff mehr nötig.

Technische Details

Die Kommandozeilenwerkzeuge und jedes Add-on sind Python 3.11, liegen in libs/ und scripts/ und werden nach /usr/local/lib/lab_creation/ installiert. Sie sind um einen kleinen Satz gemeinsamer Bibliotheksmodule herum organisiert (lab_creation.py, backends.py, services.py, spacecmd_common.py, …), die nicht voneinander abhängen. Die VM-Erstellung läuft über eine austauschbare VMBackend-Schnittstelle mit zehn Implementierungen: libvirt, Harvester und acht öffentliche Clouds (siehe Compute-Backends). Add-ons und Orchestrierungscode ändern sich deshalb zwischen ihnen nicht. Die Bash-Implementierungen, die sie ersetzt haben, liegen archiviert unter legacy_bash/ — darunter das ursprüngliche install_ds389.

So funktioniert es

Bereitstellungspipeline

setup_lab.py führt eine feste Abfolge von Phasen aus. Die beiden Kubernetes-spezifischen Phasen werden für ein Lab ohne VMs-und-Kubernetes-Anteil (also ohne Abschnitt kclusters) vollständig übersprungen:

VM-Bereitstellung

Jede VM wird wie folgt erstellt: 1. Ermitteln, auf welchem KVM-Host sie liegt (das explizite Feld kvm_host oder automatische Auswahl nach freier Kapazität — siehe Multi-Host-Labs) 2. Kopieren und Vergrößern eines QCOW2-Quellimages auf diesem Host 3. Erzeugen der Bereitstellungsdateien aus Vorlagen gemäß ihrem config_method 4. Registrieren eines DNS-Eintrags in BIND 5. Ausführen von virt-install auf dem Hypervisor per SSH 6. Warten, bis SSH verfügbar ist

Die Bereitstellungsmethode wird über config_method in der Lab-JSON gesteuert (pro Knoten oder pro common):

Wert Methode Verwendet für
(leer, Standard) Ignition + Combustion SLE Micro
cloud-init cloud-init-ISO openSUSE Leap, Ubuntu
virt_customize Ändert das QCOW2 direkt auf dem Hypervisor (virt-customize) — im Gast ist keine Ignition-/cloud-init-Unterstützung nötig CentOS 7, ältere Debian/RHEL oder jedes Image ohne Ignition/cloud-init
install_iso Skriptgesteuerte Installation von einem echten Installations-ISO (AutoYaST, Kickstart, Preseed oder AutoInstall, ausgewählt über install_type) Distributionen ohne anderen Bereitstellungsweg

Compute-Backends

Wo die VM eines Knotens erstellt wird, entscheidet eine austauschbare VMBackend-Schnittstelle. Sie wird pro Knoten einmal aus dessen Feld backend ermittelt (oder aus cloud_account`, das das Backend impliziert). Standard ist libvirt. Jedes Add-on und jedes Orchestrierungsskript spricht das ermittelte Backend auf die gleiche Weise an, egal welches es ist:

Backend Wo die VM läuft
libvirt Ein von Ihnen betriebener KVM/QEMU-Hypervisor (Standard)
harvester Ein Harvester-HCI-Cluster, als KubeVirt-VirtualMachines
aws Amazon EC2
gcp Google Compute Engine
alibaba Alibaba Cloud ECS
hetzner Hetzner Cloud
scaleway Scaleway Instances
upcloud UpCloud
ovhcloud OVHcloud Public Cloud
exoscale Exoscale

Kubernetes-Einrichtung

Sobald die VMs laufen, installiert setup_lab.py Kubernetes auf jedem Knoten gemäß dem Abschnitt kclusters der JSON. RKE2 und K3s werden beide unterstützt. Sobald ein Cluster bereit ist, laufen seine Add-ons nacheinander. VM-Add-ons (einem einzelnen Knoten statt einem Cluster zugeordnet) laufen danach, sobald dieser Knoten bereitgestellt ist.

Multi-Host-Labs

Ein Lab ist nicht auf einen Hypervisor beschränkt. Setzen Sie KVM_HOSTS (durch Leerzeichen getrennt) in /etc/lab_creation.cfg auf der Automatisierungs-VM, um mehr als einen Hypervisor verfügbar zu machen:

KVM_HOSTS="hv1.mydemo.lab hv2.mydemo.lab hv3.mydemo.lab"

Dann gilt für jeden Knoten in der Lab-JSON entweder: - explizit festlegen — "kvm_host": "hv2.mydemo.lab" in der Konfiguration dieses Knotens, oder - automatisch wählen lassen — kvm_host weglassen; der Knoten landet auf dem konfigurierten Host, der gerade genug freie CPU/RAM/Festplatte hat (live per SSH geprüft).

Knoten ohne kvm_host und Systeme mit nur einem konfigurierten Host verhalten sich genau wie vor dieser Funktion — für ein Lab mit einem Hypervisor ändert sich nichts.

Cross-Cloud-WireGuard-Overlay

Ein Cloud-Labknoten kann im Allgemeinen nicht über das Netzwerk das private Netz eines anderen Cloud-Kontos oder das Home-libvirt-Lab erreichen, weil jedes ein eigenes, isoliertes VPC/Netzwerk ist. common.overlay: true in der Lab-JSON verbindet die STANDORTE dieses Labs untereinander, Site-to-Site, über ihre echten Subnetze, über ein Hub-and-Spoke-WireGuard-Overlay (libs/overlay.py):

Nur das Gateway jedes Standorts tritt dem Overlay selbst bei, niemals ein einzelner Lab-Knoten. Ein „Standort“ ist das Home-libvirt-Lab oder ein Cloud-Konto. Sein Gateway ist entweder die Automatisierungs-VM des Heimstandorts (mysource in /etc/lab_creation.cfg) oder bei einem Cloud-Konto eine kleine eigens dort angelegte bzw. wiederverwendete VM (lab-overlay-gw-<backend>[-<account>], nach derselben Namenskonvention wie die Cloud-DNS-VM). Jeder ANDERE Knoten erhält nur eine einfache, dauerhafte lokale Route zum echten Subnetz jedes anderen Standorts, über das Gateway seines eigenen Standorts. Mehr ist der Mechanismus nicht, und einzelne Knoten sind nie WireGuard-Mitglieder.

OVERLAY_HUB_ACCOUNT (erforderlich, in /etc/lab_creation.cfg) nennt das Cloud-Konto, dessen Gateway-VM der Hub ist, also der Standort mit einer festen öffentlichen IP, mit der sich alle anderen verbinden. OVERLAY_CIDR (Standard 10.99.0.0/16) dient nur den Point-of-Presence-Adressen der Gateways auf dem Tunnel, nicht dem Routing echten Datenverkehrs. OVERLAY_WG_PORT (Standard 51820) ist der Listen-Port des Hubs. Beitreten, Verlassen und das Verteilen der Routen geschehen automatisch als Teil von setup_vm.py. Sie müssen nichts von Hand ausführen.

Bekannte Lücken: Es werden keine DNS-Änderungen vorgenommen. Ein Knoten ist über seinen echten Hostnamen erreichbar, sobald dieser Name in ein nun geroutetes Subnetz auflöst, vorher nicht. Bereits bereitgestellte Knoten eines Standorts werden nicht rückwirkend neu geroutet, wenn später ein neuer entfernter Standort beitritt. Sie werden nur bei der nächsten Bereitstellung des jeweiligen Knotens aktualisiert. AWS braucht für die Weiterleitung von Datenverkehr das Deaktivieren der „Source/Dest Check“ am Gateway des Standorts (wird automatisch erledigt). Ein Äquivalent für die anderen 7 Cloud-Backends gibt es noch nicht.

Reihenfolge beim Laden der Bibliotheken

Jedes Skript liest die Konfiguration in dieser Reihenfolge ein:

  1. /etc/lab_creation.defaults — Systemstandards, Pfade, Paketlisten
  2. /usr/local/lib/lab_creation/primary.py — Eingabevalidierung, Laden der Konfiguration
  3. /etc/lab_creation.cfg — knotenspezifische Einstellungen (REMOTE_HOST, ROOT_SSH_KEY, VIRT_SRV, KVM_HOSTS usw.)
  4. /usr/local/lib/lab_creation/lab_creation.py — VM-, DNS- und Orchestrierungsfunktionen
  5. /usr/local/lib/lab_creation/k8s.py — Kubernetes-Clusterfunktionen

Schnellstart

Voraussetzungen

  • Eine Maschine, die KVM ausführen kann (Intel VT-x oder AMD-V aktiviert)
  • Internetzugang (oder ein lokaler Spiegel) für Paket- und Image-Downloads
  • Ein QCOW2-Image für das gewählte Betriebssystem unter /var/lib/libvirt/images/sources/ auf dem Hypervisor

Die Automatisierungs-VM braucht konkret python3.11 — der Toolchain ist explizit darauf festgelegt. Die meisten Distributionen liefern daneben ein älteres Standard-python3 mit. Das Installationsskript bricht ab, wenn python3.11 fehlt.

Getestete Images: - SLE Micro — empfohlen, mit Ignition+Combustion verwendet - openSUSE Leap Micro — unterstützt, mit cloud-init verwendet

Schritt 1 — Hypervisor-Betriebssystem vorbereiten

Installieren Sie SLES (oder eine andere KVM-fähige Linux-Distribution) auf Ihrer Hardware. Wählen Sie bei der Installation: - Netzwerk: eine Bridge (br0) anlegen, die mit Ihrer Haupt-NIC verbunden ist, mit einer festen IP - Systemrolle: KVM Virtualization Host

Bootfähigen USB-Stick unter Linux erstellen 
# Before inserting USB:
cat /proc/partitions > /tmp/partb4

# Insert USB, then:
cat /proc/partitions > /tmp/parta

# Find the new device:
diff /tmp/part*

Der nächste Befehl löscht alle Daten auf dem Zielgerät. Prüfen Sie sdX gegen die diff-Ausgabe oben, bevor Sie ihn ausführen.

# Write the ISO (replace sdX with your device):
dd if=SLE-15-SP6-Online-x86_64-GM-Media1.iso of=/dev/sdX bs=4k && sync

Schritt 2 — Setup-Skripte bootstrappen

Von jeder Linux-Maschine mit SSH-Zugang zum Hypervisor aus:

curl https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | bash -

Dies lädt die Setup-Skripte nach /var/tmp/setup_demo_server/.

Schritt 3 — KVM-Knoten-Setup konfigurieren und ausführen

cd /var/tmp/setup_demo_server/setup_demo_server/
vim lab.cfg

Wichtige Einstellungen in lab.cfg:

Einstellung Beschreibung
ROOT_PWD_HASH Gehashtes Root-Passwort — erzeugen mit mkpasswd --method=SHA-512 --stdin
ROOT_SSH_PUB_KEY Ihr öffentlicher SSH-Schlüssel für passwortlosen Zugriff
AUTOMATION_HOSTNAME Hostname der Automatisierungs-VM (z. B. automation.mydemo.lab)
_QCOW_IMAGE Dateiname des QCOW2-Quellimages
Netzwerkeinstellungen IP, Gateway, Maske, DNS für das Lab-Netz

Starten Sie dann das Setup (ersetzen Sie <IP> durch die IP Ihres Hypervisors, oder lassen Sie es für lokal weg):

./setup_kvm_node.py <IP>

Dies stellt die Automatisierungs-VM bereit und startet alle erforderlichen Dienste.

Schritt 4 — Automatisierungs-VM konfigurieren

Verbinden Sie sich per SSH mit der Automatisierungs-VM und installieren Sie die Lab-Skripte:

ssh <AUTOMATION_HOSTNAME>
./install_automation_node_scripts.sh

cp /etc/lab_creation.cfg.example /etc/lab_creation.cfg
vim /etc/lab_creation.cfg

Wichtige Einstellungen in lab_creation.cfg:

Einstellung Beschreibung
REMOTE_HOST Hostname oder IP des (primären) KVM-Hypervisors
KVM_HOSTS (optional) durch Leerzeichen getrennte Liste weiterer Hypervisoren für ein Multi-Host-Lab
ROOT_SSH_KEY Inhalt des öffentlichen SSH-Schlüssels, der in die VMs eingefügt wird
VIRT_SRV libvirt-Verbindungs-URI (z. B. qemu+ssh://root@hypervisor/system)
NETWORK Standard-libvirt-Netzwerk für VMs (z. B. bridge=br0)

Schritt 5 — Client-DNS auf die Automatisierungs-VM zeigen lassen

Damit Hostnamen von Ihrem Desktop aus aufgelöst werden:

# Linux (NetworkManager):
nmcli con mod <connection> ipv4.dns <AUTOMATION_IP>

# Or add to /etc/resolv.conf:
nameserver <AUTOMATION_IP>

Schritt 6 — Das erste Lab bauen

setup_lab.py examples/cluster.json.template

Web-UI (lab-builder)

Ein browserbasierter Designer für lab.json-Dateien, der die eigenen Python-Bibliotheken des Projekts zur Laufzeit auswertet. Er hat kein fest eingebautes Wissen über ein Add-on. Wählen Sie eine Komponente, und es wird ein Formular direkt aus deren Schema gerendert. Fügen Sie ein Feld zu einem Skript hinzu, und die UI zeigt es ohne jede Frontend-Änderung an.

# Fastest way to try it — zero dependencies beyond Python:
python3.11 webui/run-local.py            # → http://localhost:8677/

Für den Produktionsbetrieb (Apache oder ein eigenständiger systemd-/init-unabhängiger Dienst, plus HTTPS über ein idempotent erzeugtes selbstsigniertes Zertifikat) siehe README.webui.md. Dort werden alle drei Betriebsarten, die HTTP-API und die Fehlersuche beschrieben.

Format der Lab-Definition

Labs werden als JSON- oder YAML-Dateien definiert (automatisch erkannt, siehe Hinweis unten). Das aktuelle Format unterstützt mehrere Kubernetes-Cluster pro Lab (kclusters). Das Format für einen einzelnen Cluster (cluster) finden Sie in examples/cluster.json.template.

Auch eine Datei .yaml/.yml funktioniert. Das Format wird anhand der Dateiendung erkannt (oder, falls eine Datei kein gültiges JSON ist, durch Rückgriff auf YAML). Dasselbe gilt für die Prüfung durch den Preflight von setup_lab.py, für install_<addon> --validate und für den Ladepfad jedes Add-ons. YAML-Eingaben benötigen pyyaml (pip install pyyaml) auf der Automatisierungs-VM. Optionale Felder auf Knotenebene:

Feld Beschreibung
addons Liste der Add-on-Skripte, die nur für diese VM laufen. Pro-Knoten-Konfigurationsüberschreibungen siehe unten.
config_method Überschreibt die Bereitstellungsmethode (cloud-init, virt_customize, install_iso)
kvm_host Diese VM an einen bestimmten Hypervisor binden, in einem Multi-Host-Lab
extra_dsk Zusätzliche Festplatte(n), die angehängt werden: "/dev/sdb" oder "/dev/sdb,bus=scsi", um den Standardbus pro Festplatte zu überschreiben
salt_states Anzuwendende Salt-States (nur bei der cloud-init-Methode)
VM_MACHINE Überschreibt den Maschinentyp von virt-install — "" (Standard, die Wahl von virt-install, derzeit q35) oder "pc" (älteres i440fx), für einen alten Gast, dessen Kernel/GRUB seine Root-Festplatte unter q35 nicht findet — siehe Bereitstellung eines Legacy-Images (CentOS 7)

Konfigurationsüberschreibungen für Add-ons pro Knoten: Jedes Add-on hat einen gemeinsamen Konfigurationsabschnitt auf oberster Ebene (z. B. client_registration im früheren SMLM-Beispiel), den jeder Knoten nutzt, der es in addons aufführt. Wenn verschiedene Knoten für dasselbe Add-on wirklich unterschiedliche Werte brauchen — der Hauptfall: ein Lab, das viele verschiedene Betriebssysteme gegen einen gemeinsamen Uyuni-/SMLM-Server registriert, wobei jeder Knoten seinen eigenen client_registration_activation_key braucht — geben Sie dem Eintrag von addons[] dieses einen Knotens eine verschachtelte Überschreibung statt einer einfachen Zeichenkette:

"nodes": {
  "mercury.mydemo.lab": {
    "addons": [
      { "client_registration": { "client_registration_activation_key": "1-sles15sp7" } }
    ]
  },
  "callisto.mydemo.lab": {
    "addons": [
      "mariadb",
      { "client_registration": { "client_registration_activation_key": "1-debian13" } }
    ]
  }
}

Ein einfacher Eintrag "mariadb" verhält sich genau wie zuvor (nur der gemeinsame Abschnitt mariadb auf oberster Ebene gilt). Die Form {"client_registration": {...}} überschreibt nur diese Felder, und zwar nur für diesen Knoten. Alles, was die Überschreibung nicht nennt (Server, Admin-Benutzer usw.), kommt weiterhin aus dem gemeinsamen Abschnitt client_registration. Das funktioniert auf dieselbe Weise für jedes Add-on, nicht nur für client_registration. Jedes install_<addon>.py macht mit, indem es seine Konfiguration über k8s.addon_node_config(definition, "<addon>", vm_name) liest, statt direkt definition.get("<addon>", {}). Die gemeinsame Auswertung, über die jeder Verbraucher einer Liste addons[] geht, steht in addon_entry_name()/addon_entry_overrides() in libs/apps.py.

Optionale Felder für kclusters:

Feld Beschreibung
mgm_node Hostname des Knotens, der die Installationsprogramme der Cluster-Add-ons ausführt. Standard ist der erste Server-Knoten.

Jedes Add-on-Skript akzeptiert außerdem --schema (Alias für --input-definition). Es gibt seine eigenen Konfigurationsschlüssel als maschinenlesbares JSON oder YAML aus. Dasselbe Schema liest auch die Web-UI aus, um ihre Formulare zu erzeugen:

install_longhorn --schema
setup_lab.py --input-definition yaml   # base topology schema (common/nodes/kclusters)

Bereitstellung eines Legacy-Images (CentOS 7)

CentOS 7 (und andere vorgefertigte .qcow2-Images dieses Alters) enthalten weder Ignition/Combustion noch cloud-init. Deshalb muss config_method auf virt_customize stehen (siehe VM-Bereitstellung). Dabei wird das qcow2-Dateisystem direkt bearbeitet, statt sich auf einen Agenten im Gast zu verlassen. Bei einem so alten Image sind zwei weitere Überschreibungen wichtig:

  • VM_BOOT: "bios" — der GRUB von CentOS 7 erwartet legacy BIOS, nicht das UEFI-Standardverhalten dieses Projekts.
  • VM_MACHINE: "pc" — funktioniert mit einem CentOS-7-GenericCloud-Image von 2015 (Kernel 3.10.0-229). Unter dem Maschinentyp-Standard von virt-install (derzeit q35) hängt es dauerhaft in einer dracut-Notfall-Shell (Not all disks have been found). Seine virtio-blk-Root-Festplatte taucht unter der PCIe-Topologie von Q35 nicht rechtzeitig auf. Dieselbe Festplatte startet problemlos mit dem älteren Chipsatz i440fx ("pc"). Das ist eine Inkompatibilität von Chipsatz und altem Kernel und nichts Spezifisches für dieses Projekt. Dieselbe Überschreibung gilt für jeden hinreichend alten Gast.
{
  "nodes": {
    "legacy1.mydemo.lab": {
      "myip": "192.168.88.120",
      "config_method": "virt_customize",
      "ISO_IMAGE": "CentOS-7-x86_64-GenericCloud-20150628_01.qcow2",
      "VM_BOOT": "bios",
      "VM_MACHINE": "pc"
    }
  },
  "common": { "VM_MEM": "2048", "VM_DSK": "30", "VM_CPU": "1", "VM_ROOT_PASS": "12345678" }
}

setup_lab.py legacy.json

VM_ROOT_PASS (in common oder pro Knoten) legt das Root-Passwort fest, das virt_customize direkt in das Image einbringt. Lassen Sie es weg, um stattdessen ROOT_PWD_HASH aus lab_creation.cfg zu verwenden. Das ist derselbe Rückgriff, den cloud-init und Ignition nutzen.

Weitere Distributionen (AlmaLinux, Debian, Rocky Linux, Alibaba Cloud Linux und ein dokumentierter, noch nicht funktionierender Versuch mit Raspberry Pi OS) stehen in EXAMPLES.md. Sie stehen dort, damit dieser Abschnitt nicht unbegrenzt wächst.

Anleitung 1 — Ihr erster Cluster: RKE2 + Rancher + Longhorn

Ziel: zwei SLE-Micro-VMs, ein RKE2-Cluster, Rancher zur Verwaltung und Longhorn für den Speicher. Am Ende ist alles aus Ihrem Browser erreichbar.

      "myip": "192.168.88.102", "mymac": "34:8a:b1:4b:1a:c2",
      "INSTALL_RKE2_TYPE": "agent", "kcluster": "cluster1"
    }
  },
  "common": {
    "ISO_IMAGE": "SL-Micro.x86_64-6.1-Default-qcow-GM.qcow2",
    "VM_MEM": "24576", "VM_DSK": "80", "VM_CPU": "6",
    "mymask": "24", "mygw": "192.168.88.1", "mydns": "192.168.88.73"
  },
  "kclusters": {
    "cluster1": {
      "clu_type": "rke2", "clu_rel": "stable", "mydomain": "mydemo.lab",
      "addons": ["rancher", "longhorn"]
    }
  },
  "rancher": {
    "rancher_shorthn": "rancher", "rancher_rel": "rancher-prime",
    "rancher_repo_url": "https://charts.rancher.com/server-charts/prime",
    "rancher_helm_rel": "rancher", "rancher_helm_chart": "rancher-prime/rancher",
    "rancher_Version": "--version 2.13.3", "cert_manager_ver": "--version v1.14.4"
  }
}
  1. Erstellen:
setup_lab.py rancher-cluster.json

setup_lab.py führt vor allem anderen automatisch einen Preflight-Check der Datei durch. Fehlerhafte IPs, eine kcluster-Referenz, die es nicht gibt, ein fehlendes ISO_IMAGE und ähnliche Fehler werden erkannt und ausgegeben (✗ Preflight FAILED — N error(s)). Dabei wird nichts erstellt, statt mitten im Lauf zu scheitern. Eine saubere Datei gibt ✓ Preflight passed aus und geht direkt zum Aufbau über.

Dabei geschieht der Reihe nach Folgendes: Beide Knoten werden in DNS registriert. Beide VMs werden erstellt (das QCOW2-Image wird kopiert, Combustion-Dateien werden erzeugt, die VMs starten, und das Skript wartet auf SSH). RKE2 wird auf node101 als Server und auf node102 als Agent installiert. Danach werden rancher und longhorn auf dem Verwaltungsknoten des Clusters installiert (mgm_node, standardmäßig der erste Server-Knoten, hier also node101). Ein Cluster mit zwei Knoten und Rancher braucht meist 15 bis 25 Minuten. Der größte Teil davon ist das Bootstrapping von RKE2 und die Helm-Installation von Rancher.

  1. Prüfen, dass DNS auflöst (von Ihrem eigenen Desktop aus, sobald er auf die DNS der Automatisierungs-VM zeigt):
dig +short node101.mydemo.lab rancher.mydemo.lab

Beide Namen sollten 192.168.88.101 zurückgeben. Der Ingress-Hostname von Rancher ist der Wert von rancher_shorthn, also rancher`, unter der mydomain des Clusters.

  1. Anmelden. Öffnen Sie https://rancher.mydemo.lab (selbstsigniertes Zertifikat, Ihr Browser warnt einmal) und melden Sie sich mit rancher_initial_pwd aus /etc/lab_creation.cfg auf der Automatisierungs-VM an.

  2. Iterieren, ohne alles neu aufzubauen. Die Konfiguration eines Knotens geändert oder eine VM abgestürzt? Führen Sie mit --keep erneut aus. Jede VM, die bereits existiert, zur definierten IP/MAC passt und per SSH erreichbar ist, bleibt unverändert. Nur was tatsächlich fehlt oder defekt ist, wird (neu) erstellt:

setup_lab.py --keep rancher-cluster.json
  1. Abbauen, wenn Sie fertig sind:
destroy_lab.py rancher-cluster.json

Anleitung 3 — Automatisierungs-VM hinter NAT (Laptop mit einer NIC als Hypervisor)

Ziel: die Automatisierungs-VM auf einem Host bootstrappen, der keine freie NIC zum Bridgen hat. Stattdessen wird ein privates, von libvirt verwaltetes Netz genutzt, bei dem bestimmte Ports von der eigenen echten IP des Hosts weitergeleitet (DNAT) werden. Ende-zu-Ende getestet auf einer wegwerfbaren verschachtelten VM.

Das ändert nichts am Standard-Schnellstart, wenn Sie es nicht aktivieren. _network_mode ist standardmäßig "bridge", also genau wie bei jedem bestehenden Setup.

  1. In lab.cfg (Schritt 3 des Schnellstarts) setzen Sie:
_network_mode="nat"
_nat_network_name="labnat"          # default shown — a new libvirt virtual network, not your host's real LAN
_nat_network_cidr="192.168.150.0/24" # default shown
_nat_forwarded_ports="22:22/TCP 80:80/TCP 443:443/TCP"  # default shown — "<port on the HYPERVISOR's real IP>:<port on the AUTOMATION VM>/<protocol>"

Dadurch werden die Ports 22, 80 und 443 auf der eigenen, von außen erreichbaren echten IP des Hypervisors (<external>) an dieselben Ports auf der privaten NAT-Adresse der Automatisierungs-VM (<internal>) weitergeleitet. Die Automatisierungs-VM ist zu diesem Zeitpunkt das Einzige, das in diesem privaten Netz lauscht. „Intern“ bedeutet hier also immer „auf der Automatisierungs-VM“. (Schritt 5 unten verwendet dieselbe Syntax <external>:<internal>/<protocol>, um stattdessen an eine Lab-VM weiterzuleiten, sobald es eine gibt. Dort bedeutet „intern“ dann die private NAT-Adresse dieser VM, nicht die der Automatisierungs-VM.)

  1. Das Setup genau wie gewohnt ausführen:
./setup_kvm_node.py

Dies legt das libvirt-Netz labnat an (NAT, DHCP und Gateway übernimmt libvirt selbst, nach demselben Mechanismus wie das eingebaute Netz default von libvirt, nur unter dem eigenen Namen und CIDR dieses Projekts) statt einer Bridge. Danach wird die Automatisierungs-VM mit einer festen IP aus diesem privaten Bereich darauf erstellt. Anschließend werden die drei oben genannten Ports per DNAT von der echten IP des Hosts weitergeleitet.

  1. Prüfen, dass Netz und Weiterleitungsregeln existieren, auf dem Hypervisor:
virsh net-list                              # labnat: active
iptables -t nat -L LAB_PORTFWD -n -v         # DNAT rules to the automation VM's private IP
iptables -L LAB_PORTFWD_FWD -n -v            # matching FORWARD-chain ACCEPT rules
  1. Die Automatisierungs-VM von außerhalb des Hypervisors erreichen, über die echte IP des Hypervisors und nicht über die private Adresse 192.168.150.x der Automatisierungs-VM. Diese ist von außen nicht routbar:
ssh root@<hypervisor-real-ip>          # DNAT'd to the automation VM's SSH, port 22

Die Ports 80 und 443 werden standardmäßig ebenfalls weitergeleitet. Über Port 80 läuft der HTTP-Server für die Bereitstellungsdateien, über Port 443 die HTTPS-Listener der Web-UI, sobald Sie sie eingerichtet haben. Beide sind auf dieselbe Weise über die echte IP des Hypervisors erreichbar.

  1. Weiterleitung für eine Lab-VM hinzufügen, nicht nur für die Automatisierungs-VM selbst. Geben Sie diesem Knoten ein Feld forwarded_ports und aktivieren Sie den Dienst portforward` einmalig in common.services:
{
  "nodes": {
    "app1.mydemo.lab": {
      "myip": "192.168.150.20",
      "forwarded_ports": ["8080:80/TCP", "8443:443/TCP"]
    }
  },
  "common": { "services": ["portforward"], "...": "…rest of common as usual" }
}

setup_lab.py bzw. setup_vm.py leiten diese beiden Ports auf dieselbe Weise von der echten IP des Hypervisors weiter. Das geschieht beim ersten Mal, dass ein Knoten im Lab forwarded_ports angibt.

Die VMs eines Labs verwenden standardmäßig libvirt (die oben genannten KVM-Hypervisoren). Mehrere Cloud-Konten, genau wie KVM_HOSTS mehrere Hypervisoren ermöglicht: Legen Sie jedes Cloud-Konto in einer eigenen Datei unter /etc/lab_creation/credentials/ ab (der Pfad ist über CREDENTIALS_PATH in lab_creation.cfg konfigurierbar), als <name>.yaml (oder .json/.cfg; die Dateiendung bestimmt den Parser). Nur .yaml/.json unterstützen die verschlüsselte Form unten, weil das flache Format KEY=value einer .cfg-Datei keine verschlüsselten Werte aufnehmen kann. Jede Datei nennt cloudtype (aws/gcp/hetzner/…) und die üblichen Verbindungsschlüssel dieses Anbieters, also genau dieselben Schlüssel, die das Backend bereits aus lab_creation.cfg liest (AWS_REGION, AWS_PROFILE, AWS_SUBNET_ID, …). Ein Knoten (oder common) wählt dann eines über "cloud_account": "<name>" aus, genau wie "kvm_host": "<host>":

// /etc/lab_creation/credentials/aws-sandbox.yaml  (built with setup_credentials.py, below)
"nodes": {
  "jupiter.mydemo.lab": { "cloud_account": "aws-sandbox" },
  "saturn.mydemo.lab":  { "cloud_account": "aws-prod" }
}

Ist cloud_account gesetzt, ist dessen cloudtype das Backend. Das Feld backend wird damit optional. Wenn Sie beides setzen und sie sich widersprechen, meldet der Preflight einen Fehler. Die Schlüssel der Kontodatei werden über lab_creation.cfg gelegt, aber nur für diesen Knoten. Lassen Sie cloud_account überall weg, bleibt das bisherige Verhalten mit einem einzigen Konto unverändert. Jedes Konto ist ein eigenes, isoliertes Netz. Deshalb wird die Cloud-DNS-VM unten pro Konto angelegt (lab-dns-aws-sandbox, lab-dns-aws-prod, …). Das unbenannte Standardkonto behält den einfachen Namen lab-dns-<backend>.

Zugangsdatendateien sind standardmäßig verschlüsselt. Erstellen Sie eine mit:

setup_credentials.py                              # interactive: pick a provider, fill in its fields
setup_credentials.py --encrypt-existing myfile.yaml  # encrypt an already-written plaintext file's sensitive fields

Verschlüsselung (siehe libs/crypto_store.py): Die Passphrase läuft durch Argon2id, eine bewusst langsame, speicherintensive Schlüsselableitung. Diese ist bei einer passphrasengeschützten Datei die eigentliche Sicherheitsgrenze, nicht die Chiffre. Daraus wird ein 512-Bit-Hauptgeheimnis abgeleitet. HKDF-SHA512 leitet danach zwei unabhängige 256-Bit-Teilschlüssel ab, die durch ihr Label getrennt sind und nicht einfach halbiert werden. Die Daten werden mit AES-256-GCM und danach ChaCha20-Poly1305 hintereinandergeschaltet verschlüsselt. Das sind zwei strukturell verschiedene, unabhängig geschlüsselte AEAD-Chiffren, sodass auch ein vollständiger Bruch einer einzelnen Algorithmus-Familie allein nicht ausreicht. Jedes Werkzeug, das eine Zugangsdaten braucht (setup_lab.py, setup_vm.py, …), fragt die Passphrase einmal pro Lauf ab. Sie wird nur im Arbeitsspeicher des Prozesses zwischengespeichert und nirgends geschrieben. Den Zugriff übernimmt try_load_cloud_account() in libs/primary.py, die zentrale Funktion, über die alles läuft.

Eine Datei kann die Verschlüsselung mit einem obersten Eintrag unencrypted: true abschalten. Das ist nicht der Standard, und setup_credentials.py fragt vor dem Schreiben einer so angelegten Datei nach. --encrypt-existing verschlüsselt nur die sensibel aussehenden Felder (Namen mit secret, password oder token) direkt in der Datei. Dabei bleiben z. B. AWS_REGION/AWS_PROFILE lesbar. Die Eingabedatei wird nie überschrieben. Stattdessen wird <name>.encrypted.yaml daneben geschrieben, damit Sie sie prüfen und dann an den richtigen Ort verschieben können. Dafür braucht die Automatisierungs-VM das Python-Paket cryptography (python311-cryptography, oder pip install cryptography, Version ≥ 41 für Argon2id). Es wird erst geladen, wenn tatsächlich eine verschlüsselte Datei angefasst wird. Ein Lab, das nie cloud_account setzt, braucht deshalb keine neue Abhängigkeit.

Zugangsdaten für externe Dienste (SCC, SUSE Application Collection, Hermes, …). Derselbe Speicher unter /etc/lab_creation/credentials/, dieselbe Verschlüsselung und dasselbe Werkzeug setup_credentials.py decken auch Zugangsdaten für externe Dienste ab, die keine Cloud-Anbieter sind. Eine Datei wird über credential_kind (z. B. scc, appcollection, hermes) statt cloudtype gekennzeichnet. So teilen sich beide Konzepte Verzeichnis und Format, ohne sich zu überschneiden. Jedes Add-on, das eine Zugangsdaten für externe Dienste braucht, dokumentiert seinen eigenen optionalen Schlüssel <field>_account (z. B. smlm_scc_account, suse_ai_registry_account, hermes_account), um eine Datei ausdrücklich zu benennen. Ohne Angabe wird eine einzige passende Datei mit credential_kind automatisch gefunden, genau wie bei cloud_account. Klartext in der Lab-JSON bleibt in jedem Fall vollständig gültig. Dieser Speicher ist eine optionale Alternative für die Zugangsdaten, nie eine Pflicht. Die Klartextfelder jedes Add-ons (smlm_scc_user, suse_ai_registry_user, hermes_llm_api_key, …) funktionieren unverändert weiter, wenn Sie den Zugangsdatenspeicher gar nicht nutzen.

Cloud-DNS-VM: Sobald ein Lab-Knoten zum ersten Mal ein bestimmtes Cloud-Backend nutzt, richtet setup_vm.py außerdem eine kleine, günstige DNS-VM im selben Cloud-Netz ein (oder verwendet eine bereits vorhandene). Sie heißt lab-dns-<backend>, z. B. lab-dns-aws, und betreibt BIND. Das ist nötig, weil Cloud-Knoten im Allgemeinen den BIND-Server der Automatisierungs-VM unter automation.mydemo.lab gar nicht erreichen können. Er steht hinter NAT und dem Router des Home-Labs und ist nicht aus dem Internet erreichbar. Ein echter Cloud-Cluster mit mehreren Knoten braucht einen eigenen DNS-Server im selben Cloud-Netz, damit sich seine Knoten gegenseitig auflösen können. Jeder DNS-Eintrag eines Cloud-Knotens wird sowohl in dieser DNS-VM als auch in der zentralen Zone automation.mydemo.lab registriert. Bekannte Lücken: (1) Ein frisch erstellter Cloud-Knoten richtet seine eigene Namensauflösung noch nicht automatisch auf diese DNS-VM aus. Ein zweiter Cloud-Knoten im selben Lab kann den ersten deshalb noch nicht über den Hostnamen finden, ohne weitere Verdrahtung. (2) Die eigene Zone dieser DNS-VM über ihre öffentliche bzw. Elastic IP bei AWS, von einem externen Client aus (auch von automation.mydemo.lab selbst), liefert derzeit eine fehlerhafte NXDOMAIN-Antwort der Root-Zone statt der richtigen Antwort. Über die private IP oder über Loopback funktioniert es. Die Ursache des Pfads über die öffentliche IP ist noch nicht geklärt. Siehe die Docstring von ensure_cloud_dns_vm() in libs/backends.py und TODO.

Dimensionierung von Cloud-Instanzen: Jedes Cloud-Backend ordnet VM_CPU/VM_MEM dem kleinsten passenden Instanztyp, Servertyp, Plan bzw. Flavor des Anbieters aus einer kleinen eingebauten Tabelle zu (die Spalte „Notes“ unten zeigt jeweils, welche). Diese Tabelle war nie als Obergrenze gedacht. Es gibt zwei Wege, sie zu überschreiben, in dieser Rangfolge:

  1. cloud_instance_type (in common oder pro Knoten, der Knotenwert gewinnt): ein genauer Name für Instanztyp, Servertyp, Plan oder Flavor, der wörtlich statt einer automatischen Auswahl verwendet wird. Das funktioniert auf jedem Cloud-Backend gleich, auch bei OVHcloud (überspringt dessen eigenen Live-Aufruf der Flavor-Liste) und bei GCP (überspringt das Bauen eines benutzerdefinierten Typs e2-custom-<cpu>-<mem>. Geben Sie stattdessen einen echten vordefinierten Typ wie n2-standard-4 an).
  2. Ein Konfigurationsschlüssel *_INSTANCE_TYPES/*_SERVER_TYPES/*_PLANS (siehe die Zeile jedes Anbieters unten). Er ersetzt die eingebaute Tabelle vollständig. Die automatische Auswahl über VM_CPU/VM_MEM funktioniert weiter, aber gegen Ihre eigene Liste. Format: name:cores:mem_gb,name:cores:mem_gb,..., z. B. HETZNER_SERVER_TYPES=cx22:2:4,cx32:4:8,cx42:8:16. Die Tabelle wird vollständig ersetzt, nicht ergänzt. Wiederholen Sie eingebaute Einträge, die Sie weiterhin brauchen. GCP und OVHcloud haben keinen solchen Schlüssel. GCP baut direkt aus VM_CPU/VM_MEM einen echten benutzerdefinierten Maschinentyp, und es gibt keinen Katalog zum Überschreiben. OVHcloud fragt bereits beim Erstellen live die eigene Flavor-Liste ab (siehe die eigene Zeile).

Jede Prüfung läuft in ihrem eigenen, unabhängigen, wegwerfbaren podman-Container. Ein Absturz, ein Hänger oder ein Zustand, der übrig bleibt, kann keine andere Prüfung beeinflussen:

tests/run_tests.sh

Abgedeckt werden die Syntax von Bash und Python im gesamten Baum, die Konsistenz von Schema und Web-UI, Unit-Tests mit gemockter SSH-Verbindung für jede zentrale Bibliothek und jedes Orchestrierungsskript sowie Regressionstests für Fehler, die bei Live-Tests gefunden wurden. Eine neue Prüfung fügen Sie hinzu, indem Sie ein ausführbares Skript in tests/checks/ ablegen. Es wird automatisch erkannt und braucht keine weitere Verdrahtung.

Eingebunden in einen Pre-Commit-Hook (einmal pro Klon aktivieren, siehe Mitwirken). Er läuft bei jedem Commit automatisch und überspringt mit einer Warnung, wenn podman nicht installiert ist. Er blockiert den Commit nicht.

Einmalige Git-Einrichtung

Führen Sie nach dem Klonen des Repositorys aus:

git config core.hooksPath .githooks

Das aktiviert die Hooks in .githooks/, die: - vor jedem Commit die vollständige Testsuite ausführen - die Versionsstempel pro Skript verwalten (siehe unten)

So funktioniert die Versionierung

Dies übernehmen vollständig die Git-Hooks oben. Sie bearbeiten __LABVERSION__ nie von Hand.

Jedes Skript enthält den Platzhalter:

__LABVERSION__ = "__LABVERSION__"

Die Hooks in .githooks/ setzen diesen Platzhalter automatisch ein und stellen ihn wieder her:

Hook Auslöser Aktion
post-checkout git checkout / git switch Ersetzt __LABVERSION__ in jedem Skript durch den Hash des letzten Commits, der diese Datei geändert hat
post-merge git pull / git merge Wie oben
post-rewrite git rebase / git commit --amend Wie oben
pre-commit git commit Stellt __LABVERSION__ in allen gestagten Skripten wieder her, bevor der Commit geschrieben wird. So werden Hashes nie im Repository gespeichert

Das Ergebnis: Jedes Skript in Ihrem Arbeitsverzeichnis zeigt seine eigene Version über --version an. Das Repository selbst speichert immer den sauberen Platzhalter. Werden die Skripte über install_automation_node_scripts.sh installiert, wird dieselbe Ersetzung pro Datei zur Installationszeit mit git log -1 --format=%h durchgeführt.

Skripte auf der Automatisierungs-VM installieren

Aus dem Wurzelverzeichnis des Repositorys auf der Automatisierungs-VM (oder einer anderen Maschine mit geklontem Repository):

./install_automation_node_scripts.sh

Das sichert die bestehende Installation, sowohl als eigenes Tarball mit Zeitstempel als auch, getrennt davon, alles, was Ihr eigener Backup-Prozess aufbewahrt. Danach kopiert es jedes Skript, jede Bibliothek und jede Vorlage an ihren Systempfad und versieht jede installierte Datei mit ihrem Versions-Hash.

Abhängigkeiten

Zur Laufzeit (auf der Automatisierungs-VM): python3.11, jq, ssh, rsync, nc, helm, kubectl, named (BIND)

Die Einrichtung des Hypervisors braucht zusätzlich: virt-install, virsh, qemu-img, zypper, QCOW2-Quellimages unter /var/lib/libvirt/images/sources/

Zum Ausführen der Testsuite braucht es zusätzlich: podman

Eine Lab-Definition in YAML statt JSON (siehe Format der Lab-Definition) braucht zusätzlich: pyyaml (pip install pyyaml)
