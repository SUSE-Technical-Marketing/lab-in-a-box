lab-in-a-box crea laboratorios completos a partir de un único archivo JSON o YAML: las VMs, el DNS, los clústeres de Kubernetes y los complementos que describa. Las VMs pueden ejecutarse en sus propios hosts KVM, en Harvester o en cualquiera de ocho nubes públicas, y el mismo archivo funciona en todas ellas.

¿Por qué lab-in-a-box?

  • Un archivo, un comando. Describa VMs, clústeres de Kubernetes (RKE2 o K3s) y complementos de forma declarativa. setup_lab.py los crea en orden de dependencias, sin que tenga que ejecutar virt-install o Ansible a mano.
  • Laboratorio en casa o en la nube, la misma definición. Las VMs del laboratorio se ejecutan en hosts KVM propios, en Harvester HCI o en AWS, Google Cloud, Alibaba Cloud, Hetzner, Scaleway, UpCloud, OVHcloud o Exoscale. Un laboratorio puede abarcar varios hosts KVM y combinar nubes y ubicaciones mediante una red superpuesta WireGuard entre nubes.
  • 71 complementos listos para usar. Rancher, Longhorn, NeuVector, Harbor, Keycloak, Jenkins, Argo CD, SUSE Multi-Linux Manager/Uyuni, Nextcloud y más, además de aplicaciones de demostración intencionadamente vulnerables para formación en seguridad.
  • Una interfaz web que sigue al código. lab-builder genera cada formulario a partir del esquema del propio complemento, de modo que un campo nuevo en un script aparece en la interfaz sin cambios en el frontend.
  • Aprovisionamiento intercambiable. Ignition y Combustion para SLE Micro, cloud-init para openSUSE y Ubuntu, virt-customize para imágenes antiguas, o una instalación desatendida desde una ISO de instalación (AutoYaST, Kickstart, Preseed o AutoInstall).
  • Credenciales fuera del archivo del laboratorio. Las credenciales de nubes y servicios pueden guardarse en archivos cifrados por cuenta (derivación de claves Argon2id y después AES-256-GCM y ChaCha20-Poly1305 en cascada).
  • Pruebas en contenedores. Cada comprobación se ejecuta en un contenedor podman desechable, y un hook de pre-commit ejecuta las que correspondan.

Nodo(s) hipervisor

Una o más máquinas físicas que ejecutan KVM/QEMU. Cada una aloja VMs del laboratorio y guarda las imágenes QCOW2 de origen en /var/lib/libvirt/images/sources/. Sirve un NUC, una estación de trabajo o cualquier máquina x86_64 capaz de ejecutar KVM. Los laboratorios que necesitan más capacidad de la que ofrece una sola máquina pueden abarcar varios hosts KVM; consulte laboratorios en varios hosts más abajo.

VM de automatización

Una VM pequeña que se ejecuta en el hipervisor y actúa como plano de control de todo el laboratorio. Proporciona:

  • DNS: BIND (named) sirve el dominio del laboratorio y reenvía las consultas externas, de modo que todos los nombres del laboratorio se resuelven desde cualquier cliente que lo use
  • HTTP: sirve los archivos de aprovisionamiento (Ignition, Combustion, cloud-init) en /srv/www/htdocs/lab_creation/
  • Scripts: todos los comandos de gestión del laboratorio, instalados en /usr/local/bin/
  • Interfaz web (opcional): lab-builder, un diseñador de lab.json en el navegador

Todos los comandos del usuario se ejecutan en la VM de automatización. Esta se conecta por SSH a los hipervisores y a las VMs creadas. Después de la configuración inicial no hace falta acceder directamente al hipervisor.

Bajo el capó

Las herramientas de línea de comandos y todos los complementos están escritos en Python 3.11, en libs/ y scripts/, y se instalan en /usr/local/lib/lab_creation/. Se organizan en torno a un pequeño conjunto de módulos de biblioteca compartidos (lab_creation.py, backends.py, services.py, spacecmd_common.py, …) y no dependen unos de otros. La creación de VMs está detrás de una interfaz VMBackend intercambiable con diez implementaciones: libvirt, Harvester y ocho nubes públicas (consulte Backends de cómputo), de modo que los complementos y la orquestación no cambian entre ellas. Las implementaciones en bash a las que sustituyeron se conservan archivadas en legacy_bash/, incluido el install_ds389 original.

Cómo funciona

Flujo de despliegue

setup_lab.py ejecuta una secuencia fija de fases; las dos fases exclusivas de Kubernetes se omiten por completo en un laboratorio solo de VMs (sin sección kclusters):

    A -->|"no kclusters"| D["phase_create_vms"]
    C --> D["phase_create_vms"]
    D -->|"has kclusters"| F["phase_reboot_and_wait_kept_nodes"]
    D -->|"no kclusters"| H["phase_vm_addons"]
    F --> G["phase_install_k8s_and_addons"]
    G --> H["phase_vm_addons"]

Aprovisionamiento de VMs

Cada VM se crea así: 1. Se determina en qué host KVM va (el campo explícito kvm_host, o selección automática según la capacidad libre; consulte laboratorios en varios hosts) 2. Se copia y redimensiona una imagen QCOW2 de origen en ese host 3. Se generan los archivos de aprovisionamiento a partir de plantillas, según su config_method 4. Se registra una entrada DNS en BIND 5. Se ejecuta virt-install en el hipervisor por SSH 6. Se espera a que SSH esté disponible

El método de aprovisionamiento se controla con config_method en el JSON del laboratorio (por nodo o en common):

Valor Método Se usa para
(vacío, predeterminado) Ignition + Combustion SLE Micro
cloud-init ISO de cloud-init openSUSE Leap, Ubuntu
virt_customize Modifica el QCOW2 directamente en el hipervisor (virt-customize); el invitado no necesita soporte de Ignition ni cloud-init CentOS 7, Debian/RHEL antiguos o cualquier imagen sin Ignition/cloud-init
install_iso Instalación desatendida desde una ISO de instalación real (AutoYaST, Kickstart, Preseed o AutoInstall, según install_type) Distribuciones sin otra vía de aprovisionamiento

Dónde se crea la VM de un nodo lo decide una interfaz VMBackend intercambiable, que se resuelve una vez por nodo a partir de su campo backend (o de cloud_account, que implica el backend). Configuración de Kubernetes

Cuando las VMs están en marcha, setup_lab.py instala Kubernetes en cada nodo según la sección kclusters del JSON. Se admiten RKE2 y K3s. Cuando un clúster está listo, sus complementos se ejecutan en secuencia; los complementos de VM (asociados a un nodo y no a un clúster) se ejecutan después de aprovisionar ese nodo.

Laboratorios en varios hosts

Un laboratorio no está limitado a un hipervisor. Defina KVM_HOSTS (separados por espacios) en /etc/lab_creation.cfg en la VM de automatización para disponer de más de un hipervisor:

KVM_HOSTS="hv1.mydemo.lab hv2.mydemo.lab hv3.mydemo.lab"

Después, para cada nodo del JSON del laboratorio: - fíjelo explícitamente, con "kvm_host": "hv2.mydemo.lab" en la configuración de ese nodo, o - deje que se elija solo: omita kvm_host; el nodo va al host configurado que tenga en ese momento suficiente CPU/RAM/disco libre (comprobado en vivo por SSH).

Los nodos que no indican kvm_host y las instalaciones con un solo host configurado se comportan exactamente igual que antes de existir esta función: nada cambia para un laboratorio con un único hipervisor.

Red superpuesta WireGuard entre nubes

Por lo general, un nodo de laboratorio en la nube no puede alcanzar por red la red privada de otra cuenta de nube ni el laboratorio libvirt doméstico: cada una es su propia VPC o red aislada. common.overlay: true en el JSON del laboratorio enruta entre sí los SITIOS de este laboratorio, de sitio a sitio, por sus subredes reales, a través de una red superpuesta WireGuard en estrella (libs/overlay.py):

graph TD
    Hub["Overlay hub<br/>(gateway VM, stable public IP)"]
    HomeGW["Home automation VM<br/>(site gateway)"]
    GWB["Site gateway VM<br/>(account B)"]
    HomeNode["home lab node"]
    NodeA["node — account A (hub's own site)"]
    NodeB["node — account B"]
    HomeGW -- "wg0 spoke" --> Hub
    GWB -- "wg0 spoke" --> Hub
    HomeNode -. "local route" .-> HomeGW
    NodeB -. "local route" .-> GWB
    NodeA -. "on the hub's own subnet" .-> Hub

Solo la puerta de enlace de cada sitio se une a la red superpuesta, nunca un nodo individual del laboratorio. Un «sitio» es el laboratorio libvirt doméstico o una cuenta de nube; su puerta de enlace es la propia VM de automatización del sitio doméstico (mysource en /etc/lab_creation.cfg) o, en una cuenta de nube, una VM pequeña dedicada que se crea o reutiliza allí automáticamente (lab-overlay-gw-<backend>[-<account>], la misma convención de nombres que la VM de DNS en la nube). Todos los DEMÁS nodos solo reciben una ruta local persistente a la subred real de cada otro sitio, a través de la puerta de enlace de su propio sitio: ese es todo el mecanismo, sin pertenencia a WireGuard por nodo.

OVERLAY_HUB_ACCOUNT (obligatorio, en /etc/lab_creation.cfg) indica la cuenta de nube cuya VM de puerta de enlace es el concentrador, el único sitio con una IP pública estable al que se conectan todos los demás. OVERLAY_CIDR (predeterminado 10.99.0.0/16) solo se usa para las direcciones propias de las puertas de enlace en el túnel, no para enrutar el tráfico real; OVERLAY_WG_PORT (predeterminado 51820) es el puerto de escucha del concentrador. La entrada, la salida y la distribución de rutas ocurren automáticamente como parte de setup_vm.py; no hay que ejecutar nada más a mano.

Limitaciones conocidas: no se modifica el DNS (un nodo es accesible por su nombre real cuando ese nombre resuelve a una subred ya enrutada, no antes); los nodos ya aprovisionados de un sitio no se reenrutan cuando se une más tarde un sitio remoto nuevo, solo se actualizan cuando se aprovisiona cada nodo; AWS necesita desactivar la «comprobación de origen/destino» de la puerta de enlace del sitio para reenviar tráfico (se hace automáticamente), y todavía no existe equivalente para los otros 7 backends de nube.

Orden de carga de bibliotecas

Cada script carga la configuración en este orden:

  1. /etc/lab_creation.defaults: valores predeterminados del sistema, rutas, listas de paquetes
  2. /usr/local/lib/lab_creation/primary.py: validación de entradas, carga de la configuración
  3. /etc/lab_creation.cfg: ajustes específicos del nodo (REMOTE_HOST, ROOT_SSH_KEY, VIRT_SRV, KVM_HOSTS, etc.)
  4. /usr/local/lib/lab_creation/lab_creation.py: funciones de VM, DNS y orquestación
  5. /usr/local/lib/lab_creation/k8s.py: funciones de clúster Kubernetes

Requisitos

  • Una máquina capaz de ejecutar KVM (con Intel VT-x o AMD-V activado)
  • Acceso a Internet (o un mirror local) para descargar paquetes e imágenes
  • Una imagen QCOW2 del sistema operativo elegido en /var/lib/libvirt/images/sources/ del hipervisor

El hipervisor no necesita Python instalado de antemano: el comando de configuración instala python311 en openSUSE Leap / SLES 15 y el python3 propio de la distribución (3.9 o posterior) en todas las demás.

Imágenes probadas: - SLE Micro: recomendada, se usa con Ignition+Combustion - openSUSE Leap Micro: compatible, se usa con cloud-init

Paso 1: instalar el sistema operativo del hipervisor

Instale uno de estos sistemas en su hardware; basta con una instalación mínima o de servidor, sin bridge ni paquetes adicionales previos:

Familia Versiones
openSUSE Leap, SLES 15 (SP6+), 16
Debian, Ubuntu Debian 12, 13; Ubuntu 22.04, 24.04
RHEL, Rocky Linux, AlmaLinux, CentOS Stream, Fedora 9, 10; Fedora actual

Otras versiones de estas familias reciben la lista de paquetes coincidente más reciente, con un aviso de que no se ha verificado para ellas. SLES necesita un código de registro (se solicita durante la configuración) salvo que el host ya esté registrado.

En hipervisores de la familia RHEL y Fedora la configuración del host se completa, pero todavía no se puede crear allí la VM de automatización: libguestfs en esos sistemas no puede leer el sistema de archivos btrfs de su imagen openSUSE Leap. Por ahora, cree el nodo de automatización en un host de otra familia.

cat /proc/partitions > /tmp/parta

Paso 2: ejecutar el comando de configuración

En el hipervisor, como root:

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash

Instala git y Python, descarga lab-in-a-box en /var/tmp/setup_demo_server/ y ejecuta setup_demo_server/setup_kvm_node.py, que toma los ajustes del laboratorio de sus opciones y de los valores de este host; con --interactive los pide uno a uno, con esos valores como predeterminados:

  • Red del laboratorio: bridge coloca las VMs del laboratorio en la LAN del host; nat usa en su lugar una red privada de libvirt (para un portátil o un host con una sola NIC)
  • Dominio DNS del laboratorio (predeterminado mydemo.lab), la dirección IP de la VM de automatización (se sugiere una dirección libre de la red del laboratorio) y su contraseña de root
  • En SLES, el código de registro

La red, la puerta de enlace, el servidor DNS, la zona horaria y la clave SSH (~/.ssh/id_ed25519.pub, que se crea si no existe) se toman del host. Las respuestas se escriben en setup_demo_server/lab.cfg; tras un resumen (y, con --interactive, una confirmación), la configuración:

  1. instala los paquetes del hipervisor para la distribución detectada (en hosts de la familia RHEL se activan EPEL y CRB);
  2. en modo bridge, convierte la NIC de la ruta predeterminada en un puerto de br0, conservando la dirección del host. Se admiten NetworkManager, netplan, wicked, systemd-networkd e ifupdown. Un temporizador restaura la configuración de red anterior salvo que la puerta de enlace siga respondiendo a través del bridge, de modo que un cambio fallido no puede dejar el host inaccesible;
  3. configura libvirt y crea la VM de automatización.

Cada ajuste puede darse como opción, por ejemplo en una ejecución desatendida desde cloud-init:

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh \
  | sudo bash -s -- --domain mydemo.lab --automation-ip 192.168.8.71 --root-password 'secret'

Sin --root-password (ni LAB_ROOT_PASSWORD), se genera una contraseña que se muestra al final, salvo que --interactive la pida. Ejecute python3 /var/tmp/setup_demo_server/setup_demo_server/setup_kvm_node.py --help para ver todas las opciones.

Paso 3: volver a ejecutar o cambiar la configuración

Al ejecutar el comando de nuevo se usa el lab.cfg existente tal cual; las opciones que corresponden a sus ajustes (por ejemplo --network-mode nat) los actualizan primero, y --reconfigure vuelve a preguntarlo todo. Para revisar o editar lab.cfg antes de cambiar nada, descargue solo el código:

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash -s -- --fetch-only

Para configurar otra máquina desde esta, indique su dirección; el código se copia allí por SSH y se aplican las mismas opciones:

python3 /var/tmp/setup_demo_server/setup_demo_server/setup_kvm_node.py <IP>

Ajustes principales de lab.cfg:

Ajuste Descripción
_network_mode, _bridge_name, _bridge_nic Red en modo bridge o NAT; el bridge al que se conectan las VMs del laboratorio y la NIC que pasa a ser su puerto
_mynet, _mygw, _mydns, _myip Red del laboratorio, puerta de enlace, DNS superior y dirección de la VM de automatización

Paso 4: configurar la VM de automatización

Conéctese por SSH a la VM de automatización e instale los scripts del laboratorio:

ssh <AUTOMATION_HOSTNAME>
./install_automation_node_scripts.sh

cp /etc/lab_creation.cfg.example /etc/lab_creation.cfg
vim /etc/lab_creation.cfg

Ajustes principales de lab_creation.cfg:

Ajuste Descripción
REMOTE_HOST Nombre de host o IP del hipervisor KVM (principal)
KVM_HOSTS (opcional) lista separada por espacios de hipervisores adicionales para un laboratorio en varios hosts
ROOT_SSH_KEY Contenido de la clave pública SSH que se inyecta en las VMs
VIRT_SRV URI de conexión de libvirt (p. ej. qemu+ssh://root@hypervisor/system)
NETWORK Red libvirt predeterminada para las VMs (p. ej. bridge=br0)

HTTP y HTTPS. La VM de automatización sirve sus archivos en el puerto 80 (HTTP) y en el 443 (HTTPS, con un certificado autofirmado en /etc/lab_creation/tls/). Los instaladores (AutoYaST, kickstart, preseed) y Helm los descargan por HTTPS y aceptan el certificado autofirmado. Establezca PROVISIONING_TLS_VERIFY=1 para verificarlo, o PROVISIONING_BASE_URL (p. ej. http://192.168.88.250) para usar otra dirección o volver a HTTP. El arranque iPXE de Harvester usa siempre HTTP: iPXE no acepta certificados autofirmados.

Paso 5: apuntar el DNS del cliente a la VM de automatización

Para que los nombres de host se resuelvan desde su escritorio:

# Linux (NetworkManager):
nmcli con mod <connection> ipv4.dns <AUTOMATION_IP>

# Or add to /etc/resolv.conf:
nameserver <AUTOMATION_IP>

Los laboratorios se definen en archivos JSON o YAML (se detecta automáticamente; consulte la nota más abajo). El formato actual admite varios clústeres de Kubernetes por laboratorio (kclusters); consulte examples/cluster.json.template para el formato antiguo de un solo clúster (cluster).

Campo Descripción

Sobrescritura de la configuración de un complemento por nodo: cada complemento tiene una sección de configuración compartida de nivel superior (p. ej. client_registration en el ejemplo de SMLM anterior) que usan todos los nodos que lo incluyen en addons. Cuando distintos nodos necesitan de verdad valores diferentes para el mismo complemento (el caso que lo motivó: un laboratorio que registra muchos sistemas operativos distintos en un único servidor Uyuni/SMLM compartido, donde cada nodo necesita su propia client_registration_activation_key), dé a la entrada addons[] de ese nodo una sobrescritura anidada en lugar de una cadena simple:

"nodes": {
  "mercury.mydemo.lab": {
    "addons": [
      { "client_registration": { "client_registration_activation_key": "1-sles15sp7" } }
    ]
  },
  "callisto.mydemo.lab": {
    "addons": [
      "mariadb",
      { "client_registration": { "client_registration_activation_key": "1-debian13" } }
    ]
  }
}

Una entrada "mariadb" de cadena simple se comporta exactamente como antes (solo se aplica la sección compartida mariadb). La forma {"client_registration": {...}} sobrescribe solo esos campos, solo para ese nodo; todo lo que la sobrescritura no menciona (servidor, usuario administrador, …) sigue viniendo de la sección compartida client_registration. Funciona igual para cualquier complemento, no solo para client_registration; cada install_<addon>.py lo admite leyendo su configuración con k8s.addon_node_config(definition, "<addon>", vm_name) en lugar de definition.get("<addon>", {}) directamente; consulte addon_entry_name()/addon_entry_overrides() en libs/apps.py, el análisis compartido por el que pasa todo consumidor de una lista addons[].

Campo Descripción

Todo script de complemento acepta también --schema (alias de --input-definition), que muestra sus propias claves de configuración en JSON o YAML legible por máquina: el mismo esquema que lee la interfaz web para construir sus formularios:

install_longhorn --schema
setup_lab.py --input-definition yaml   # base topology schema (common/nodes/kclusters)

Versiones de esquema y migración

Cada esquema tiene una versión, MAJOR.MINOR: la definición del laboratorio, la sección de cada add-on y cada archivo de configuración (lab_creation.cfg, lab_creation.defaults, lab.cfg, el JSON de harvester-cluster y los archivos de credenciales). Un MAJOR nuevo significa que un archivo escrito para la versión anterior puede no funcionar o hacer otra cosa. schemas/compatibility.json enumera cada versión y lo que cambió.

Una definición de laboratorio registra las versiones para las que se escribió en su objeto schema_versions de nivel superior; la interfaz web lo escribe. Una definición que no registra ninguna cuenta como versión 1.0 de cada esquema.

"schema_versions": {"lab": "1.0", "addon:rancher": "2.0", "addon:longhorn": "1.0"}

setup_lab.py y setup_vm.py se detienen cuando una definición de laboratorio aún necesita una migración, y enumeran los cambios. migrate_config.py los aplica:

migrate_config.py --check lab.json   # list the changes lab.json needs; exit 1 when there are any
migrate_config.py lab.json           # write the migrated copy to lab.json.system_modified.json

El archivo original nunca se modifica. migrate_config.py también migra lab_creation.cfg, lab_creation.defaults, lab.cfg, los archivos JSON de harvester-cluster y los archivos de credenciales; estos registran su versión en una línea # Schema version: o en una clave schema_version.

Desplegar una imagen antigua (CentOS 7)

CentOS 7 (y otras imágenes .qcow2 igual de antiguas) no incluye ni Ignition/Combustion ni cloud-init, así que config_method debe ser virt_customize (consulte Aprovisionamiento de VMs): edita directamente el sistema de archivos del qcow2 en lugar de depender de un agente dentro del invitado. Para una imagen tan antigua importan dos sobrescrituras más:

  • VM_BOOT: "bios": el GRUB de CentOS 7 espera BIOS heredada, no el UEFI predeterminado de este proyecto.
  • VM_MACHINE: "pc": funciona con una imagen GenericCloud de CentOS 7 de 2015 (kernel 3.10.0-229). Arrancada con el tipo de máquina predeterminado de virt-install (actualmente q35), se queda colgada en una shell de emergencia de dracut (Not all disks have been found): su disco raíz virtio-blk no aparece a tiempo con la topología PCIe de Q35. El mismo disco arranca sin problemas con el chipset i440fx heredado ("pc"). Es una incompatibilidad entre chipset y kernel antiguo, no algo propio de este proyecto: la misma sobrescritura sirve para cualquier invitado suficientemente antiguo.
{
  "nodes": {
    "legacy1.mydemo.lab": {
      "myip": "192.168.88.120",
      "config_method": "virt_customize",
      "ISO_IMAGE": "CentOS-7-x86_64-GenericCloud-20150628_01.qcow2",
      "VM_BOOT": "bios",
      "VM_MACHINE": "pc"
    }
  },
  "common": { "VM_MEM": "2048", "VM_DSK": "30", "VM_CPU": "1", "VM_ROOT_PASS": "12345678" }
}

setup_lab.py legacy.json

VM_ROOT_PASS (en common o por nodo) define la contraseña de root que virt_customize graba directamente en la imagen; omítala para reutilizar ROOT_PWD_HASH de lab_creation.cfg, la misma alternativa que usan cloud-init e Ignition.

Guía 1: su primer clúster, RKE2 + Rancher + Longhorn

      "INSTALL_RKE2_TYPE": "server", "kcluster": "cluster1"

    }
  },
  "common": {
    "ISO_IMAGE": "SL-Micro.x86_64-6.1-Default-qcow-GM.qcow2",
    "VM_MEM": "24576", "VM_DSK": "80", "VM_CPU": "6",
    "mymask": "24", "mygw": "192.168.88.1", "mydns": "192.168.88.73"
  },
  "kclusters": {
    "cluster1": {

      "addons": ["rancher", "longhorn"]
    }

  "rancher": {
    "rancher_shorthn": "rancher", "rancher_rel": "rancher-prime",

    "rancher_helm_rel": "rancher", "rancher_helm_chart": "rancher-prime/rancher",
    "rancher_Version": "--version 2.13.3", "cert_manager_ver": "--version v1.14.4"

  1. Créelo:
setup_lab.py rancher-cluster.json

setup_lab.py comprueba el archivo automáticamente antes de hacer nada más: IPs incorrectas, una referencia a un kcluster inexistente, un ISO_IMAGE que falta y errores similares se detectan y se muestran (✗ Preflight FAILED — N error(s)) sin crear nada, en lugar de fallar a mitad de camino. Un archivo correcto muestra ✓ Preflight passed y pasa directamente a la creación.

Por orden: registra ambos nodos en el DNS → crea ambas VMs (copia la imagen QCOW2, genera los archivos de Combustion, las arranca y espera a SSH) → instala RKE2 en node101 como servidor y después en node102 como agente → instala rancher y longhorn en el nodo de gestión del clúster (mgm_node, por defecto el primer nodo servidor, aquí node101). Un clúster de 2 nodos con Rancher suele tardar entre 15 y 25 minutos; la mayor parte es el arranque de RKE2 y la instalación de Rancher con Helm.

dig +short node101.mydemo.lab rancher.mydemo.lab

Ambos deben devolver 192.168.88.101 (el nombre de host del ingress de Rancher es el valor de rancher_shorthn, rancher, bajo el mydomain del clúster).

  1. Inicie sesión. Abra https://rancher.mydemo.lab (certificado autofirmado: el navegador avisará una vez) e inicie sesión con rancher_initial_pwd de /etc/lab_creation.cfg en la VM de automatización.

  2. Itere sin reconstruirlo todo. ¿Ha cambiado la configuración de un nodo o se ha caído una VM? Vuelva a ejecutar con --keep: toda VM que ya exista, coincida con su IP/MAC definida y sea accesible por SSH se deja como está; solo se (re)crea lo que realmente falta o está roto:

setup_lab.py --keep rancher-cluster.json
  1. Elimínelo cuando termine:
destroy_lab.py rancher-cluster.json

Guía 3: VM de automatización con NAT (un portátil con una sola NIC como hipervisor)

Objetivo: crear la VM de automatización en un host sin una NIC libre para el bridge, usando en su lugar una red privada gestionada por libvirt, con puertos concretos redirigidos (DNAT) desde la IP real del host. Probado en vivo de principio a fin en una VM anidada desechable.

Si no lo activa, no cambia nada del flujo del Inicio rápido predeterminado: _network_mode vale "bridge" por defecto, exactamente igual que en cualquier instalación existente.

  1. En lab.cfg (paso 3 del Inicio rápido), defina:
_network_mode="nat"
_nat_network_name="labnat"          # default shown — a new libvirt virtual network, not your host's real LAN
_nat_network_cidr="192.168.150.0/24" # default shown
_nat_forwarded_ports="22:22/TCP 80:80/TCP 443:443/TCP"  # default shown — "<port on the HYPERVISOR's real IP>:<port on the AUTOMATION VM>/<protocol>"

Esto redirige los puertos 22/80/443 de la IP real del hipervisor, accesible desde fuera (<external>) a los mismos puertos de la dirección NAT privada de la VM de automatización (<internal>); en este momento la VM de automatización es lo único que escucha en esta red privada, así que aquí «interno» siempre significa «en la VM de automatización». (El paso 5 reutiliza exactamente la misma sintaxis <external>:<internal>/<protocol> para redirigir a una VM del laboratorio cuando exista; allí «interno» pasa a ser la dirección NAT privada de esa VM, no la de la VM de automatización).

  1. Ejecute la configuración como siempre:
./setup_kvm_node.py

Esto define la red libvirt labnat (con NAT; libvirt gestiona el DHCP y la puerta de enlace, con el mismo mecanismo que la red default integrada de libvirt, pero con el nombre y el CIDR de este proyecto) en lugar de un bridge, crea en ella la VM de automatización con una IP estática dentro de ese rango privado y redirige por DNAT los tres puertos anteriores desde la IP real del host.

  1. Compruebe que existen la red y las reglas de redirección, en el hipervisor:
virsh net-list                              # labnat: active
iptables -t nat -L LAB_PORTFWD -n -v         # DNAT rules to the automation VM's private IP
iptables -L LAB_PORTFWD_FWD -n -v            # matching FORWARD-chain ACCEPT rules
  1. Acceda a la VM de automatización desde fuera del hipervisor, usando la IP real del hipervisor, no la dirección privada 192.168.150.x de la VM de automatización, que no es enrutable desde ningún otro sitio:
ssh root@<hypervisor-real-ip>          # DNAT'd to the automation VM's SSH, port 22

Los puertos 80 y 443 también se redirigen por defecto (el servidor HTTP de archivos de aprovisionamiento y, cuando configure la interfaz web, su escucha HTTPS), y se accede a ellos igual, a través de la IP real del hipervisor.

  1. Añada redirección para una VM del laboratorio, no solo para la VM de automatización: dé a ese nodo un campo forwarded_ports y active una vez el servicio portforward en common.services:
{
  "nodes": {
    "app1.mydemo.lab": {
      "myip": "192.168.150.20",
      "forwarded_ports": ["8080:80/TCP", "8443:443/TCP"]
    }
  },
  "common": { "services": ["portforward"], "...": "…rest of common as usual" }
}

setup_lab.py/setup_vm.py redirigen por DNAT esos dos puertos desde la IP real del hipervisor de la misma forma, la primera vez que algún nodo del laboratorio declara forwarded_ports.

Para añadir un complemento nuevo: cree un ejecutable scripts/install_<name> en cualquier lenguaje, con o sin extensión de archivo (install_<name>.py, install_<name>.sh, un binario compilado), añada plantillas en templates/addons/<name>/ si las necesita y haga referencia a "<name>" en la lista addons de su JSON. install_automation_node_scripts.sh lo instala como /usr/local/bin/install_<name>, y setup_lab.py y la interfaz web lo usan solo a través de su interfaz de línea de comandos:

  • install_<name> --schema json muestra su esquema en JSON, con un objeto capabilities (targets, layers, requires_kubernetes, aux_services); --schema yaml muestra lo mismo en YAML
  • install_<name> --capabilities muestra esas mismas capacidades en JSON
  • install_<name> --validate <lab.json> termina con un código distinto de cero, mostrando líneas [ERROR], cuando su configuración no es válida
  • install_<name> --version y --help
  • install_<name> <lab.json> lo instala en la VM indicada en $_vm_name (y en el clúster de $clu_name si es un complemento de clúster)

Un complemento en Python obtiene todo esto de addon_common.handle_common_args() y de un diccionario PLUGIN a nivel de módulo; siga el modelo de uno existente (cargue la sección JSON correspondiente con load_definition() y haga el trabajo por SSH).

Las VMs de un laboratorio usan por defecto libvirt (los hipervisores KVM anteriores). Defina common.backend (o un backend por nodo, que tiene prioridad) para usar otro; consulte el enum del campo backend para la lista completa actual. Gráficos de consola con libvirt: las VMs del laboratorio reciben una pantalla SPICE (--graphics spice,listen=0.0.0.0) salvo que el QEMU del hipervisor no admita SPICE (SLES 16 es un caso), en cuyo caso reciben VNC. lab-in-a-box lo lee de virsh domcapabilities una vez por ejecución; si la consulta falla, usa SPICE.

Varias cuentas de nube, igual que KVM_HOSTS le da varios hipervisores: ponga cada cuenta de nube en su propio archivo bajo /etc/lab_creation/credentials/ (ruta configurable con CREDENTIALS_PATH en lab_creation.cfg), como <name>.yaml (o .json/.cfg: la extensión elige el analizador; solo .yaml/.json admiten la forma cifrada descrita más abajo, porque el formato plano KEY=value de un .cfg no puede contenerla). Cada archivo declara cloudtype (aws/gcp/hetzner/…) y las claves de conexión habituales de ese proveedor, exactamente las mismas que el backend ya lee de lab_creation.cfg (AWS_REGION, AWS_PROFILE, AWS_SUBNET_ID, …). Un nodo (o common) elige una con "cloud_account": "<name>", igual que "kvm_host": "<host>":

// /etc/lab_creation/credentials/aws-sandbox.yaml  (built with setup_credentials.py, below)
"nodes": {
  "jupiter.mydemo.lab": { "cloud_account": "aws-sandbox" },
  "saturn.mydemo.lab":  { "cloud_account": "aws-prod" }
}

Cuando se define cloud_account, su cloudtype es el backend (así que el campo backend pasa a ser opcional; si define ambos y no coinciden, la comprobación previa da error), y las claves del archivo de la cuenta se superponen a lab_creation.cfg solo para ese nodo. Omita cloud_account en todas partes para mantener el comportamiento actual de una sola cuenta, sin cambios. Cada cuenta es una red aislada, así que la VM de DNS en la nube descrita más abajo pasa a ser por cuenta (lab-dns-aws-sandbox, lab-dns-aws-prod, …); la cuenta predeterminada sin nombre conserva el nombre simple lab-dns-<backend>.

Los archivos de credenciales se cifran en reposo por defecto. Cree uno con:

setup_credentials.py                              # interactive: pick a provider, fill in its fields
setup_credentials.py --encrypt-existing myfile.yaml  # encrypt an already-written plaintext file's sensitive fields

Cifrado (consulte libs/crypto_store.py): la frase de contraseña pasa por Argon2id (una KDF deliberadamente lenta y exigente en memoria; esta, y no el cifrado, es el verdadero límite de seguridad de un archivo cifrado con frase de contraseña) para derivar un secreto maestro de 512 bits; después HKDF-SHA512 deriva dos subclaves independientes de 256 bits (separadas por etiqueta, no simplemente partidas por la mitad); los datos se cifran con AES-256-GCM y después ChaCha20-Poly1305 en cascada, dos cifrados AEAD estructuralmente distintos y con claves independientes, de modo que romper por completo uno solo de los algoritmos no basta. Toda herramienta que necesite una credencial (setup_lab.py, setup_vm.py, …) pide la frase de contraseña una vez por ejecución (solo se guarda en la memoria del proceso, nunca se escribe en ningún sitio) mediante try_load_cloud_account() de libs/primary.py, la única función por la que pasa todo.

Un archivo puede renunciar al cifrado con unencrypted: true en el nivel superior (no es lo predeterminado: setup_credentials.py pregunta antes de escribir uno así). --encrypt-existing cifra en el sitio solo los campos que parecen sensibles (nombres con forma de secreto, contraseña o token), deja legibles por ejemplo AWS_REGION/AWS_PROFILE y nunca sobrescribe su entrada: escribe <name>.encrypted.yaml al lado para que lo revise y lo coloque en su sitio. Requiere el paquete Python cryptography (python311-cryptography, o pip install cryptography, ≥41 para Argon2id) en la VM de automatización; se importa solo cuando se toca un archivo realmente cifrado, así que un laboratorio que nunca define cloud_account no necesita ninguna dependencia nueva.

Credenciales de servicios externos (SCC, SUSE Application Collection, Hermes, …). El mismo almacén /etc/lab_creation/credentials/, el mismo cifrado y la misma herramienta setup_credentials.py cubren también credenciales de servicios externos que no son de nube. Un archivo se marca con credential_kind (p. ej. scc, appcollection, hermes) en lugar de cloudtype, de modo que ambos conceptos comparten directorio y formato sin chocar nunca. Cada complemento que necesita una credencial de un servicio externo documenta su propio campo opcional <field>_account (p. ej. smlm_scc_account, suse_ai_registry_account, hermes_account) para indicarla explícitamente; si no se define, un único archivo con el credential_kind correspondiente se detecta automáticamente, igual que con cloud_account. Poner las credenciales en texto plano en el JSON del laboratorio sigue siendo totalmente válido: este almacén es una alternativa opcional, nunca un requisito; los campos en texto plano de cada complemento (smlm_scc_user, suse_ai_registry_user, hermes_llm_api_key, …) siguen funcionando igual si nunca usa el almacén de credenciales.

setup_credentials.py   # interactive — now asks "cloud provider or external service?" first

Un archivo de credenciales por tipo sirve para todos los complementos que necesitan ese tipo (p. ej. un único archivo scc cubre las credenciales SCC de cualquier complemento), sea cual sea el prefijo de los campos JSON de cada uno; consulte resolve_credential()/Validator.vreq_or_credential() en libs/addon_common.py y las funciones *_service_credential* de libs/primary.py para el mecanismo subyacente.

Backends de nube (Hetzner/AWS/GCP/Alibaba/Scaleway/UpCloud/OVHcloud/Exoscale) y myip: deje vacío el myip de un nodo con backend de nube en el JSON del laboratorio: la IP real solo se conoce cuando el proveedor la asigna al crear el nodo, no es algo que se pueda decidir de antemano como una IP estática de libvirt/Harvester. setup_vm.py toma la IP real del valor que devuelve create_vm() y la registra en el DNS después de que el nodo exista, no antes (un fallo real encontrado al probar AWSBackend en vivo, 2026-09-06; consulte TODO). mymac tampoco tiene sentido con un backend de nube: déjelo sin definir; se ignora en lugar de generarse o comprobarse.

VM de DNS en la nube: la primera vez que un nodo del laboratorio usa un backend de nube concreto, setup_vm.py también aprovisiona (o reutiliza, si ya existe) una VM pequeña y barata que sirve DNS dentro de esa misma red de nube, lab-dns-<backend>, p. ej. lab-dns-aws, con BIND. Existe porque, en general, los nodos de nube no pueden alcanzar el servidor BIND de automation.mydemo.lab (está detrás del NAT/router del laboratorio doméstico, no es accesible desde Internet); un clúster de nube real con varios nodos necesita su propio servidor DNS dentro de esa red para que sus nodos se resuelvan entre sí. La entrada DNS de cada nodo de nube se registra tanto en esta VM de DNS como en la zona central de automation.mydemo.lab. Limitaciones conocidas: (1) un nodo de nube recién creado todavía no usa automáticamente esta VM de DNS para su propia resolución, así que un segundo nodo de nube del mismo laboratorio aún no puede resolver al primero por nombre sin más configuración; (2) los nodos consultan esta VM de DNS a través de su IP privada; las consultas DNS a su IP pública desde fuera de la nube pueden ser interceptadas por las redes del camino, ya que algunos proveedores de Internet y routers responden ellos mismos a todo el tráfico DNS. Consulte el docstring de ensure_cloud_dns_vm() en libs/backends.py.

Tamaño de las instancias en la nube: cada backend de nube traduce VM_CPU/VM_MEM al tipo de instancia, tipo de servidor, plan o flavor más pequeño suficiente del proveedor a partir de una pequeña tabla integrada (la columna «Notas» de cada uno indica cuál); esa tabla nunca pretendió ser un límite. Hay dos formas de cambiarla, por orden de prioridad: 1. cloud_instance_type (en common o por nodo; gana el del nodo): el nombre exacto de un tipo de instancia, tipo de servidor, plan o flavor, que se usa tal cual sin elegir ninguno automáticamente. Funciona igual en todos los backends de nube, incluidos OVHcloud (omite su llamada en vivo a la API de flavors) y GCP (omite crear un tipo personalizado e2-custom-<cpu>-<mem>; indique en su lugar un tipo predefinido real como n2-standard-4). 2. Una clave de configuración *_INSTANCE_TYPES/*_SERVER_TYPES/*_PLANS (consulte la fila de cada proveedor más abajo): sustituye por completo la tabla integrada, de modo que la elección automática por VM_CPU/VM_MEM sigue funcionando, pero con su propia lista. Formato: name:cores:mem_gb,name:cores:mem_gb,..., p. ej. HETZNER_SERVER_TYPES=cx22:2:4,cx32:4:8,cx42:8:16. Reemplaza la tabla entera, no se combina con ella: repita las entradas integradas que quiera conservar. GCP y OVHcloud no tienen esta clave: GCP crea un tipo de máquina personalizado real directamente a partir de VM_CPU/VM_MEM (no hay catálogo que sustituir) y OVHcloud ya consulta en vivo su lista real de flavors al crear la instancia (consulte su fila).

Pruebas

Cada comprobación se ejecuta en su propio contenedor podman independiente y desechable: un fallo, un bloqueo o el estado residual de una no puede afectar a ninguna otra:

tests/run_tests.sh

Cubre la sintaxis de bash y Python en todo el árbol, la coherencia entre esquemas y la interfaz web, pruebas unitarias con SSH simulado para cada biblioteca principal y script de orquestación, y pruebas de regresión de fallos encontrados en pruebas en vivo. Para añadir una comprobación nueva, deje un script ejecutable en tests/checks/: se detecta automáticamente, sin configuración adicional.

Está conectado a un hook de pre-commit (actívelo una vez por clon, consulte Contribuir): se ejecuta automáticamente en cada commit y, si podman no está instalado, se omite con un aviso en lugar de bloquear el commit.

Cada uno de los Ejemplos anteriores tiene su prueba de despliegue y comprobación en hardware real en tests/examples/; necesitan un hipervisor KVM y una VM de automatización que funcionen, así que no forman parte de la ejecución automática de tests/run_tests.sh, pero están ahí y se pueden ejecutar a mano (tests/examples/run_example.sh <name>) antes de subir un cambio que pueda afectar a alguno de estos flujos documentados. Configuración inicial de git

Después de clonar el repositorio, ejecute:

git config core.hooksPath .githooks

Esto activa los hooks de .githooks/, que: - ejecutan el conjunto de pruebas completo antes de cada commit - gestionan el sellado de versión de cada script (consulte más abajo)

Cómo funciona el versionado

De esto se encargan por completo los hooks de git anteriores: nunca edita __LABVERSION__ a mano.

Cada script contiene el marcador:

__LABVERSION__ = "__LABVERSION__"

Los hooks de .githooks/ expanden y restauran este marcador automáticamente:

Hook Disparador Acción
post-checkout git checkout / git switch Sustituye __LABVERSION__ en cada script por el hash del último commit que modificó ese archivo
post-merge git pull / git merge Igual que el anterior
post-rewrite git rebase / git commit --amend Igual que el anterior
pre-commit git commit Restaura __LABVERSION__ en los scripts preparados antes de escribir el commit, de modo que los hashes nunca se guardan en el repositorio

Resultado: cada script de su árbol de trabajo muestra su propia versión con --version, y el repositorio siempre guarda el marcador limpio. Cuando los scripts se instalan con install_automation_node_scripts.sh, se aplica la misma sustitución de hash por archivo en el momento de la instalación con git log -1 --format=%h.

Instalar los scripts en la VM de automatización

Desde la raíz del repositorio en la VM de automatización (o en cualquier máquina con el repositorio clonado):

./install_automation_node_scripts.sh

Esto hace una copia de seguridad de la instalación existente (en su propio tarball con marca de tiempo y, por separado, en lo que conserve su propio proceso de copias), copia cada script, biblioteca y plantilla a su ruta del sistema y sella cada archivo instalado con su hash de versión.
