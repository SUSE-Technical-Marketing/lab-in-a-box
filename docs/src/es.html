lab-in-a-box crea laboratorios completos a partir de un único archivo JSON o YAML: las VMs, DNS, clústeres de Kubernetes y complementos que describe. Las VMs pueden ejecutarse en sus propios hosts KVM, en Harvester o en una de ocho nubes públicas, y el mismo archivo funciona en todas ellas.

¿Por qué lab-in-a-box?

  • Un archivo, un comando. Describa VMs, clústeres de Kubernetes (RKE2 o K3s) y complementos de forma declarativa. setup_lab.py los crea en orden de dependencias, sin necesidad de ejecutar virt-install o Ansible manualmente.
  • Lab en casa o en la nube, la misma definición. Las VMs del laboratorio se ejecutan en hosts KVM de su propiedad, en Harvester HCI o en AWS, Google Cloud, Alibaba Cloud, Hetzner, Scaleway, UpCloud, OVHcloud o Exoscale. Los laboratorios pueden extenderse por múltiples hosts KVM, y un solo laboratorio puede combinar nubes y ubicaciones mediante una superposición de WireGuard entre nubes.
  • 71 complementos preintegrados. Rancher, Longhorn, NeuVector, Harbor, Keycloak, Jenkins, Argo CD, SUSE Multi-Linux Manager/Uyuni, Nextcloud y más, además de aplicaciones de demostración intencionalmente vulnerables para entrenamiento en seguridad.
  • Una interfaz web que sigue al código. lab-builder representa cada formulario a partir del esquema propio del complemento. Un nuevo campo en un script aparece en la interfaz de usuario sin cambios en el frontend.
  • Provisión intercambiable. Ignition y Combustion para SLE Micro, cloud-init para openSUSE y Ubuntu, virt-customize para imágenes antiguas, o instalación guionizada desde ISO de instalación (AutoYaST, Kickstart, Preseed o AutoInstall).
  • Credenciales fuera del archivo de laboratorio. Las credenciales de nubes y servicios pueden residir en archivos cifrados por cuenta (derivación de claves con Argon2id, seguida de AES-256-GCM y ChaCha20-Poly1305 en cascada).
  • Pruebas containerizadas. Cada verificación se ejecuta en su propio contenedor podman desechable, y un gancho anterior a la confirmación ejecuta las verificaciones relevantes.

Arquitectura

El sistema se basa en una arquitectura de dos niveles:

    Operator["Cliente del operador"] -->|"SSH / DNS / HTTP"| AutoVM
    subgraph HV["Nodo hipervisor — KVM/QEMU"]
        AutoVM["VM de automatización<br/>DNS · HTTP · Scripts · Web UI"]
        AutoVM -->|"virt-install / virsh"| VM1["VM de laboratorio"]
        AutoVM -->|"virt-install / virsh"| VM2["VM de laboratorio"]
        AutoVM -->|"virt-install / virsh"| VM3["VM de laboratorio"]
    end

Nodos hipervisor

Una o más máquinas físicas (servidores dedicados) con KVM/QEMU. Cada una aloja VMs de laboratorio y mantiene imágenes QCOW2 de origen en /var/lib/libvirt/images/sources/. Un NUC, una estación de trabajo o cualquier máquina x86_64 que ejecute KVM es suficiente. Los laboratorios que requieren más capacidad de la que ofrece una máquina pueden extenderse a múltiples hosts KVM — véase Laboratorios de múltiples hosts más abajo.

VM de automatización

Una pequeña VM en el hipervisor que actúa como plano de control para todo el laboratorio. Proporciona:

  • DNS — BIND (named) sirve el dominio del laboratorio y reenvía consultas externas, por lo que todos los nombres de host del laboratorio se resuelven desde cualquier cliente que lo apunte
  • HTTP — sirve archivos de provisión (Ignition, Combustion, cloud-init) en /srv/www/htdocs/lab_creation/
  • Scripts — todos los comandos de administración del laboratorio, instalados en /usr/local/bin/
  • Interfaz web (opcional) — lab-builder, un diseñador basado en navegador para archivos lab.json

Todos los comandos del usuario se ejecutan en la VM de automatización. Se conecta por SSH con el hipervisor o los hipervisores, y con las VMs creadas. Después de la configuración inicial, no se requiere acceso directo al hipervisor.

Entre bastidores

Las herramientas de línea de comandos y cada complemento están en Python 3.11, residentes en libs/ y scripts/, e instalados en /usr/local/lib/lab_creation/. Se organizan alrededor de un pequeño conjunto de módulos de biblioteca compartida (lab_creation.py, backends.py, services.py, spacecmd_common.py, …) que no dependen unos de otros. La creación de VMs se realiza a través de una interfaz VMBackend intercambiable con diez implementaciones: libvirt, Harvester y ocho nubes públicas (véase Backends de cálculo). Los complementos y el código de orquestación no cambian entre ellos. Las implementaciones en Bash que reemplazaron se archivan bajo legacy_bash/ — incluido el install_ds389 original.

Cómo funciona

Canalización de despliegue

setup_lab.py ejecuta una secuencia fija de fases. Las dos fases específicas de Kubernetes se omiten completamente para un laboratorio sin la sección kclusters:

flowchart LR
    A["phase_services"] -->|"has kclusters"| C["phase_dns"]
    A -->|"no kclusters"| D["phase_create_vms"]
    C --> D["phase_create_vms"]
    D -->|"has kclusters"| F["phase_reboot_and_wait_kept_nodes"]
    D -->|"no kclusters"| H["phase_vm_addons"]
    F --> G["phase_install_k8s_and_addons"]
    G --> H["phase_vm_addons"]

Provisión de VM

Cada VM se crea así: 1. Determinar en qué host KVM reside (el campo explícito kvm_host o selección automática por capacidad libre — véase Laboratorios de múltiples hosts) 2. Copiar y expandir una imagen QCOW2 de origen en ese host 3. Generar archivos de provisión desde plantillas según su config_method 4. Registrar una entrada DNS en BIND 5. Ejecutar virt-install en el hipervisor por SSH 6. Esperar a que SSH esté disponible

El método de provisión se controla mediante config_method en el JSON del laboratorio (por nodo o en common):

Valor Método Se utiliza para
(vacío, predeterminado) Ignition + Combustion SLE Micro
cloud-init ISO de cloud-init openSUSE Leap, Ubuntu
virt_customize Modifica el QCOW2 directamente en el hipervisor (virt-customize) — no se requiere soporte Ignition/cloud-init en el huésped CentOS 7, RHEL/Debian antiguos o cualquier imagen sin Ignition/cloud-init
install_iso Instalación guionizada desde un ISO de instalación real (AutoYaST, Kickstart, Preseed o AutoInstall, seleccionado mediante install_type) Distribuciones sin otra ruta de provisión

Backends de cálculo

Dónde se crea la VM de un nodo lo decide una interfaz VMBackend intercambiable. Se resuelve una vez por nodo desde su campo backend (o desde cloud_account, que implica el backend). El predeterminado es libvirt. Cada complemento y script de orquestación habla con el backend resuelto de la misma manera, sin importar cuál sea:

hetzner Hetzner Cloud
scaleway Scaleway Instances

Configuración de Kubernetes

Una vez que las VMs están en funcionamiento, setup_lab.py instala Kubernetes en cada nodo de acuerdo con la sección kclusters del JSON. Se soportan tanto RKE2 como K3s. Una vez que un clúster está listo, sus complementos se ejecutan secuencialmente. Los complementos de VM (asignados a un nodo individual en lugar de un clúster) se ejecutan posteriormente, una vez que ese nodo está aprovisionado.

Laboratorios de múltiples hosts

Un laboratorio no se limita a un hipervisor. Establezca KVM_HOSTS (separado por espacios) en /etc/lab_creation.cfg en la VM de automatización para poner más de un hipervisor a disposición:

KVM_HOSTS="hv1.mydemo.lab hv2.mydemo.lab hv3.mydemo.lab"

Entonces, para cada nodo en el JSON del laboratorio, ya sea: - especificar explícitamente — "kvm_host": "hv2.mydemo.lab" en la configuración de ese nodo, o - dejar que elija automáticamente — omitir kvm_host; el nodo aterrizará en el host configurado que tenga suficiente CPU/RAM/disco libre en ese momento (verificado en vivo por SSH).

Los nodos sin kvm_host y los sistemas con un solo host configurado se comportan exactamente como antes — para un laboratorio con un hipervisor, nada cambia.

Superposición de WireGuard entre nubes

Generalmente, un nodo de laboratorio en la nube no puede llegar a través de la red a la red privada de otra cuenta de nube o al laboratorio libvirt en casa, porque cada una tiene su propia red VPC aislada. common.overlay: true en el JSON del laboratorio conecta los SITIOS de este laboratorio entre sí, sitio a sitio, sobre sus subredes reales, a través de una superposición de WireGuard de concentrador y radio (libs/overlay.py):

graph TD
    Hub["Concentrador de superposición<br/>(VM puerta de enlace, IP pública fija)"]
    HomeGW["VM de automatización doméstica<br/>(Puerta de enlace del sitio)"]
    GWB["VM puerta de enlace del sitio<br/>(Cuenta B)"]
    HomeNode["Nodo de laboratorio doméstico"]
    NodeA["Nodo — Cuenta A (sitio propio del concentrador)"]
    NodeB["Nodo — Cuenta B"]
    HomeGW -- "wg0 spoke" --> Hub
    GWB -- "wg0 spoke" --> Hub
    HomeNode -. "local route" .-> HomeGW
    NodeB -. "local route" .-> GWB
    NodeA -. "on the hub's own subnet" .-> Hub

Solo la puerta de enlace de cada sitio se une a la superposición en sí, nunca un nodo individual del laboratorio. Un "sitio" es el laboratorio libvirt doméstico o una cuenta de nube. Su puerta de enlace es la VM de automatización del sitio doméstico (mysource en /etc/lab_creation.cfg) o, para una cuenta de nube, una VM pequeña creada o reutilizada allí (lab-overlay-gw-<backend>[-<account>], siguiendo la misma convención de nomenclatura que la VM de DNS en la nube). Cualquier OTRO nodo simplemente obtiene una ruta local permanente y simple a la subred real de cada otro sitio, a través de la puerta de enlace de su propio sitio. El mecanismo no es más que eso, y los nodos individuales nunca son miembros de WireGuard.

OVERLAY_HUB_ACCOUNT (requerido, en /etc/lab_creation.cfg) nombra la cuenta de nube cuya VM puerta de enlace es el concentrador, es decir, el sitio con una IP pública fija con la que todos los demás se conectan. OVERLAY_CIDR (predeterminado 10.99.0.0/16) solo sirve para las direcciones de punto de presencia de las puertas de enlace en el túnel, no para el enrutamiento del tráfico real. OVERLAY_WG_PORT (predeterminado 51820) es el puerto de escucha del concentrador. La unión, la salida y la distribución de rutas ocurren automáticamente como parte de setup_vm.py. No necesita ejecutar nada manualmente.

Lagunas conocidas: No se realizan cambios en DNS. Un nodo es alcanzable por su nombre de host real una vez que ese nombre se resuelve en una subred que ahora está enrutada, no antes. Los nodos ya aprovisionados de un sitio no se reenrutan retroactivamente cuando posteriormente se une un nuevo sitio remoto. Solo se actualizan en el próximo aprovisionamiento de ese nodo individual. AWS requiere deshabilitar la "Verificación de origen/destino" en la puerta de enlace del sitio para reenviar tráfico (se hace automáticamente). Un equivalente para los otros 7 backends de nube aún no existe.

Orden de carga de bibliotecas

Cada script lee la configuración en este orden:

  1. /etc/lab_creation.defaults — valores predeterminados del sistema, rutas, listas de paquetes
  2. /usr/local/lib/lab_creation/primary.py — validación de entrada, carga de configuración
  3. /etc/lab_creation.cfg — configuración específica del nodo (REMOTE_HOST, ROOT_SSH_KEY, VIRT_SRV, KVM_HOSTS, etc.)
  4. /usr/local/lib/lab_creation/lab_creation.py — funciones de VM, DNS y orquestación
  5. /usr/local/lib/lab_creation/k8s.py — funciones del clúster de Kubernetes

Requisitos

  • Una máquina que pueda ejecutar KVM (Intel VT-x o AMD-V habilitado)
  • Acceso a Internet (o un espejo local) para descargar paquetes e imágenes
  • Una imagen QCOW2 para el SO elegido en /var/lib/libvirt/images/sources/ en el hipervisor

El hipervisor no necesita Python instalado de antemano: el comando de instalación instala python311 en openSUSE Leap / SLES 15 y el python3 propio de la distribución (3.9 o posterior) en las demás.

Imágenes probadas: - SLE Micro — recomendado, utilizado con Ignition+Combustion - openSUSE Leap Micro — soportado, utilizado con cloud-init

Paso 1 — Instalar el SO del hipervisor

Instale uno de estos sistemas en su hardware: openSUSE Leap / SLES 15 SP6+ & 16, Debian 12 & 13, Ubuntu 22.04 & 24.04, RHEL / Rocky Linux / AlmaLinux / CentOS Stream 9 & 10, Fedora. Basta con una instalación mínima o de servidor; no hace falta crear un puente ni instalar paquetes de antemano.

En hipervisores de la familia RHEL y Fedora la configuración del host se completa, pero la VM de automatización aún no puede crearse allí: libguestfs en esos sistemas no puede leer el sistema de archivos btrfs de su imagen openSUSE Leap. Por ahora, cree el nodo de automatización en un host de otra familia.

Crear un USB de arranque en Linux 
# Antes de insertar USB:
cat /proc/partitions > /tmp/partb4

# Inserte USB, luego:
cat /proc/partitions > /tmp/parta

# Encuentre el nuevo dispositivo:
diff /tmp/part*

El siguiente comando elimina todos los datos en el dispositivo de destino. Compruebe sdX contra la salida de diff anterior antes de ejecutarlo.

# Escribir la ISO (reemplazar sdX con su dispositivo):
dd if=SLE-15-SP6-Online-x86_64-GM-Media1.iso of=/dev/sdX bs=4k && sync

Paso 2 — Ejecutar el comando de instalación

En el hipervisor, como root:

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash

Instala git y Python, descarga lab-in-a-box en /var/tmp/setup_demo_server/ y pregunta la configuración del laboratorio, con los valores de este host como predeterminados: red en puente o NAT, dominio DNS del laboratorio, dirección IP y contraseña de root de la VM de automatización (y el código de registro en SLES). Después instala los paquetes del hipervisor, convierte la NIC de la ruta por defecto en puerto del puente br0 conservando la dirección del host (si la puerta de enlace deja de responder, se restaura automáticamente la configuración de red anterior) y crea la VM de automatización.

Cada respuesta también puede darse como opción, para ejecuciones desatendidas (por ejemplo desde cloud-init):

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh \
  | sudo bash -s -- --non-interactive --domain mydemo.lab --automation-ip 192.168.8.71 --root-password 'secret'

Paso 3 — Volver a ejecutar o cambiar la configuración

Una nueva ejecución usa el setup_demo_server/lab.cfg existente; --reconfigure vuelve a preguntarlo todo. Para editar lab.cfg antes de cambiar nada, descargue solo el código:

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash -s -- --fetch-only

setup_kvm_node.py <IP> configura otra máquina por SSH; setup_kvm_node.py --help muestra todas las opciones.

Paso 4 — Configurar la VM de automatización

Conéctese por SSH a la VM de automatización e instale los scripts del laboratorio:

ssh <AUTOMATION_HOSTNAME>
./install_automation_node_scripts.sh

cp /etc/lab_creation.cfg.example /etc/lab_creation.cfg
vim /etc/lab_creation.cfg

Configuraciones importantes en lab_creation.cfg:

Configuración Descripción
REMOTE_HOST Nombre de host o IP del hipervisor KVM (primario)
KVM_HOSTS (opcional) lista de hosts hipervisores adicionales separada por espacios para un laboratorio de múltiples hosts
ROOT_SSH_KEY Contenido de la clave SSH pública a insertar en las VMs
VIRT_SRV URI de conexión de libvirt (p. ej. qemu+ssh://root@hypervisor/system)
NETWORK Red libvirt predeterminada para VMs (p. ej. bridge=br0)

Paso 5 — Apuntar el DNS del cliente a la VM de automatización

Para que los nombres de host se resuelvan desde su escritorio:

# Linux (NetworkManager):
nmcli con mod <connection> ipv4.dns <AUTOMATION_IP>

# O agregar a /etc/resolv.conf:
nameserver <AUTOMATION_IP>

Paso 6 — Crear el primer laboratorio

setup_lab.py examples/cluster.json.template

Encontrará más puntos de partida a continuación en Ejemplos. Alternativamente, puede abrir la interfaz web en lugar de escribir JSON manualmente.

Interfaz web (lab-builder)

Un diseñador de archivos lab.json basado en navegador que evalúa las propias bibliotecas de Python del proyecto en tiempo de ejecución. No tiene conocimiento incorporado de ningún complemento. Seleccione un componente y se representará un formulario directamente desde su esquema. Agregue un campo a un script y la interfaz de usuario lo mostrará sin cambios en el frontend.

# La forma más rápida de probarlo — cero dependencias más allá de Python:
python3.11 webui/run-local.py            # → http://localhost:8677/

Para producción (Apache o un servicio independiente systemd/init, más HTTPS sobre un certificado autofirmado creado idempotentemente) véase README.webui.md. Allí se describen los tres modos de funcionamiento, la API HTTP y la solución de problemas.

Formato de definición de laboratorio

Los laboratorios se definen como archivos JSON o YAML (se reconocen automáticamente, véase la nota a continuación). El formato actual admite múltiples clústeres de Kubernetes por laboratorio (kclusters). El formato para un clúster individual (cluster) se encuentra en examples/cluster.json.template.

graph TD
    Lab["lab.json"] --> Nodes["nodes<br/>per-VM: myip, mymac, kcluster, addons..."]
    Lab --> Common["common<br/>shared defaults: ISO_IMAGE, VM_MEM, VM_DSK..."]
    Lab --> KClusters["kclusters<br/>clu_type, clu_rel, mydomain, addons"]
    Lab --> AddonSections["one section per add-on<br/>e.g. rancher, longhorn"]
    Nodes -. "kcluster" .-> KClusters
    KClusters -. "addons" .-> AddonSections
    Nodes -. "addons" .-> AddonSections

Un archivo .yaml/.yml también funciona. El formato se detecta por la extensión de archivo (o, si un archivo no es JSON válido, retrocede a YAML). Esto también se aplica a la verificación previa de vuelo de setup_lab.py, a install_<addon> --validate y a la ruta de carga de cada complemento. Las entradas YAML requieren pyyaml (pip install pyyaml) en la VM de automatización. Sin este paquete, obtendrá un mensaje de error claro diciéndole que lo instale, no un fallo silencioso que solo entienda JSON.
