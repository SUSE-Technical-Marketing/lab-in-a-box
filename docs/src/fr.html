lab-in-a-box construit des laboratoires complets à partir d'un seul fichier JSON ou YAML : les VM, le DNS, les clusters Kubernetes et les modules complémentaires que vous décrivez. Les VM peuvent tourner sur vos propres hôtes KVM, sur Harvester ou sur l'un des huit clouds publics, et le même fichier fonctionne partout.

Pourquoi lab-in-a-box ?

  • Un fichier, une commande. Décrivez de façon déclarative des VM, des clusters Kubernetes (RKE2 ou K3s) et des modules complémentaires. setup_lab.py les construit dans l'ordre des dépendances, sans que vous ayez à lancer virt-install ou Ansible à la main.
  • Labo à domicile ou dans le cloud, même définition. Les VM du laboratoire tournent sur vos propres hôtes KVM, sur Harvester HCI ou sur AWS, Google Cloud, Alibaba Cloud, Hetzner, Scaleway, UpCloud, OVHcloud ou Exoscale. Un laboratoire peut s'étendre sur plusieurs hôtes KVM et combiner clouds et sites grâce à un réseau superposé WireGuard multi-cloud.
  • 71 modules prêts à l'emploi. Rancher, Longhorn, NeuVector, Harbor, Keycloak, Jenkins, Argo CD, SUSE Multi-Linux Manager/Uyuni, Nextcloud et d'autres, ainsi que des applications de démonstration volontairement vulnérables pour la formation à la sécurité.
  • Une interface web qui suit le code. lab-builder génère chaque formulaire à partir du schéma du module lui-même : un nouveau champ dans un script apparaît dans l'interface sans modification du frontend.
  • Provisionnement interchangeable. Ignition et Combustion pour SLE Micro, cloud-init pour openSUSE et Ubuntu, virt-customize pour les images anciennes, ou une installation automatisée depuis une ISO d'installation (AutoYaST, Kickstart, Preseed ou AutoInstall).
  • Identifiants hors du fichier de laboratoire. Les identifiants des clouds et des services peuvent être stockés dans des fichiers chiffrés par compte (dérivation de clé Argon2id, puis AES-256-GCM et ChaCha20-Poly1305 en cascade).
  • Tests en conteneurs. Chaque vérification s'exécute dans un conteneur podman jetable, et un hook pre-commit lance celles qui sont concernées.

Nœud(s) hyperviseur

Une ou plusieurs machines physiques exécutant KVM/QEMU. Chacune héberge des VM du laboratoire et conserve les images QCOW2 sources dans /var/lib/libvirt/images/sources/. Un NUC, une station de travail ou toute machine x86_64 capable d'exécuter KVM convient. Les laboratoires qui ont besoin de plus de capacité qu'une seule machine peuvent s'étendre sur plusieurs hôtes KVM ; voir laboratoires multi-hôtes plus bas.

VM d'automatisation

Une petite VM qui tourne sur l'hyperviseur et sert de plan de contrôle à tout le laboratoire. Elle fournit :

  • DNS : BIND (named) sert le domaine du laboratoire et transfère les requêtes externes, si bien que tous les noms du laboratoire se résolvent depuis n'importe quel client qui l'utilise
  • HTTP : sert les fichiers de provisionnement (Ignition, Combustion, cloud-init) dans /srv/www/htdocs/lab_creation/
  • Scripts : toutes les commandes de gestion du laboratoire, installées dans /usr/local/bin/
  • Interface web (facultative) : lab-builder, un éditeur de lab.json dans le navigateur

Toutes les commandes de l'utilisateur s'exécutent sur la VM d'automatisation. Elle se connecte en SSH aux hyperviseurs et aux VM créées. Après la configuration initiale, aucun accès direct à l'hyperviseur n'est nécessaire.

Sous le capot

Les outils en ligne de commande et tous les modules sont écrits en Python 3.11, dans libs/ et scripts/, et installés dans /usr/local/lib/lab_creation/. Ils s'articulent autour d'un petit ensemble de modules de bibliothèque partagés (lab_creation.py, backends.py, services.py, spacecmd_common.py, …) plutôt que les uns autour des autres. La création des VM passe par une interface VMBackend interchangeable avec dix implémentations : libvirt, Harvester et huit clouds publics (voir Backends de calcul), si bien que les modules et l'orchestration ne changent pas de l'une à l'autre. Les implémentations bash qu'elles ont remplacées sont archivées dans legacy_bash/, y compris le install_ds389 d'origine.

Provisionnement des VM

Chaque VM est créée ainsi : 1. Détermination de l'hôte KVM qui l'accueille (le champ explicite kvm_host, ou une sélection automatique selon la capacité libre ; voir laboratoires multi-hôtes) 2. Copie et redimensionnement d'une image QCOW2 source sur cet hôte 3. Génération des fichiers de provisionnement à partir de modèles, selon son config_method 4. Enregistrement d'une entrée DNS dans BIND 5. Exécution de virt-install sur l'hyperviseur via SSH 6. Attente de la disponibilité de SSH

La méthode de provisionnement est choisie par config_method dans le JSON du laboratoire (par nœud ou dans common) :

Valeur Méthode Utilisée pour
(vide, par défaut) Ignition + Combustion SLE Micro
cloud-init ISO cloud-init openSUSE Leap, Ubuntu
virt_customize Modifie le QCOW2 directement sur l'hyperviseur (virt-customize) ; l'invité n'a pas besoin de prendre en charge Ignition ou cloud-init CentOS 7, anciennes Debian/RHEL ou toute image sans Ignition/cloud-init
install_iso Installation automatisée depuis une véritable ISO d'installation (AutoYaST, Kickstart, Preseed ou AutoInstall, selon install_type) Distributions sans autre méthode de provisionnement

Mise en place de Kubernetes

Une fois les VM démarrées, setup_lab.py installe Kubernetes sur chaque nœud selon la section kclusters du JSON. RKE2 et K3s sont tous deux pris en charge. Quand un cluster est prêt, ses modules s'exécutent les uns après les autres ; les modules de VM (rattachés à un nœud plutôt qu'à un cluster) s'exécutent une fois ce nœud provisionné.

Laboratoires multi-hôtes

Un laboratoire n'est pas limité à un seul hyperviseur. Définissez KVM_HOSTS (séparés par des espaces) dans /etc/lab_creation.cfg sur la VM d'automatisation pour rendre plusieurs hyperviseurs disponibles :

KVM_HOSTS="hv1.mydemo.lab hv2.mydemo.lab hv3.mydemo.lab"

Ensuite, pour chaque nœud du JSON du laboratoire : - fixez-le explicitement avec "kvm_host": "hv2.mydemo.lab" dans la configuration du nœud, ou - laissez la sélection automatique : omettez kvm_host ; le nœud est placé sur l'hôte configuré qui dispose à ce moment de suffisamment de CPU, de RAM et de disque libres (vérifié en direct via SSH).

Les nœuds sans kvm_host et les installations avec un seul hôte configuré se comportent exactement comme avant l'existence de cette fonction : rien ne change pour un laboratoire à un seul hyperviseur.

Réseau superposé WireGuard multi-cloud

En général, un nœud de laboratoire dans le cloud ne peut pas du tout joindre par le réseau le réseau privé d'un autre compte cloud ni le laboratoire libvirt domestique : chacun est son propre VPC ou réseau isolé. common.overlay: true dans le JSON du laboratoire relie entre eux les SITES de ce laboratoire, de site à site, par leurs sous-réseaux réels, via un réseau superposé WireGuard en étoile (libs/overlay.py) :

graph TD
    Hub["Overlay hub<br/>(gateway VM, stable public IP)"]
    HomeGW["Home automation VM<br/>(site gateway)"]
    GWB["Site gateway VM<br/>(account B)"]
    HomeNode["home lab node"]
    NodeA["node — account A (hub's own site)"]
    NodeB["node — account B"]
    HomeGW -- "wg0 spoke" --> Hub
    GWB -- "wg0 spoke" --> Hub
    HomeNode -. "local route" .-> HomeGW
    NodeB -. "local route" .-> GWB
    NodeA -. "on the hub's own subnet" .-> Hub

Seule la passerelle de chaque site rejoint le réseau superposé, jamais un nœud individuel du laboratoire. Un « site » est le laboratoire libvirt domestique ou un compte cloud ; sa passerelle est soit la VM d'automatisation du site domestique (mysource dans /etc/lab_creation.cfg), soit, pour un compte cloud, une petite VM dédiée créée ou réutilisée automatiquement sur place (lab-overlay-gw-<backend>[-<account>], même convention de nommage que la VM DNS cloud). Tous les AUTRES nœuds reçoivent simplement une route locale persistante vers le sous-réseau réel de chaque autre site, via la passerelle de leur propre site : c'est tout le mécanisme, sans appartenance WireGuard par nœud.

OVERLAY_HUB_ACCOUNT (obligatoire, dans /etc/lab_creation.cfg) désigne le compte cloud dont la VM passerelle est le concentrateur, le seul site doté d'une IP publique stable auquel tous les autres se connectent. OVERLAY_CIDR (par défaut 10.99.0.0/16) sert uniquement aux adresses des passerelles sur le tunnel, pas au routage du trafic réel ; OVERLAY_WG_PORT (par défaut 51820) est le port d'écoute du concentrateur. L'adhésion, le départ et la diffusion des routes se font automatiquement dans setup_vm.py ; il n'y a rien d'autre à lancer à la main.

Limites connues : aucune modification DNS n'est faite (un nœud est joignable par son vrai nom dès que ce nom se résout dans un sous-réseau désormais routé, pas avant) ; les nœuds déjà provisionnés d'un site ne sont pas re-routés quand un nouveau site distant arrive plus tard, seulement mis à jour lors du provisionnement de chaque nœud ; AWS exige de désactiver le « source/dest check » de la passerelle du site pour transférer le trafic (fait automatiquement), et il n'existe pas encore d'équivalent pour les 7 autres backends cloud.

Ordre de chargement des bibliothèques

Chaque script charge la configuration dans cet ordre :

  1. /etc/lab_creation.defaults : valeurs par défaut du système, chemins, listes de paquets
  2. /usr/local/lib/lab_creation/primary.py : validation des entrées, chargement de la configuration
  3. /etc/lab_creation.cfg : paramètres propres au nœud (REMOTE_HOST, ROOT_SSH_KEY, VIRT_SRV, KVM_HOSTS, etc.)
  4. /usr/local/lib/lab_creation/lab_creation.py : fonctions de VM, de DNS et d'orchestration
  5. /usr/local/lib/lab_creation/k8s.py : fonctions de cluster Kubernetes

Prérequis

  • Une machine capable d'exécuter KVM (Intel VT-x ou AMD-V activé)
  • Un accès à Internet (ou un miroir local) pour télécharger les paquets et les images
  • Une image QCOW2 du système choisi placée dans /var/lib/libvirt/images/sources/ sur l'hyperviseur

L'hyperviseur n'a pas besoin de Python au préalable : la commande d'installation installe python311 sur openSUSE Leap / SLES 15 et le python3 de la distribution (3.9 ou plus récent) partout ailleurs.

Images testées : - SLE Micro : recommandée, utilisée avec Ignition+Combustion - openSUSE Leap Micro : prise en charge, utilisée avec cloud-init

Étape 1 : installer le système de l'hyperviseur

Installez l'un de ces systèmes sur votre matériel ; une installation minimale ou serveur suffit, sans bridge ni paquet supplémentaire au préalable :

Famille Versions
openSUSE Leap, SLES 15 (SP6+), 16
Debian, Ubuntu Debian 12, 13 ; Ubuntu 22.04, 24.04
RHEL, Rocky Linux, AlmaLinux, CentOS Stream, Fedora 9, 10 ; Fedora actuelle

Les autres versions de ces familles reçoivent la liste de paquets correspondante la plus récente, avec un avertissement indiquant qu'elle n'a pas été vérifiée pour elles. SLES a besoin d'un code d'enregistrement (demandé pendant l'installation), sauf si l'hôte est déjà enregistré.

Sur les hyperviseurs de la famille RHEL et Fedora, la configuration de l'hôte se termine, mais la VM d'automatisation ne peut pas encore y être construite : libguestfs sur ces systèmes ne sait pas lire le système de fichiers btrfs de son image openSUSE Leap. Pour l'instant, créez le nœud d'automatisation sur un hôte d'une autre famille.

Écrire une clé USB amorçable depuis Linux 
# Before inserting USB:
cat /proc/partitions > /tmp/partb4

# Insert USB, then:
cat /proc/partitions > /tmp/parta

# Find the new device:
diff /tmp/part*

La commande suivante détruit toutes les données du périphérique cible. Vérifiez bien sdX par rapport à la sortie de diff ci-dessus avant de l'exécuter.

# Write the ISO (replace sdX with your device):
dd if=SLE-15-SP6-Online-x86_64-GM-Media1.iso of=/dev/sdX bs=4k && sync

Étape 2 : lancer la commande d'installation

Sur l'hyperviseur, en tant que root :

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash

Elle installe git et Python, récupère lab-in-a-box dans /var/tmp/setup_demo_server/ et lance setup_demo_server/setup_kvm_node.py, qui prend les paramètres du laboratoire dans ses options et dans les valeurs de cet hôte ; avec --interactive, il les demande un par un, avec ces valeurs par défaut :

  • Réseau du laboratoire : bridge place les VM du laboratoire sur le réseau local de l'hôte ; nat utilise à la place un réseau libvirt privé (pour un portable ou un hôte à une seule carte réseau)
  • Domaine DNS du laboratoire (par défaut mydemo.lab), l'adresse IP de la VM d'automatisation (une adresse libre du réseau du laboratoire est proposée) et son mot de passe root
  • Sur SLES, le code d'enregistrement

Le réseau, la passerelle, le serveur DNS, le fuseau horaire et la clé SSH (~/.ssh/id_ed25519.pub, créée si absente) sont repris de l'hôte. Les réponses sont écrites dans setup_demo_server/lab.cfg ; après un récapitulatif (et, avec --interactive, une confirmation), l'installation :

  1. installe les paquets d'hyperviseur pour la distribution détectée (EPEL et CRB sont activés sur les hôtes de la famille RHEL) ;
  2. en mode bridge, transforme la carte réseau portant la route par défaut en port de br0, en conservant l'adresse de l'hôte. NetworkManager, netplan, wicked, systemd-networkd et ifupdown sont pris en charge. Une minuterie restaure la configuration réseau précédente si la passerelle ne répond plus à travers le bridge, si bien qu'un changement raté ne peut pas rendre l'hôte injoignable ;
  3. configure libvirt et crée la VM d'automatisation.

Chaque paramètre peut être passé en option, par exemple pour une exécution sans surveillance depuis cloud-init :

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh \
  | sudo bash -s -- --domain mydemo.lab --automation-ip 192.168.8.71 --root-password 'secret'

Sans --root-password (ni LAB_ROOT_PASSWORD), un mot de passe est généré et affiché à la fin, sauf si --interactive le demande. Lancez python3 /var/tmp/setup_demo_server/setup_demo_server/setup_kvm_node.py --help pour voir toutes les options.

Étape 3 : relancer ou modifier l'installation

Relancer la commande utilise le lab.cfg existant tel quel ; les options correspondant à ses paramètres (par exemple --network-mode nat) les mettent d'abord à jour, et --reconfigure repose toutes les questions. Pour relire ou modifier lab.cfg avant tout changement, récupérez seulement le code :

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash -s -- --fetch-only

Pour installer une autre machine depuis celle-ci, indiquez son adresse ; le code y est copié via SSH et les mêmes options s'appliquent :

python3 /var/tmp/setup_demo_server/setup_demo_server/setup_kvm_node.py <IP>

Principaux paramètres de lab.cfg :

Paramètre Description
_network_mode, _bridge_name, _bridge_nic Réseau en bridge ou NAT ; le bridge auquel se rattachent les VM du laboratoire et la carte réseau qui devient son port
_mynet, _mygw, _mydns, _myip Réseau du laboratoire, passerelle, DNS amont et adresse de la VM d'automatisation
ROOT_PWD_HASH, ROOT_SSH_PUB_KEY Empreinte du mot de passe root de la VM d'automatisation et clé SSH autorisée à se connecter
AUTOMATION_HOSTNAME Nom d'hôte de la VM d'automatisation (par ex. automation.mydemo.lab)
_QCOW_IMAGE Nom du fichier de l'image QCOW2 source

Étape 4 : configurer la VM d'automatisation

Connectez-vous en SSH à la VM d'automatisation et installez les scripts du laboratoire :

ssh <AUTOMATION_HOSTNAME>
./install_automation_node_scripts.sh

cp /etc/lab_creation.cfg.example /etc/lab_creation.cfg
vim /etc/lab_creation.cfg

Principaux paramètres de lab_creation.cfg :

Paramètre Description
REMOTE_HOST Nom d'hôte ou IP de l'hyperviseur KVM (principal)
KVM_HOSTS (facultatif) liste, séparée par des espaces, d'hyperviseurs supplémentaires pour un laboratoire multi-hôtes
ROOT_SSH_KEY Contenu de la clé publique SSH injectée dans les VM
VIRT_SRV URI de connexion libvirt (par ex. qemu+ssh://root@hypervisor/system)
NETWORK Réseau libvirt par défaut des VM (par ex. bridge=br0)

HTTP et HTTPS. La VM d'automatisation sert ses fichiers sur le port 80 (HTTP) et sur le port 443 (HTTPS, certificat auto-signé dans /etc/lab_creation/tls/). Les installateurs (AutoYaST, kickstart, preseed) et Helm les téléchargent en HTTPS et acceptent le certificat auto-signé. Définissez PROVISIONING_TLS_VERIFY=1 pour le vérifier, ou PROVISIONING_BASE_URL (par ex. http://192.168.88.250) pour utiliser une autre adresse ou revenir à HTTP. Le démarrage iPXE de Harvester utilise toujours HTTP : iPXE n'accepte pas les certificats auto-signés.

Champs facultatifs au niveau du nœud :

Champ Description
addons Liste des modules à exécuter pour cette VM uniquement ; voir plus bas les surcharges de configuration par nœud
config_method Remplace la méthode de provisionnement (cloud-init, virt_customize, install_iso)
kvm_host Fixe cette VM sur un hyperviseur précis dans un laboratoire multi-hôtes
extra_dsk Disque(s) supplémentaire(s) à attacher : "/dev/sdb", ou "/dev/sdb,bus=scsi" pour changer le bus par défaut d'un disque
salt_states États Salt à appliquer (méthode cloud-init uniquement)

Surcharges de configuration de module par nœud : chaque module a une section de configuration partagée de premier niveau (par ex. client_registration dans l'exemple SMLM précédent), utilisée par tous les nœuds qui le citent dans addons. Quand différents nœuds ont réellement besoin de valeurs différentes pour ce même module (le cas d'origine : un laboratoire qui enregistre de nombreux systèmes différents auprès d'un serveur Uyuni/SMLM partagé, où chaque nœud a besoin de sa propre client_registration_activation_key), donnez à l'entrée addons[] de ce nœud une surcharge imbriquée au lieu d'une simple chaîne :

"nodes": {
  "mercury.mydemo.lab": {
    "addons": [
      { "client_registration": { "client_registration_activation_key": "1-sles15sp7" } }
    ]
  },
  "callisto.mydemo.lab": {
    "addons": [
      "mariadb",
      { "client_registration": { "client_registration_activation_key": "1-debian13" } }
    ]
  }
}

Une entrée simple "mariadb" se comporte exactement comme avant (seule la section partagée mariadb s'applique). La forme {"client_registration": {...}} remplace uniquement ces champs, pour ce nœud seulement ; tout ce que la surcharge ne mentionne pas (serveur, utilisateur administrateur, …) provient toujours de la section partagée client_registration. Cela fonctionne de la même façon pour n'importe quel module, pas seulement client_registration ; chaque install_<addon>.py l'active en lisant sa configuration via k8s.addon_node_config(definition, "<addon>", vm_name) au lieu de definition.get("<addon>", {}) directement ; voir addon_entry_name()/addon_entry_overrides() dans libs/apps.py, l'analyse commune par laquelle passe chaque utilisateur d'une liste addons[].

Champs facultatifs de kcluster :

Champ Description
mgm_node Nom d'hôte du nœud qui exécute les installateurs des modules du cluster ; par défaut, le premier nœud serveur

Chaque script de module accepte aussi --schema (alias de --input-definition), qui affiche ses propres clés de configuration en JSON ou YAML lisible par une machine : le même schéma que l'interface web lit pour construire ses formulaires :

install_longhorn --schema
setup_lab.py --input-definition yaml   # base topology schema (common/nodes/kclusters)

Versions de schéma et migration

Chaque schéma a une version, MAJOR.MINOR : la définition du lab, la section de chaque add-on et chaque fichier de configuration (lab_creation.cfg, lab_creation.defaults, lab.cfg, le JSON harvester-cluster et les fichiers d'identifiants). Un nouveau MAJOR signifie qu'un fichier écrit pour la version précédente peut ne pas fonctionner, ou faire autre chose. schemas/compatibility.json liste chaque version et ce qui a changé.

Une définition de lab enregistre les versions pour lesquelles elle a été écrite dans son objet schema_versions de premier niveau ; l'interface web l'écrit. Une définition qui n'en enregistre aucune compte comme version 1.0 de chaque schéma.

"schema_versions": {"lab": "1.0", "addon:rancher": "2.0", "addon:longhorn": "1.0"}

setup_lab.py et setup_vm.py s'arrêtent quand une définition de lab a encore besoin d'une migration, et listent les changements. migrate_config.py les applique :

migrate_config.py --check lab.json   # list the changes lab.json needs; exit 1 when there are any
migrate_config.py lab.json           # write the migrated copy to lab.json.system_modified.json

Le fichier original n'est jamais modifié. migrate_config.py migre aussi lab_creation.cfg, lab_creation.defaults, lab.cfg, les fichiers JSON harvester-cluster et les fichiers d'identifiants ; ceux-ci enregistrent leur version dans une ligne # Schema version: ou une clé schema_version.

Déployer une image ancienne (CentOS 7)

CentOS 7 (et les autres images .qcow2 aussi anciennes) n'intègre ni Ignition/Combustion ni cloud-init ; config_method doit donc être virt_customize (voir Provisionnement des VM), qui modifie directement le système de fichiers du qcow2 au lieu de s'appuyer sur un agent dans l'invité. Deux autres surcharges comptent pour une image aussi ancienne :

  • VM_BOOT: "bios" : le GRUB de CentOS 7 attend un BIOS classique, pas l'UEFI par défaut de ce projet.
  • VM_MACHINE: "pc" : fonctionne avec une image GenericCloud de CentOS 7 de 2015 (noyau 3.10.0-229). Démarrée avec le type de machine par défaut de virt-install (actuellement q35), elle reste bloquée dans un shell d'urgence dracut (Not all disks have been found) : son disque racine virtio-blk n'apparaît jamais à temps avec la topologie PCIe de Q35. Le même disque démarre sans problème avec l'ancien chipset i440fx ("pc"). C'est une incompatibilité entre chipset et noyau ancien, rien de propre à ce projet : la même surcharge s'applique à tout invité suffisamment ancien.
{
  "nodes": {
    "legacy1.mydemo.lab": {
      "myip": "192.168.88.120",
      "config_method": "virt_customize",
      "ISO_IMAGE": "CentOS-7-x86_64-GenericCloud-20150628_01.qcow2",
      "VM_BOOT": "bios",
      "VM_MACHINE": "pc"
    }
  },
  "common": { "VM_MEM": "2048", "VM_DSK": "30", "VM_CPU": "1", "VM_ROOT_PASS": "12345678" }
}

setup_lab.py legacy.json

VM_ROOT_PASS (dans common ou par nœud) définit le mot de passe root que virt_customize inscrit directement dans l'image ; omettez-le pour réutiliser ROOT_PWD_HASH de lab_creation.cfg, la même solution de repli que cloud-init et Ignition.

D'autres distributions (AlmaLinux, Debian, Rocky Linux, Alibaba Cloud Linux et une tentative documentée, encore infructueuse, avec Raspberry Pi OS) se trouvent dans EXAMPLES.md, à part pour que cette section ne grossisse pas sans fin.

  "common": {

setup_lab.py rancher-cluster.json

setup_lab.py vérifie automatiquement le fichier avant toute autre action : IP incorrectes, référence à un kcluster inexistant, ISO_IMAGE manquant et erreurs similaires sont détectés et affichés (✗ Preflight FAILED — N error(s)) sans rien créer, au lieu d'échouer en cours de route. Dans l'ordre : enregistre les deux nœuds dans le DNS → crée les deux VM (copie l'image QCOW2, génère les fichiers Combustion, les démarre, attend SSH) → installe RKE2 sur node101 en serveur, puis sur node102 en agent → installe rancher et longhorn sur le nœud de gestion du cluster (mgm_node, par défaut le premier nœud serveur, ici node101). dig +short node101.mydemo.lab rancher.mydemo.lab

Les deux doivent renvoyer 192.168.88.101 (le nom d'hôte de l'ingress de Rancher est la valeur de rancher_shorthn, rancher, sous le mydomain du cluster).

  1. Connectez-vous. Ouvrez https://rancher.mydemo.lab (certificat auto-signé : le navigateur avertira une fois) et connectez-vous avec rancher_initial_pwd de /etc/lab_creation.cfg sur la VM d'automatisation.

  2. Itérez sans tout reconstruire. Vous avez modifié la configuration d'un nœud, ou une VM a planté ? Relancez avec --keep : toute VM qui existe déjà, correspond à son IP/MAC définie et répond en SSH est laissée telle quelle ; seul ce qui manque ou est cassé est (re)créé :

setup_lab.py --keep rancher-cluster.json

destroy_lab.py rancher-cluster.json

Guide 3 : VM d'automatisation derrière un NAT (un portable à une carte réseau comme hyperviseur)

Objectif : amorcer la VM d'automatisation sur un hôte sans carte réseau libre pour un bridge, avec à la place un réseau privé géré par libvirt et certains ports redirigés (DNAT) depuis l'IP réelle de l'hôte. Testé en conditions réelles de bout en bout sur une VM imbriquée jetable.

Si vous ne l'activez pas, rien ne change dans le Démarrage rapide par défaut : _network_mode vaut "bridge" par défaut, exactement comme toute installation existante.

  1. Dans lab.cfg (étape 3 du Démarrage rapide), définissez :
_network_mode="nat"
_nat_network_name="labnat"          # default shown — a new libvirt virtual network, not your host's real LAN
_nat_network_cidr="192.168.150.0/24" # default shown
_nat_forwarded_ports="22:22/TCP 80:80/TCP 443:443/TCP"  # default shown — "<port on the HYPERVISOR's real IP>:<port on the AUTOMATION VM>/<protocol>"

Cela redirige les ports 22/80/443 de l'IP réelle de l'hyperviseur, joignable de l'extérieur (<external>) vers les mêmes ports de l'adresse NAT privée de la VM d'automatisation (<internal>) ; à ce stade, la VM d'automatisation est la seule à écouter sur ce réseau privé, donc « interne » signifie toujours ici « sur la VM d'automatisation ». (L'étape 5 réutilise exactement la même syntaxe <external>:<internal>/<protocol> pour rediriger vers une VM du laboratoire une fois qu'elle existe ; « interne » désigne alors l'adresse NAT privée de cette VM, et non celle de la VM d'automatisation.)

  1. Lancez l'installation comme d'habitude :
./setup_kvm_node.py

Cela définit le réseau libvirt labnat (en NAT, avec DHCP et passerelle gérés par libvirt, le même mécanisme que le réseau intégré default de libvirt, mais avec le nom et le CIDR de ce projet) au lieu d'un bridge, y crée la VM d'automatisation avec une IP statique dans cette plage privée, puis redirige en DNAT les trois ports ci-dessus depuis l'IP réelle de l'hôte.

  1. Vérifiez que le réseau et les règles de redirection existent, sur l'hyperviseur :
virsh net-list                              # labnat: active
iptables -t nat -L LAB_PORTFWD -n -v         # DNAT rules to the automation VM's private IP
iptables -L LAB_PORTFWD_FWD -n -v            # matching FORWARD-chain ACCEPT rules
  1. Joignez la VM d'automatisation depuis l'extérieur de l'hyperviseur, avec l'IP réelle de l'hyperviseur, et non l'adresse privée 192.168.150.x de la VM d'automatisation, qui n'est routable depuis nulle part ailleurs :
ssh root@<hypervisor-real-ip>          # DNAT'd to the automation VM's SSH, port 22

Les ports 80 et 443 sont aussi redirigés par défaut (le serveur HTTP des fichiers de provisionnement et, une fois l'interface web installée, son écoute HTTPS) et se joignent de la même façon, via l'IP réelle de l'hyperviseur.

  1. Ajoutez une redirection vers une VM du laboratoire, et pas seulement vers la VM d'automatisation : donnez à ce nœud un champ forwarded_ports et activez une fois le service portforward dans common.services :
{
  "nodes": {
    "app1.mydemo.lab": {
      "myip": "192.168.150.20",
      "forwarded_ports": ["8080:80/TCP", "8443:443/TCP"]
    }
  },
  "common": { "services": ["portforward"], "...": "…rest of common as usual" }
}

setup_lab.py/setup_vm.py redirigent en DNAT ces deux ports depuis l'IP réelle de l'hyperviseur de la même façon, la première fois qu'un nœud du laboratoire déclare forwarded_ports.

Pour ajouter un module : créez un exécutable scripts/install_<name> dans n'importe quel langage, avec ou sans extension de fichier (install_<name>.py, install_<name>.sh, un binaire compilé), ajoutez si besoin des modèles sous templates/addons/<name>/ et référencez "<name>" dans la liste addons de votre JSON. install_automation_node_scripts.sh l'installe sous /usr/local/bin/install_<name>, et setup_lab.py et l'interface web ne l'utilisent qu'au travers de son interface en ligne de commande :

  • install_<name> --capabilities affiche ces mêmes capacités en JSON

Backends de calcul

Les VM d'un laboratoire utilisent par défaut libvirt (les hyperviseurs KVM ci-dessus). Définissez common.backend (ou un backend par nœud, prioritaire) pour en cibler un autre ; voir l'enum du champ backend pour la liste actuelle complète. Chaque backend non par défaut a besoin de ses propres identifiants dans /etc/lab_creation.cfg :

Affichage de la console avec libvirt : les VM du laboratoire reçoivent un affichage SPICE (--graphics spice,listen=0.0.0.0) sauf si le QEMU de l'hyperviseur ne prend pas en charge SPICE (c'est le cas de SLES 16) ; elles reçoivent alors VNC. lab-in-a-box le lit dans virsh domcapabilities une fois par exécution ; si cette requête échoue, il utilise SPICE.

Plusieurs comptes cloud, de la même façon que KVM_HOSTS vous donne plusieurs hyperviseurs : placez chaque compte cloud dans son propre fichier sous /etc/lab_creation/credentials/ (chemin configurable par CREDENTIALS_PATH dans lab_creation.cfg), sous la forme <name>.yaml (ou .json/.cfg : l'extension choisit l'analyseur ; seuls .yaml/.json prennent en charge la forme chiffrée décrite plus bas, car le format plat KEY=value d'un .cfg ne peut pas la contenir). Chaque fichier déclare cloudtype (aws/gcp/hetzner/…) et les clés de connexion habituelles de ce fournisseur, exactement les mêmes que celles que le backend lit déjà dans lab_creation.cfg (AWS_REGION, AWS_PROFILE, AWS_SUBNET_ID, …). Un nœud (ou common) en choisit un avec "cloud_account": "<name>", exactement comme "kvm_host": "<host>" :

// /etc/lab_creation/credentials/aws-sandbox.yaml  (built with setup_credentials.py, below)
"nodes": {
  "jupiter.mydemo.lab": { "cloud_account": "aws-sandbox" },
  "saturn.mydemo.lab":  { "cloud_account": "aws-prod" }
}

Quand cloud_account est défini, son cloudtype est le backend (le champ backend devient donc facultatif ; si vous définissez les deux et qu'ils diffèrent, la vérification préalable échoue), et les clés du fichier de compte s'appliquent par-dessus lab_creation.cfg pour ce nœud seulement. Omettez cloud_account partout pour conserver le comportement actuel à un seul compte, inchangé. Chaque compte est un réseau isolé, si bien que la VM DNS cloud décrite plus bas devient propre à chaque compte (lab-dns-aws-sandbox, lab-dns-aws-prod, …) ; le compte par défaut sans nom garde le nom simple lab-dns-<backend>.

Les fichiers d'identifiants sont chiffrés au repos par défaut. Créez-en un avec :

setup_credentials.py                              # interactive: pick a provider, fill in its fields
setup_credentials.py --encrypt-existing myfile.yaml  # encrypt an already-written plaintext file's sensitive fields

Chiffrement (voir libs/crypto_store.py) : la phrase secrète passe par Argon2id (une KDF volontairement lente et gourmande en mémoire ; c'est elle, et non le chiffrement, qui constitue la vraie barrière de sécurité d'un fichier chiffré par phrase secrète) pour dériver un secret maître de 512 bits ; HKDF-SHA512 dérive ensuite deux sous-clés indépendantes de 256 bits (séparées par étiquette, et non simplement coupées en deux) ; les données sont chiffrées avec AES-256-GCM puis ChaCha20-Poly1305 en cascade, deux chiffrements AEAD structurellement différents et à clés indépendantes, si bien que casser complètement un seul algorithme ne suffit pas. Tout outil qui a besoin d'un identifiant (setup_lab.py, setup_vm.py, …) demande la phrase secrète une fois par exécution (conservée uniquement en mémoire du processus, jamais écrite nulle part) via try_load_cloud_account() de libs/primary.py, la seule fonction par laquelle tout passe.

Un fichier peut renoncer au chiffrement avec unencrypted: true au premier niveau (ce n'est pas le défaut : setup_credentials.py demande confirmation avant d'en écrire un ainsi). --encrypt-existing chiffre sur place uniquement les champs qui semblent sensibles (noms en forme de secret, mot de passe ou jeton), laisse lisibles par exemple AWS_REGION/AWS_PROFILE et n'écrase jamais son entrée : il écrit <name>.encrypted.yaml à côté pour que vous le relisiez et le mettiez en place. Nécessite le paquet Python cryptography (python311-cryptography, ou pip install cryptography, ≥41 pour Argon2id) sur la VM d'automatisation ; il n'est importé que lorsqu'un fichier réellement chiffré est utilisé, si bien qu'un laboratoire qui ne définit jamais cloud_account n'a besoin d'aucune nouvelle dépendance.

Identifiants de services externes (SCC, SUSE Application Collection, Hermes, …). Le même magasin /etc/lab_creation/credentials/, le même chiffrement et le même outil setup_credentials.py couvrent aussi les identifiants de services externes autres que les clouds. Un fichier est marqué par credential_kind (par ex. scc, appcollection, hermes) au lieu de cloudtype, si bien que les deux notions partagent répertoire et format sans jamais entrer en conflit. Chaque module qui a besoin d'un identifiant de service externe documente son propre champ facultatif <field>_account (par ex. smlm_scc_account, suse_ai_registry_account, hermes_account) pour en désigner un explicitement ; s'il n'est pas défini, un fichier unique avec le credential_kind correspondant est détecté automatiquement, comme pour cloud_account. Les identifiants en clair dans le JSON du laboratoire restent tout à fait valables : ce magasin est une alternative facultative, jamais une obligation ; les champs en clair de chaque module (smlm_scc_user, suse_ai_registry_user, hermes_llm_api_key, …) fonctionnent toujours sans changement si vous n'utilisez jamais le magasin d'identifiants.

setup_credentials.py   # interactive — now asks "cloud provider or external service?" first

Un fichier d'identifiants par type sert à tous les modules qui en ont besoin (par ex. un seul fichier scc couvre les identifiants SCC de n'importe quel module), quel que soit le préfixe des champs JSON de chacun ; voir resolve_credential()/Validator.vreq_or_credential() dans libs/addon_common.py et les fonctions *_service_credential* de libs/primary.py pour le mécanisme sous-jacent.

Backends cloud (Hetzner/AWS/GCP/Alibaba/Scaleway/UpCloud/OVHcloud/Exoscale) et myip : laissez vide le myip d'un nœud cloud dans le JSON du laboratoire : la vraie IP n'est connue que lorsque le fournisseur l'attribue à la création, ce n'est pas quelque chose que l'on peut fixer à l'avance comme une IP statique libvirt/Harvester. setup_vm.py récupère la vraie IP dans la valeur renvoyée par create_vm() et l'enregistre dans le DNS après la création réelle du nœud, pas avant (un vrai bogue trouvé lors des tests en conditions réelles d'AWSBackend, 2026-09-06 ; voir TODO). mymac n'a pas non plus de sens pour un backend cloud : laissez-le vide ; il est ignoré au lieu d'être généré ou vérifié.

VM DNS cloud : la première fois qu'un nœud du laboratoire utilise un backend cloud donné, setup_vm.py provisionne aussi (ou réutilise, si elle existe déjà) une petite VM DNS peu coûteuse dans ce même réseau cloud, lab-dns-<backend>, par ex. lab-dns-aws, qui exécute BIND. Elle existe parce que les nœuds cloud ne peuvent généralement pas du tout joindre le serveur BIND de automation.mydemo.lab (il se trouve derrière le NAT/routeur du laboratoire domestique, inaccessible depuis Internet) ; un vrai cluster cloud à plusieurs nœuds a besoin de son propre serveur DNS dans ce même réseau pour que ses nœuds se résolvent entre eux. L'entrée DNS de chaque nœud cloud est enregistrée à la fois dans cette VM DNS et dans la zone centrale de automation.mydemo.lab. Limites connues : (1) un nœud cloud tout juste créé n'utilise pas encore automatiquement cette VM DNS pour sa propre résolution, si bien qu'un deuxième nœud cloud du même laboratoire ne peut pas encore résoudre le premier par son nom sans configuration supplémentaire ; (2) les nœuds interrogent cette VM DNS via son IP privée ; les requêtes DNS vers son IP publique depuis l'extérieur du cloud peuvent être interceptées par les réseaux traversés, car certains fournisseurs d'accès et routeurs répondent eux-mêmes à tout le trafic DNS. Voir la docstring de ensure_cloud_dns_vm() dans libs/backends.py.

Dimensionnement des instances cloud : chaque backend cloud convertit VM_CPU/VM_MEM en le plus petit type d'instance, type de serveur, plan ou flavor suffisant du fournisseur, à partir d'une petite table intégrée (la colonne « Notes » de chacun précise lequel) ; cette table n'a jamais été conçue comme une limite. Deux façons de la remplacer, par ordre de priorité : 1. cloud_instance_type (dans common ou par nœud ; celui du nœud l'emporte) : le nom exact d'un type d'instance, type de serveur, plan ou flavor, utilisé tel quel sans aucune sélection automatique. Fonctionne de la même façon sur tous les backends cloud, y compris OVHcloud (qui saute son appel en direct à l'API des flavors) et GCP (qui ne construit pas de type personnalisé e2-custom-<cpu>-<mem> ; indiquez plutôt un vrai type prédéfini comme n2-standard-4). 2. Une clé de configuration *_INSTANCE_TYPES/*_SERVER_TYPES/*_PLANS (voir la ligne de chaque fournisseur ci-dessous) : remplace entièrement la table intégrée, si bien que la sélection automatique par VM_CPU/VM_MEM continue de fonctionner, mais avec votre propre liste. Format : name:cores:mem_gb,name:cores:mem_gb,..., par ex. HETZNER_SERVER_TYPES=cx22:2:4,cx32:4:8,cx42:8:16. Cela remplace la table en entier au lieu de la fusionner : répétez les entrées intégrées que vous voulez garder. GCP et OVHcloud n'ont pas cette clé : GCP construit un vrai type de machine personnalisé directement à partir de VM_CPU/VM_MEM (pas de catalogue à remplacer) et OVHcloud interroge déjà en direct sa vraie liste de flavors à la création (voir sa ligne).

Tests

Chaque vérification s'exécute dans son propre conteneur podman indépendant et jetable : un plantage, un blocage ou un état résiduel dans l'une ne peut affecter aucune autre :

tests/run_tests.sh

Couvre la syntaxe bash et Python de toute l'arborescence, la cohérence entre schémas et interface web, des tests unitaires avec SSH simulé pour chaque bibliothèque principale et chaque script d'orchestration, et des tests de non-régression pour les bogues trouvés lors des tests en conditions réelles. Configuration git initiale

Après avoir cloné le dépôt, lancez :

git config core.hooksPath .githooks

Cela active les hooks de .githooks/, qui : - lancent la suite de tests complète avant chaque commit - gèrent l'estampillage de version de chaque script (voir ci-dessous)

Fonctionnement du versionnage

Tout est géré par les hooks git ci-dessus : vous ne modifiez jamais __LABVERSION__ à la main.

Chaque script contient le marqueur :

__LABVERSION__ = "__LABVERSION__"

Les hooks de .githooks/ développent et restaurent ce marqueur automatiquement :

Hook Déclencheur Action
post-checkout git checkout / git switch Remplace __LABVERSION__ dans chaque script par le hash du dernier commit qui a modifié ce fichier
post-merge git pull / git merge Comme ci-dessus
post-rewrite git rebase / git commit --amend Comme ci-dessus
pre-commit git commit Restaure __LABVERSION__ dans les scripts indexés avant l'écriture du commit, si bien que les hashs ne sont jamais stockés dans le dépôt

Résultat : chaque script de votre arborescence de travail affiche sa propre version avec --version, et le dépôt stocke toujours le marqueur vierge. Quand les scripts sont installés par install_automation_node_scripts.sh, la même substitution de hash par fichier est appliquée à l'installation avec git log -1 --format=%h.

Installer les scripts sur la VM d'automatisation

Depuis la racine du dépôt sur la VM d'automatisation (ou sur toute machine où le dépôt est cloné) :

./install_automation_node_scripts.sh

Cela sauvegarde l'installation existante (dans sa propre archive horodatée et, séparément, dans ce que conserve votre propre processus de sauvegarde), copie chaque script, bibliothèque et modèle vers son chemin système et estampille chaque fichier installé avec son hash de version.
