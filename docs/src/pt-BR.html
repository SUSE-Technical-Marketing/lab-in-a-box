lab-in-a-box cria laboratórios completos a partir de um único arquivo JSON ou YAML: as VMs, o DNS, os clusters Kubernetes e os complementos que você descrever. As VMs podem rodar nos seus próprios hosts KVM, no Harvester ou em qualquer uma de oito nuvens públicas, e o mesmo arquivo funciona em todas elas.

Por que lab-in-a-box?

  • Um arquivo, um comando. Descreva VMs, clusters Kubernetes (RKE2 ou K3s) e complementos de forma declarativa. O setup_lab.py os cria na ordem das dependências, sem que você precise executar virt-install ou Ansible manualmente.
  • Laboratório em casa ou na nuvem, a mesma definição. As VMs do laboratório rodam em hosts KVM próprios, no Harvester HCI ou na AWS, Google Cloud, Alibaba Cloud, Hetzner, Scaleway, UpCloud, OVHcloud ou Exoscale. Um laboratório pode abranger vários hosts KVM e combinar nuvens e locais por meio de uma rede sobreposta WireGuard entre nuvens.
  • 71 complementos prontos. Rancher, Longhorn, NeuVector, Harbor, Keycloak, Jenkins, Argo CD, SUSE Multi-Linux Manager/Uyuni, Nextcloud e outros, além de aplicações de demonstração intencionalmente vulneráveis para treinamento em segurança.
  • Uma interface web que acompanha o código. O lab-builder gera cada formulário a partir do esquema do próprio complemento, então um campo novo em um script aparece na interface sem mudanças no frontend.
  • Provisionamento intercambiável. Ignition e Combustion para SLE Micro, cloud-init para openSUSE e Ubuntu, virt-customize para imagens antigas, ou uma instalação automatizada a partir de uma ISO de instalação (AutoYaST, Kickstart, Preseed ou AutoInstall).
  • Credenciais fora do arquivo do laboratório. As credenciais de nuvens e serviços podem ficar em arquivos criptografados por conta (derivação de chave Argon2id, seguida de AES-256-GCM e ChaCha20-Poly1305 em cascata).
  • Testes em contêineres. Cada verificação roda em um contêiner podman descartável, e um hook de pre-commit executa as verificações relevantes.

Arquitetura

O sistema é construído em torno de uma arquitetura de duas camadas:

Nó(s) hipervisor

Uma ou mais máquinas físicas executando KVM/QEMU. Cada uma hospeda VMs do laboratório e guarda as imagens QCOW2 de origem em /var/lib/libvirt/images/sources/. Serve um NUC, uma estação de trabalho ou qualquer máquina x86_64 capaz de executar KVM. Laboratórios que precisam de mais capacidade do que uma única máquina podem abranger vários hosts KVM; veja laboratórios com vários hosts abaixo.

VM de automação

Uma VM pequena que roda no hipervisor e atua como plano de controle de todo o laboratório. Ela fornece:

  • DNS: o BIND (named) serve o domínio do laboratório e encaminha consultas externas, de modo que todos os nomes do laboratório são resolvidos a partir de qualquer cliente que o utilize
  • HTTP: serve os arquivos de provisionamento (Ignition, Combustion, cloud-init) em /srv/www/htdocs/lab_creation/
  • Scripts: todos os comandos de gerenciamento do laboratório, instalados em /usr/local/bin/
  • Interface web (opcional): o lab-builder, um editor de lab.json no navegador

Todos os comandos do usuário são executados na VM de automação. Ela se conecta por SSH aos hipervisores e às VMs criadas. Depois da configuração inicial, não é preciso acessar o hipervisor diretamente.

Por dentro

As ferramentas de linha de comando e todos os complementos são escritos em Python 3.11, em libs/ e scripts/, e instalados em /usr/local/lib/lab_creation/. Eles se organizam em torno de um pequeno conjunto de módulos de biblioteca compartilhados (lab_creation.py, backends.py, services.py, spacecmd_common.py, …), e não uns dos outros. A criação de VMs fica atrás de uma interface VMBackend intercambiável com dez implementações: libvirt, Harvester e oito nuvens públicas (veja Backends de computação), de modo que os complementos e a orquestração não mudam entre elas. As implementações em bash que elas substituíram estão arquivadas em legacy_bash/, incluindo o install_ds389 original.

Como funciona

Fluxo de implantação

O setup_lab.py executa uma sequência fixa de fases; as duas fases exclusivas do Kubernetes são totalmente ignoradas em um laboratório só de VMs (sem seção kclusters):

    A -->|"no kclusters"| D["phase_create_vms"]
    C --> D["phase_create_vms"]
    D -->|"has kclusters"| F["phase_reboot_and_wait_kept_nodes"]
    D -->|"no kclusters"| H["phase_vm_addons"]
    F --> G["phase_install_k8s_and_addons"]
    G --> H["phase_vm_addons"]

Provisionamento de VMs

Cada VM é criada assim: 1. Define-se em qual host KVM ela fica (o campo explícito kvm_host, ou seleção automática pela capacidade livre; veja laboratórios com vários hosts) 2. Copia-se e redimensiona-se uma imagem QCOW2 de origem nesse host 3. Geram-se os arquivos de provisionamento a partir de modelos, conforme o config_method 4. Registra-se uma entrada DNS no BIND 5. Executa-se o virt-install no hipervisor via SSH 6. Aguarda-se o SSH ficar disponível

O método de provisionamento é definido por config_method no JSON do laboratório (por nó ou em common):

Valor Método Usado para
(vazio, padrão) Ignition + Combustion SLE Micro
cloud-init ISO do cloud-init openSUSE Leap, Ubuntu
virt_customize Modifica o QCOW2 diretamente no hipervisor (virt-customize); o convidado não precisa suportar Ignition nem cloud-init CentOS 7, Debian/RHEL antigos ou qualquer imagem sem Ignition/cloud-init
install_iso Instalação automatizada a partir de uma ISO de instalação real (AutoYaST, Kickstart, Preseed ou AutoInstall, escolhido por install_type) Distribuições sem outro caminho de provisionamento

Configuração do Kubernetes

Com as VMs no ar, o setup_lab.py instala o Kubernetes em cada nó conforme a seção kclusters do JSON. RKE2 e K3s são suportados. Quando um cluster fica pronto, seus complementos rodam em sequência; os complementos de VM (ligados a um nó em vez de um cluster) rodam depois que esse nó é provisionado.

Laboratórios com vários hosts

Um laboratório não está limitado a um hipervisor. Defina KVM_HOSTS (separados por espaço) em /etc/lab_creation.cfg na VM de automação para disponibilizar mais de um hipervisor:

KVM_HOSTS="hv1.mydemo.lab hv2.mydemo.lab hv3.mydemo.lab"

Depois, para cada nó do JSON do laboratório: - fixe-o explicitamente com "kvm_host": "hv2.mydemo.lab" na configuração do nó, ou - deixe a seleção automática: omita kvm_host; o nó vai para o host configurado que tiver no momento CPU/RAM/disco livres suficientes (verificado ao vivo via SSH).

Nós sem kvm_host e instalações com um único host configurado se comportam exatamente como antes desse recurso existir: nada muda para um laboratório com um só hipervisor.

Rede sobreposta WireGuard entre nuvens

Em geral, um nó de laboratório na nuvem não consegue alcançar pela rede a rede privada de outra conta de nuvem nem o laboratório libvirt doméstico: cada um é sua própria VPC ou rede isolada. common.overlay: true no JSON do laboratório roteia entre si os SITES deste laboratório, de site para site, pelas sub-redes reais, por meio de uma rede sobreposta WireGuard em estrela (libs/overlay.py):

graph TD
    Hub["Overlay hub<br/>(gateway VM, stable public IP)"]
    HomeGW["Home automation VM<br/>(site gateway)"]
    GWB["Site gateway VM<br/>(account B)"]
    HomeNode["home lab node"]
    NodeA["node — account A (hub's own site)"]
    NodeB["node — account B"]
    HomeGW -- "wg0 spoke" --> Hub
    GWB -- "wg0 spoke" --> Hub
    HomeNode -. "local route" .-> HomeGW
    NodeB -. "local route" .-> GWB
    NodeA -. "on the hub's own subnet" .-> Hub

Apenas o gateway de cada site entra na rede sobreposta, nunca um nó individual do laboratório. Um "site" é o laboratório libvirt doméstico ou uma conta de nuvem; o gateway é a própria VM de automação do site doméstico (mysource em /etc/lab_creation.cfg) ou, numa conta de nuvem, uma pequena VM dedicada criada ou reutilizada ali automaticamente (lab-overlay-gw-<backend>[-<account>], a mesma convenção de nomes da VM de DNS na nuvem). Todos os OUTROS nós apenas recebem uma rota local persistente para a sub-rede real de cada outro site, pelo gateway do próprio site: esse é todo o mecanismo, sem participação de cada nó no WireGuard.

OVERLAY_HUB_ACCOUNT (obrigatório, em /etc/lab_creation.cfg) indica a conta de nuvem cuja VM de gateway é o hub, o único site com IP público estável ao qual todos os outros se conectam. OVERLAY_CIDR (padrão 10.99.0.0/16) é usado só para os endereços dos gateways no túnel, não para rotear o tráfego real; OVERLAY_WG_PORT (padrão 51820) é a porta de escuta do hub. A entrada, a saída e a distribuição de rotas acontecem automaticamente no setup_vm.py; não há mais nada para executar manualmente.

Limitações conhecidas: o DNS não é alterado (um nó fica acessível pelo nome real quando esse nome resolve para uma sub-rede já roteada, não antes); os nós já provisionados de um site não são roteados de novo quando um novo site remoto entra depois, apenas atualizados no provisionamento de cada nó; a AWS exige desativar o "source/dest check" do gateway do site para encaminhar tráfego (feito automaticamente), e ainda não há equivalente para os outros 7 backends de nuvem.

Ordem de carregamento das bibliotecas

Cada script carrega a configuração nesta ordem:

  1. /etc/lab_creation.defaults: padrões do sistema, caminhos, listas de pacotes
  2. /usr/local/lib/lab_creation/primary.py: validação de entrada, carregamento da configuração
  3. /etc/lab_creation.cfg: configurações específicas do nó (REMOTE_HOST, ROOT_SSH_KEY, VIRT_SRV, KVM_HOSTS etc.)
  4. /usr/local/lib/lab_creation/lab_creation.py: funções de VM, DNS e orquestração
  5. /usr/local/lib/lab_creation/k8s.py: funções de cluster Kubernetes

Requisitos

  • Uma máquina capaz de executar KVM (com Intel VT-x ou AMD-V ativado)
  • Acesso à Internet (ou um espelho local) para baixar pacotes e imagens
  • Uma imagem QCOW2 do sistema escolhido em /var/lib/libvirt/images/sources/ no hipervisor

O hipervisor não precisa ter Python instalado antes: o comando de configuração instala python311 no openSUSE Leap / SLES 15 e o python3 da própria distribuição (3.9 ou mais recente) em todas as outras.

Imagens testadas: - SLE Micro: recomendada, usada com Ignition+Combustion - openSUSE Leap Micro: suportada, usada com cloud-init

Etapa 1: instalar o sistema do hipervisor

Instale um destes sistemas no seu hardware; basta uma instalação mínima ou de servidor, sem bridge nem pacotes extras antes:

Família Versões
openSUSE Leap, SLES 15 (SP6+), 16
Debian, Ubuntu Debian 12, 13; Ubuntu 22.04, 24.04
RHEL, Rocky Linux, AlmaLinux, CentOS Stream, Fedora 9, 10; Fedora atual

Outras versões dessas famílias recebem a lista de pacotes correspondente mais recente, com um aviso de que ela não foi verificada para elas. O SLES precisa de um código de registro (pedido durante a configuração), a menos que o host já esteja registrado.

Em hipervisores da família RHEL e Fedora a configuração do host é concluída, mas a VM de automação ainda não pode ser criada neles: o libguestfs desses sistemas não consegue ler o sistema de arquivos btrfs da imagem openSUSE Leap. Por enquanto, crie o nó de automação em um host de outra família.

Gravar um pendrive inicializável no Linux 
# Before inserting USB:
cat /proc/partitions > /tmp/partb4

# Insert USB, then:
cat /proc/partitions > /tmp/parta

# Find the new device:
diff /tmp/part*

O próximo comando apaga todos os dados do dispositivo de destino. Confira sdX com a saída do diff acima antes de executá-lo.

# Write the ISO (replace sdX with your device):
dd if=SLE-15-SP6-Online-x86_64-GM-Media1.iso of=/dev/sdX bs=4k && sync

Etapa 2: executar o comando de configuração

No hipervisor, como root:

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash

Ele instala o git e o Python, baixa o lab-in-a-box em /var/tmp/setup_demo_server/ e executa setup_demo_server/setup_kvm_node.py, que obtém as configurações do laboratório das suas opções e dos valores deste host; com --interactive ele as pede uma a uma, com esses valores como padrão:

  • Rede do laboratório: bridge coloca as VMs do laboratório na LAN do host; nat usa uma rede privada do libvirt (para um notebook ou um host com uma só placa de rede)
  • Domínio DNS do laboratório (padrão mydemo.lab), o endereço IP da VM de automação (é sugerido um endereço livre na rede do laboratório) e a senha de root
  • No SLES, o código de registro

A rede, o gateway, o servidor DNS, o fuso horário e a chave SSH (~/.ssh/id_ed25519.pub, criada se não existir) vêm do host. As respostas são gravadas em setup_demo_server/lab.cfg; depois de um resumo (e, com --interactive, de uma confirmação), a configuração:

  1. instala os pacotes do hipervisor para a distribuição detectada (EPEL e CRB são ativados em hosts da família RHEL);
  2. no modo bridge, transforma a placa de rede da rota padrão em uma porta de br0, mantendo o endereço do host. NetworkManager, netplan, wicked, systemd-networkd e ifupdown são suportados. Um temporizador restaura a configuração de rede anterior se o gateway não responder pelo bridge, de modo que uma mudança malsucedida não deixa o host inacessível;
  3. configura o libvirt e cria a VM de automação.

Cada configuração pode ser passada como opção, por exemplo em uma execução sem intervenção a partir do cloud-init:

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh \
  | sudo bash -s -- --domain mydemo.lab --automation-ip 192.168.8.71 --root-password 'secret'

Sem --root-password (ou LAB_ROOT_PASSWORD), uma senha é gerada e mostrada no final, a menos que --interactive a peça. Execute python3 /var/tmp/setup_demo_server/setup_demo_server/setup_kvm_node.py --help para ver todas as opções.

Etapa 3: executar de novo ou alterar a configuração

Executar o comando novamente usa o lab.cfg existente como está; as opções que correspondem às suas configurações (por exemplo --network-mode nat) as atualizam antes, e --reconfigure pergunta tudo de novo. Para revisar ou editar o lab.cfg antes de qualquer mudança, baixe apenas o código:

curl -fsSL https://raw.githubusercontent.com/SUSE-Technical-Marketing/lab-in-a-box/main/install_demo_server_scripts.sh | sudo bash -s -- --fetch-only

Para configurar outra máquina a partir desta, informe o endereço dela; o código é copiado por SSH e as mesmas opções se aplicam:

python3 /var/tmp/setup_demo_server/setup_demo_server/setup_kvm_node.py <IP>

Principais configurações do lab.cfg:

Configuração Descrição
_network_mode, _bridge_name, _bridge_nic Rede em bridge ou NAT; o bridge ao qual as VMs do laboratório se conectam e a placa de rede que vira sua porta
_mynet, _mygw, _mydns, _myip Rede do laboratório, gateway, DNS de origem e endereço da VM de automação
ROOT_PWD_HASH, ROOT_SSH_PUB_KEY Hash da senha de root da VM de automação e a chave SSH autorizada a entrar
AUTOMATION_HOSTNAME Nome de host da VM de automação (por exemplo automation.mydemo.lab)
_QCOW_IMAGE Nome do arquivo da imagem QCOW2 de origem

Etapa 4: configurar a VM de automação

Acesse a VM de automação por SSH e instale os scripts do laboratório:

ssh <AUTOMATION_HOSTNAME>
./install_automation_node_scripts.sh

cp /etc/lab_creation.cfg.example /etc/lab_creation.cfg
vim /etc/lab_creation.cfg

Principais configurações do lab_creation.cfg:

Configuração Descrição
REMOTE_HOST Nome de host ou IP do hipervisor KVM (principal)
KVM_HOSTS (opcional) lista separada por espaços de hipervisores adicionais para um laboratório com vários hosts
ROOT_SSH_KEY Conteúdo da chave pública SSH injetada nas VMs
VIRT_SRV URI de conexão do libvirt (por exemplo qemu+ssh://root@hypervisor/system)
NETWORK Rede libvirt padrão das VMs (por exemplo bridge=br0)

HTTP e HTTPS. A VM de automação serve seus arquivos na porta 80 (HTTP) e na porta 443 (HTTPS, certificado autoassinado em /etc/lab_creation/tls/). Os instaladores (AutoYaST, kickstart, preseed) e o Helm os baixam por HTTPS e aceitam o certificado autoassinado. Defina PROVISIONING_TLS_VERIFY=1 para verificá-lo, ou PROVISIONING_BASE_URL (por exemplo http://192.168.88.250) para usar outro endereço ou voltar ao HTTP. O boot iPXE do Harvester sempre usa HTTP: o iPXE não aceita certificados autoassinados.

Etapa 5: apontar o DNS do cliente para a VM de automação

Para que os nomes de host sejam resolvidos a partir do seu computador:

# Linux (NetworkManager):
nmcli con mod <connection> ipv4.dns <AUTOMATION_IP>

# Or add to /etc/resolv.conf:
nameserver <AUTOMATION_IP>

Campos opcionais no nível do nó:

Campo Descrição

kvm_host Fixa esta VM em um hipervisor específico em um laboratório com vários hosts
extra_dsk Discos adicionais a anexar: "/dev/sdb", ou "/dev/sdb,bus=scsi" para mudar o barramento padrão de um disco

Substituições de configuração de complemento por nó: cada complemento tem uma seção de configuração compartilhada de nível superior (por exemplo client_registration no exemplo de SMLM anterior), usada por todos os nós que o listam em addons. Quando nós diferentes realmente precisam de valores diferentes para o mesmo complemento (o caso que motivou isso: um laboratório que registra muitos sistemas operacionais diferentes em um servidor Uyuni/SMLM compartilhado, em que cada nó precisa da sua própria client_registration_activation_key), dê à entrada addons[] desse nó uma substituição aninhada em vez de uma string simples:

"nodes": {
  "mercury.mydemo.lab": {
    "addons": [
      { "client_registration": { "client_registration_activation_key": "1-sles15sp7" } }
    ]
  },
  "callisto.mydemo.lab": {
    "addons": [
      "mariadb",
      { "client_registration": { "client_registration_activation_key": "1-debian13" } }
    ]
  }
}

Uma entrada simples "mariadb" se comporta exatamente como antes (só a seção compartilhada mariadb se aplica). A forma {"client_registration": {...}} substitui apenas esses campos, apenas para esse nó; tudo o que a substituição não menciona (servidor, usuário administrador, …) continua vindo da seção compartilhada client_registration. Isso funciona da mesma forma para qualquer complemento, não só para client_registration; cada install_<addon>.py adota o recurso lendo sua configuração com k8s.addon_node_config(definition, "<addon>", vm_name) em vez de definition.get("<addon>", {}) diretamente; veja addon_entry_name()/addon_entry_overrides() em libs/apps.py, a análise compartilhada pela qual passa todo consumidor de uma lista addons[].

Campo Descrição
mgm_node Nome de host do nó que executa os instaladores de complementos do cluster; por padrão, o primeiro nó servidor

Implantar uma imagem antiga (CentOS 7)

O CentOS 7 (e outras imagens .qcow2 tão antigas) não traz Ignition/Combustion nem cloud-init, então config_method precisa ser virt_customize (veja Provisionamento de VMs): ele edita diretamente o sistema de arquivos do qcow2 em vez de depender de um agente dentro do convidado. Para uma imagem tão antiga, mais duas substituições importam:

  • VM_BOOT: "bios": o GRUB do CentOS 7 espera BIOS legado, não o UEFI padrão deste projeto.
  • VM_MACHINE: "pc": funciona com uma imagem GenericCloud do CentOS 7 de 2015 (kernel 3.10.0-229). Iniciada com o tipo de máquina padrão do virt-install (atualmente q35), ela fica presa para sempre em um shell de emergência do dracut (Not all disks have been found): o disco raiz virtio-blk nunca aparece a tempo com a topologia PCIe do Q35. O mesmo disco inicia normalmente com o chipset legado i440fx ("pc"). É uma incompatibilidade entre chipset e kernel antigo, nada específico deste projeto: a mesma substituição vale para qualquer convidado antigo o suficiente.
{
  "nodes": {
    "legacy1.mydemo.lab": {
      "myip": "192.168.88.120",
      "config_method": "virt_customize",
      "ISO_IMAGE": "CentOS-7-x86_64-GenericCloud-20150628_01.qcow2",
      "VM_BOOT": "bios",
      "VM_MACHINE": "pc"
    }
  },
  "common": { "VM_MEM": "2048", "VM_DSK": "30", "VM_CPU": "1", "VM_ROOT_PASS": "12345678" }
}

setup_lab.py legacy.json

VM_ROOT_PASS (em common ou por nó) define a senha de root que o virt_customize grava diretamente na imagem; omita-a para reutilizar ROOT_PWD_HASH do lab_creation.cfg, a mesma alternativa usada pelo cloud-init e pelo Ignition.

O setup_lab.py verifica o arquivo automaticamente antes de fazer qualquer outra coisa: IPs errados, uma referência a um kcluster inexistente, um ISO_IMAGE ausente e erros semelhantes são detectados e mostrados (✗ Preflight FAILED — N error(s)) sem criar nada, em vez de falhar no meio do caminho. dig +short node101.mydemo.lab rancher.mydemo.lab

destroy_lab.py rancher-cluster.json

Guia 3: VM de automação atrás de NAT (notebook com uma placa de rede como hipervisor)

Objetivo: criar a VM de automação em um host sem placa de rede livre para o bridge, usando uma rede privada gerenciada pelo libvirt e portas específicas redirecionadas (DNAT) a partir do IP real do host. Testado ao vivo de ponta a ponta em uma VM aninhada descartável.

Se você não ativar, nada muda no fluxo do Início rápido padrão: _network_mode vale "bridge" por padrão, exatamente como em qualquer instalação existente.

  1. No lab.cfg (etapa 3 do Início rápido), defina:
_network_mode="nat"
_nat_network_name="labnat"          # default shown — a new libvirt virtual network, not your host's real LAN
_nat_network_cidr="192.168.150.0/24" # default shown
_nat_forwarded_ports="22:22/TCP 80:80/TCP 443:443/TCP"  # default shown — "<port on the HYPERVISOR's real IP>:<port on the AUTOMATION VM>/<protocol>"

Isso redireciona as portas 22/80/443 do IP real do hipervisor, acessível de fora (<external>) para as mesmas portas do endereço NAT privado da VM de automação (<internal>); neste momento a VM de automação é a única coisa escutando nessa rede privada, então "interno" aqui sempre significa "na VM de automação". (A etapa 5 abaixo reutiliza exatamente a mesma sintaxe <external>:<internal>/<protocol> para redirecionar para uma VM do laboratório quando ela existir; ali, "interno" passa a ser o endereço NAT privado dessa VM, não o da VM de automação.)

  1. Execute a configuração normalmente:
./setup_kvm_node.py

Isso define a rede libvirt labnat (com NAT; DHCP e gateway ficam a cargo do próprio libvirt, o mesmo mecanismo da rede default embutida no libvirt, só que com o nome e o CIDR deste projeto) em vez de um bridge, cria nela a VM de automação com um IP estático dentro dessa faixa privada e redireciona por DNAT as três portas acima a partir do IP real do host.

  1. Verifique se a rede e as regras de redirecionamento existem, no hipervisor:
virsh net-list                              # labnat: active
iptables -t nat -L LAB_PORTFWD -n -v         # DNAT rules to the automation VM's private IP
iptables -L LAB_PORTFWD_FWD -n -v            # matching FORWARD-chain ACCEPT rules
  1. Acesse a VM de automação de fora do hipervisor, usando o IP real do hipervisor, e não o endereço privado 192.168.150.x da VM de automação, que não é roteável a partir de nenhum outro lugar:
ssh root@<hypervisor-real-ip>          # DNAT'd to the automation VM's SSH, port 22

As portas 80 e 443 também são redirecionadas por padrão (o servidor HTTP dos arquivos de provisionamento e, quando você configurar a interface web, o seu HTTPS) e são acessadas da mesma forma, pelo IP real do hipervisor.

  1. Adicione redirecionamento para uma VM do laboratório, não só para a VM de automação: dê a esse nó um campo forwarded_ports e ative uma vez o serviço portforward em common.services:
{
  "nodes": {
    "app1.mydemo.lab": {
      "myip": "192.168.150.20",
      "forwarded_ports": ["8080:80/TCP", "8443:443/TCP"]
    }
  },
  "common": { "services": ["portforward"], "...": "…rest of common as usual" }
}

O setup_lab.py/setup_vm.py redireciona por DNAT essas duas portas a partir do IP real do hipervisor da mesma forma, na primeira vez que algum nó do laboratório declara forwarded_ports.

Para adicionar um complemento: crie um executável scripts/install_<name> em qualquer linguagem, com ou sem extensão de arquivo (install_<name>.py, install_<name>.sh, um binário compilado), adicione modelos em templates/addons/<name>/ se necessário e faça referência a "<name>" na lista addons do seu JSON.   • install_<name> --schema json mostra seu esquema em JSON, incluindo um objeto capabilities (targets, layers, requires_kubernetes, aux_services); --schema yaml mostra o mesmo em YAML
  • install_<name> --capabilities mostra as mesmas capacidades em JSON
  • install_<name> --validate <lab.json> termina com código diferente de zero, mostrando linhas [ERROR], quando sua configuração é inválida
  • install_<name> --version e --help
  • install_<name> <lab.json> o instala na VM indicada em $_vm_name (e no cluster de $clu_name para um complemento de cluster)

Um complemento em Python obtém tudo isso de addon_common.handle_common_args() e de um dicionário PLUGIN no nível do módulo; siga o modelo de um existente (carregue a seção JSON correspondente com load_definition() e faça o trabalho via SSH).

Backends de computação

As VMs de um laboratório usam libvirt por padrão (os hipervisores KVM acima). Defina common.backend (ou um backend por nó, que tem prioridade) para usar outro; veja o enum do campo backend para a lista completa atual. Cada backend não padrão precisa das próprias credenciais em /etc/lab_creation.cfg:

Gráficos de console no libvirt: as VMs do laboratório recebem uma tela SPICE (--graphics spice,listen=0.0.0.0), a menos que o QEMU do hipervisor não suporte SPICE (o SLES 16 é um caso); nesse caso recebem VNC. O lab-in-a-box lê isso em virsh domcapabilities uma vez por execução; se a consulta falhar, usa SPICE.

Várias contas de nuvem, do mesmo jeito que KVM_HOSTS oferece vários hipervisores: coloque cada conta de nuvem em um arquivo próprio em /etc/lab_creation/credentials/ (caminho configurável com CREDENTIALS_PATH no lab_creation.cfg), como <name>.yaml (ou .json/.cfg: a extensão escolhe o analisador; só .yaml/.json suportam a forma criptografada descrita abaixo, porque o formato plano KEY=value de um .cfg não comporta isso). Cada arquivo declara cloudtype (aws/gcp/hetzner/…) e as chaves de conexão usuais desse provedor, exatamente as mesmas que o backend já lê do lab_creation.cfg (AWS_REGION, AWS_PROFILE, AWS_SUBNET_ID, …). Um nó (ou common) escolhe uma com "cloud_account": "<name>", exatamente como "kvm_host": "<host>":

// /etc/lab_creation/credentials/aws-sandbox.yaml  (built with setup_credentials.py, below)
"nodes": {
  "jupiter.mydemo.lab": { "cloud_account": "aws-sandbox" },
  "saturn.mydemo.lab":  { "cloud_account": "aws-prod" }
}

Quando cloud_account está definido, seu cloudtype é o backend (então o campo backend passa a ser opcional; se você definir os dois e eles divergirem, a verificação prévia acusa erro), e as chaves do arquivo da conta se sobrepõem ao lab_creation.cfg apenas para aquele nó. Omita cloud_account em todo lugar para manter o comportamento atual de uma única conta, sem mudanças. Cada conta é uma rede isolada, então a VM de DNS na nuvem descrita abaixo passa a ser por conta (lab-dns-aws-sandbox, lab-dns-aws-prod, …); a conta padrão sem nome mantém o nome simples lab-dns-<backend>.

Os arquivos de credenciais são criptografados em repouso por padrão. Crie um com:

setup_credentials.py                              # interactive: pick a provider, fill in its fields
setup_credentials.py --encrypt-existing myfile.yaml  # encrypt an already-written plaintext file's sensitive fields

Criptografia (veja libs/crypto_store.py): a senha passa pelo Argon2id (uma KDF propositalmente lenta e pesada em memória; é ela, e não a cifra, a verdadeira barreira de segurança de um arquivo criptografado por senha) para derivar um segredo mestre de 512 bits; o HKDF-SHA512 então deriva duas subchaves independentes de 256 bits (separadas por rótulo, e não simplesmente divididas ao meio); os dados são criptografados com AES-256-GCM e depois ChaCha20-Poly1305 em cascata, duas cifras AEAD estruturalmente diferentes e com chaves independentes, de modo que quebrar totalmente um único algoritmo não basta. Toda ferramenta que precisa de uma credencial (setup_lab.py, setup_vm.py, …) pede a senha uma vez por execução (guardada só na memória do processo, nunca gravada em lugar nenhum) por meio de try_load_cloud_account() de libs/primary.py, a única função pela qual tudo passa.

Um arquivo pode dispensar a criptografia com unencrypted: true no nível superior (não é o padrão: o setup_credentials.py pergunta antes de gravar um assim). --encrypt-existing criptografa no lugar apenas os campos que parecem sensíveis (nomes com cara de segredo, senha ou token), deixa legíveis por exemplo AWS_REGION/AWS_PROFILE e nunca sobrescreve a entrada: grava <name>.encrypted.yaml ao lado para você revisar e colocar no lugar. Exige o pacote Python cryptography (python311-cryptography, ou pip install cryptography, ≥41 para o Argon2id) na VM de automação; ele só é importado quando um arquivo realmente criptografado é usado, então um laboratório que nunca define cloud_account não precisa de nenhuma dependência nova.

Credenciais de serviços externos (SCC, SUSE Application Collection, Hermes, …). O mesmo armazenamento /etc/lab_creation/credentials/, a mesma criptografia e a mesma ferramenta setup_credentials.py também cobrem credenciais de serviços externos que não são de nuvem. Um arquivo é marcado com credential_kind (por exemplo scc, appcollection, hermes) em vez de cloudtype, de modo que os dois conceitos compartilham diretório e formato sem nunca colidir. Cada complemento que precisa de uma credencial de serviço externo documenta seu próprio campo opcional <field>_account (por exemplo smlm_scc_account, suse_ai_registry_account, hermes_account) para indicá-la explicitamente; se não for definido, um único arquivo com o credential_kind correspondente é detectado automaticamente, como acontece com cloud_account. Credenciais em texto puro no JSON do laboratório continuam totalmente válidas: este armazenamento é uma alternativa opcional, nunca uma exigência; os campos em texto puro de cada complemento (smlm_scc_user, suse_ai_registry_user, hermes_llm_api_key, …) continuam funcionando sem mudanças se você nunca usar o armazenamento de credenciais.

setup_credentials.py   # interactive — now asks "cloud provider or external service?" first

Um arquivo de credenciais por tipo serve para todos os complementos que precisam desse tipo (por exemplo, um único arquivo scc cobre as credenciais SCC de qualquer complemento), independentemente do prefixo dos campos JSON de cada um; veja resolve_credential()/Validator.vreq_or_credential() em libs/addon_common.py e as funções *_service_credential* de libs/primary.py para o mecanismo por trás.

Backends de nuvem (Hetzner/AWS/GCP/Alibaba/Scaleway/UpCloud/OVHcloud/Exoscale) e myip: deixe vazio o myip de um nó de nuvem no JSON do laboratório: o IP real só é conhecido quando o provedor o atribui na criação, não é algo que se decide de antemão como um IP estático de libvirt/Harvester. O setup_vm.py pega o IP real do valor retornado por create_vm() e o registra no DNS depois que o nó existe de fato, não antes (um bug real encontrado nos testes ao vivo do AWSBackend, 2026-09-06; veja TODO). mymac também não faz sentido em um backend de nuvem: deixe-o sem definir; ele é ignorado em vez de gerado ou verificado.

VM de DNS na nuvem: na primeira vez que um nó do laboratório usa determinado backend de nuvem, o setup_vm.py também provisiona (ou reutiliza, se já existir) uma VM pequena e barata que serve DNS dentro dessa mesma rede de nuvem, lab-dns-<backend>, por exemplo lab-dns-aws, rodando BIND. Ela existe porque os nós de nuvem em geral não conseguem alcançar o servidor BIND do automation.mydemo.lab (ele fica atrás do NAT/roteador do laboratório doméstico, inacessível pela Internet); um cluster real de vários nós na nuvem precisa do próprio servidor DNS dentro dessa rede para que seus nós se resolvam entre si. A entrada DNS de cada nó de nuvem é registrada tanto nessa VM de DNS quanto na zona central do automation.mydemo.lab. Limitações conhecidas: (1) um nó de nuvem recém-criado ainda não passa a usar automaticamente essa VM de DNS para a própria resolução, então um segundo nó de nuvem do mesmo laboratório ainda não consegue resolver o primeiro pelo nome sem mais configuração; (2) consultar a zona dessa VM de DNS pelo IP elástico/público da AWS a partir de um cliente externo (inclusive o próprio automation.mydemo.lab) hoje retorna um NXDOMAIN falso da zona raiz em vez da resposta real; a consulta pelo IP privado ou pelo loopback funciona, e a causa do caminho pelo IP público ainda não foi encontrada. Veja a docstring de ensure_cloud_dns_vm() em libs/backends.py e o TODO.

Dimensionamento de instâncias na nuvem: cada backend de nuvem converte VM_CPU/VM_MEM no menor tipo de instância, tipo de servidor, plano ou flavor suficiente do provedor, a partir de uma pequena tabela embutida (a coluna "Notas" de cada um indica qual); essa tabela nunca foi pensada como limite. Há duas formas de substituí-la, em ordem de prioridade: 1. cloud_instance_type (em common ou por nó; o do nó prevalece): o nome exato de um tipo de instância, tipo de servidor, plano ou flavor, usado como está, sem escolha automática. Funciona igual em todos os backends de nuvem, inclusive no OVHcloud (que pula sua chamada ao vivo à API de flavors) e no GCP (que não cria um tipo personalizado e2-custom-<cpu>-<mem>; informe um tipo predefinido real como n2-standard-4). 2. Uma chave de configuração *_INSTANCE_TYPES/*_SERVER_TYPES/*_PLANS (veja a linha de cada provedor abaixo): substitui por completo a tabela embutida, de modo que a escolha automática por VM_CPU/VM_MEM continua funcionando, mas com a sua lista. Formato: name:cores:mem_gb,name:cores:mem_gb,..., por exemplo HETZNER_SERVER_TYPES=cx22:2:4,cx32:4:8,cx42:8:16. Isso substitui a tabela inteira, sem mesclar: repita as entradas embutidas que ainda quiser. GCP e OVHcloud não têm essa chave: o GCP cria um tipo de máquina personalizado real diretamente a partir de VM_CPU/VM_MEM (não há catálogo a substituir) e o OVHcloud já consulta ao vivo sua lista real de flavors na criação (veja a linha dele).

Testes

Cada verificação roda no seu próprio contêiner podman independente e descartável: uma falha, um travamento ou um estado residual em uma não afeta nenhuma outra:

tests/run_tests.sh

Cobre a sintaxe de bash e Python de toda a árvore, a consistência entre esquemas e a interface web, testes unitários com SSH simulado para cada biblioteca principal e script de orquestração, e testes de regressão para bugs encontrados em testes ao vivo. Para adicionar uma verificação, coloque um script executável em tests/checks/: ele é detectado automaticamente, sem nenhuma configuração.

Está ligado a um hook de pre-commit (ative uma vez por clone, veja Contribuir): roda automaticamente a cada commit e, se o podman não estiver instalado, é ignorado com um aviso em vez de bloquear o commit.

Cada um dos Exemplos acima tem um teste de implantação e verificação em hardware real em tests/examples/; eles precisam de um hipervisor KVM e de uma VM de automação funcionando, por isso não fazem parte da execução automática de tests/run_tests.sh, mas estão lá e podem ser executados manualmente (tests/examples/run_example.sh <name>) antes de enviar uma mudança que possa afetar algum desses fluxos documentados. Configuração inicial do git

Depois de clonar o repositório, execute:

git config core.hooksPath .githooks

Isso ativa os hooks de .githooks/, que: - executam o conjunto de testes completo antes de cada commit - cuidam da marcação de versão de cada script (veja abaixo)

Como funciona o versionamento

Isso fica inteiramente a cargo dos hooks do git acima: você nunca edita __LABVERSION__ à mão.

Todo script contém o marcador:

__LABVERSION__ = "__LABVERSION__"

Os hooks de .githooks/ expandem e restauram esse marcador automaticamente:

Hook Gatilho Ação
post-checkout git checkout / git switch Substitui __LABVERSION__ em cada script pelo hash do último commit que alterou esse arquivo
post-merge git pull / git merge Igual ao anterior
post-rewrite git rebase / git commit --amend Igual ao anterior
pre-commit git commit Restaura __LABVERSION__ nos scripts preparados antes de o commit ser gravado, de modo que os hashes nunca ficam armazenados no repositório

O resultado: cada script da sua árvore de trabalho mostra a própria versão com --version, e o repositório sempre guarda o marcador limpo. Quando os scripts são instalados pelo install_automation_node_scripts.sh, a mesma substituição de hash por arquivo é aplicada na instalação com git log -1 --format=%h.

Instalar os scripts na VM de automação

A partir da raiz do repositório na VM de automação (ou em qualquer máquina com o repositório clonado):

./install_automation_node_scripts.sh

Isso faz backup da instalação existente (no próprio tarball com data e hora e, separadamente, no que o seu próprio processo de backup guardar), copia cada script, biblioteca e modelo para o caminho do sistema e marca cada arquivo instalado com o hash da sua versão.

Dependências

Em tempo de execução (na VM de automação): python3.11, jq, ssh, rsync, nc, helm, kubectl, named (BIND)

A configuração do hipervisor exige ainda: virt-install, virsh, qemu-img, zypper, imagens QCOW2 de origem em /var/lib/libvirt/images/sources/

Executar o conjunto de testes exige ainda: podman

Usar uma definição de laboratório em YAML (em vez de JSON) exige ainda: pyyaml (pip install pyyaml)
