IT labs, deployed automatically

· Add-on Guide

An add-on installs one piece of software into a lab: on a Kubernetes cluster (a kcluster), on a VM or on an existing machine. It is one executable, in any language, and setup_lab.py, the preflight check and the web UI use it only through its command-line contract. This guide is that contract, and what to do to add one.

How a lab uses an add-on

A lab definition lists an add-on by its name in an addons array, and configures it in a top-level section of the same name:

{
  "kclusters": { "k1": { "clu_type": "rke2", "clu_rel": "stable", "mydomain": "lab", "addons": ["example_chart"] } },
  "nodes": {
    "vm1.lab": { "kcluster": "k1", "addons": ["example_motd"] },
    "vm2.lab": { "addons": [{ "example_motd": { "example_motd_message": "vm2's own message" } }] }
  },
  "example_chart": { "example_chart_replicas": 2 },
  "example_motd":  { "example_motd_message": "Welcome to the lab" }
}

An add-on is called at these points:

  1. Discovery. The web UI and the preflight run install_<name> --schema json to learn its fields and capabilities. The output is cached per file (in $LAB_ADDON_CACHE, else ~/.cache/lab_creation/addons.json) and refreshed when the file changes. It must answer within 120 seconds.
  2. Preflight. Before any VM is created, setup_lab.py checks where each add-on is placed against its capabilities, and runs install_<name> --validate <lab.json>. A non-zero exit stops the lab, with the add-on's [ERROR] lines as the reasons.
  3. Install. After the VMs and Kubernetes clusters are up, setup_lab.py runs install_<name> <lab.json>:
    • for a kcluster add-on, once per kcluster that lists it, with $clu_name set to the kcluster and $_vm_name to one of its nodes (its mgm_node, else its first node);
    • for a VM add-on, once per node that lists it, with $_vm_name set to that node.
    The lab definition is the first argument. A non-zero exit is reported in the lab summary as FAILED (exit N); the other add-ons still run.

The add-on reaches its node over SSH as root (ssh root@$_vm_name); the automation VM's key is already authorised there.

Naming and deployment

  • The file is scripts/install_<name>, with or without an extension (install_<name>.py, install_<name>.sh, a compiled binary), and executable. <name> is what labs write in addons; use the software's name, lower case, with _ between words.
  • install_automation_node_scripts.sh deploys it as /usr/local/bin/install_<name>, without the extension, and replaces __LABVERSION__ in a text file with the lab-in-a-box version.
  • Files it needs at run time (manifests, configuration templates) go in templates/addons/<name>/; they are deployed to /usr/share/lab_creation/templates/addons/<name>/ (_templ_addons_loc in /etc/lab_creation.defaults).

The contract

CommandMust
install_<name> --schema jsonexit 0 and print one JSON object: the schema (below). --schema yaml prints the same as YAML; JSON is valid YAML, so printing JSON is enough. --input-definition is an alias of --schema.
install_<name> --capabilitiesexit 0 and print the schema's capabilities object as JSON.
install_<name> --validate <lab.json>check its own section of the lab; print one [ERROR] … line per problem and exit with a non-zero code when there is one, else exit 0. [WARNING] … lines do not change the exit code. Print nothing else.
install_<name> --versionexit 0 and print install_<name> <version>.
install_<name> --helpexit 0 and print its usage and fields.
install_<name> <lab.json>install it (see above); exit 0 on success, non-zero on failure.

The schema

{
  "schema_version": "1.0",
  "addon": "example_chart",
  "section": "example_chart",
  "description": "podinfo web application installed with Helm",
  "fields": [
    {"name": "example_chart_ns", "type": "namespace", "required": false, "default": "podinfo",
     "description": "Namespace"},
    {"name": "example_chart_replicas", "type": "integer", "required": false, "default": "1", "min": 1, "max": 5,
     "description": "Number of replicas"}
  ],
  "capabilities": {
    "targets": ["container"], "layers": ["kubernetes"], "requires_kubernetes": ["rke2", "k3s"],
    "aux_services": [], "versions": {}
  }
}
  • schema_version: the version of this schema, MAJOR.MINOR (see Schema versions).
  • section: the top-level key of its configuration in a lab. description: one line, shown in the web UI.
  • Each field has name, type, required (true or false), and optionally default, description, enum (the allowed values; the web UI shows a list), pattern (a regular expression), min and max (numbers).
  • type is one of string, integer, boolean, password, port, url, namespace, version, array, object. The web UI shows a number box for integer and port, true/false for boolean, and masks password; a password value is never sent when the lab-builder hands a lab to another page.
  • capabilities:
    • targets: where it may be placed: container (on a kcluster), vm (a VM this lab creates), baremetal (an existing machine, existing nodes). The preflight refuses any other placement.
    • layers: how it installs: kubernetes, standalone-container (podman on a host), os-native (packages and files). The web UI groups add-ons by it.
    • requires_kubernetes: for a container add-on, the kcluster types it supports (rke2, k3s), or null.
    • aux_services: lab services it needs on the automation VM (e.g. pxe).
    • versions: optional version matrix; see Add-on version matrix.

Writing it in Python

A Python add-on gets the whole contract from libs/addon_common.py. It writes three things: a header comment block (the fields), a PLUGIN dict (the capabilities) and a main() that calls handle_common_args() first. See examples/addons/install_example_chart.py.

#!/usr/bin/env python3.11
# Schema version: 1.0
#
# JSON section: "example_chart" — podinfo web application installed with Helm
#
#   example_chart_ns       : [OPTIONAL] Namespace            (default: podinfo)
#   example_chart_version  : [OPTIONAL] Helm chart version   (empty = latest, e.g. 6.15.0)
#   example_chart_replicas : [OPTIONAL] Number of replicas   (default: 1) (min: 1) (max: 5)

__version__ = "__LABVERSION__"

PLUGIN = {
    "name": "example_chart",
    "targets": ["container"],
    "layers": ["kubernetes"],
    "requires_kubernetes": ["rke2", "k3s"],
    "aux_services": [],
}

def main():
    ac.handle_common_args(__file__, __version__, validate_fn=_validate, plugin=PLUGIN)
    ...

The # Schema version: MAJOR.MINOR line, above the header block, is the schema's schema_version. The header block starts at the JSON section: "<section>" — <description> line and ends at the first line that is not a comment. Each field is a line # <name> : <description>; a following comment line continues it. Inside a field:

  • [MANDATORY] or [OPTIONAL]; a # MANDATORY line makes every following field required, until a # OPTIONAL line.
  • (default: value), (options: a, b, c) (the enum), (pattern: regex), (min: N), (max: N).
  • A default is the literal value the add-on uses when the field is unset; surrounding quotes are dropped. It must be valid for the field's type (check_addon.py checks integer, port, boolean, namespace, url and version). Explanations go in the description, outside the parentheses. A default the add-on computes, such as a generated password or a value taken from another field, is described in the text ("when unset, …") and has no (default: …). In a field that holds a JSON object or list, write a sub-key's default as "(X when unset)": a (default: …) there would become the whole field's default.
  • The type comes from the name's suffix, for example: _ns/_namespace namespace, _version/_ver version, _url url, _port port, _pass/_pwd/_password password, _enabled boolean, _replicas integer; anything else is a string.

validate_fn receives an addon_common.Validator: vreq(section, field), vns(section), vver(section), vurl(section), vbool(section, field) add the matching [ERROR] lines, and you can append your own to v.errors. The version matrix's warnings are added for you.

Use the helpers in libs/lab_creation.py to work on nodes: ssh_run(host, cmd), setup_helm(host, clu_name), helm_repo_add(host, name, url), die(msg); and versions.helm_version_flag(value) for a chart version field.

Writing it in another language

Any executable works: it implements the commands of the contract itself and prints the schema JSON. See examples/addons/install_example_motd.sh, which uses jq (a dependency of the automation VM) to read the lab definition.

Reading its configuration

  • Its configuration is the lab's top-level <section> object. A missing field means its default.
  • A node may override it: an addons entry can be {"<name>": {...}} instead of "<name>", and those keys replace the section's for that node. In Python, k8s.addon_node_config(definition, "<name>", vm_name) returns the merged result; in jq: (.<section> // {}) + ([.nodes[$vm].addons[]? | objects | .<section> // empty] | add // {}).
  • Kubernetes cluster settings: k8s.load_kclu_vars(definition, clu_name) (clu_type, clu_rel, mydomain, …). A service's host name is usually <short name>.<clu_name>.<mydomain>.
  • Credentials for external services (SCC, registries) come from the credential store with addon_common.resolve_credential(); the lab's own fields are the fallback.

Schema versions

An add-on's schema has a version, MAJOR.MINOR, like every schema lab-in-a-box reads; check_addon.py fails an add-on without one. A new add-on starts at 1.0. Any change to its fields raises it:

  • Breaking, when a lab written for the previous version may not work, or may do something else: a field removed or renamed, a type changed, a field that became required, an option no longer accepted, a default or the behaviour of an unset field changed. It raises MAJOR and resets MINOR (1.4 to 2.0), and comes with its migration in the same change: a step in libs/migrations.py that rewrites a lab from the old form to the new one, changing only what is still in the old form. migrate_config.py applies it to users' labs, and setup_lab.py stops on a lab that still needs it.
  • Compatible, anything else, such as a new optional field or a new option. It raises MINOR by one (1.4 to 1.5).

For an add-on in scripts/, record each version in schemas/compatibility.json after raising it:

scripts/schema_versions.py diff addon:<name>      # what changed since the last recorded version
scripts/schema_versions.py record addon:<name> "What changed, in one sentence." [--migration <step>]

Check 80 fails when the schema changed without a new recorded version, when a compatible version removes, retypes or makes a field required, or when a breaking version has no migration. CONTRIBUTING.md, Schema versions, has the full rules.

Rules

  • Idempotent. Running it twice gives the same result: helm upgrade --install, never helm install; kubectl apply; create only what is missing.
  • Wait on a condition, not a delay. kubectl rollout status, kubectl wait, or a polling loop with a timeout, not a fixed sleep.
  • Secrets are password fields or credential-store entries; never default values, never printed.
  • Placement is declared, not guessed: the preflight enforces targets and requires_kubernetes, so the install run can rely on them.
  • Quote every lab value that goes into a shell command (shlex.quote in Python).
  • Comments and help text say what the add-on does and needs, not its history.

Testing

  • check_addon.py <install_<name>> (in scripts/, deployed to /usr/local/bin) checks the contract: the name, --schema json and its schema version, fields and capabilities (including the version matrix), --capabilities, --version, --help and --validate. It prints PASS or FAIL per check (--quiet: only failures) and exits 1 on any failure. The test suite runs it on every add-on in scripts/. In a repository checkout, put scripts/ on PATH first (PATH=$PWD/scripts:$PATH), since a Python add-on reads lab_schema from beside it or from PATH.
  • Check 79 (tests/checks/79_addon_install_test.py) runs the install path of every Python add-on against a one-kcluster lab, with every command faked: it must finish with exit 0, send at least one command and never run helm install. It runs each add-on twice: once with only the required fields set, so every other field takes the code's own fallback, and once with every schema default filled in. Both runs must send the same commands, so a published default must be the value the code really uses. When an add-on needs more to run (a field its code requires, or a reply to a command it reads or polls), add it to EXTRA_CONFIG or RESPONSES there.
  • Add a check for what it installs in tests/checks/NN_<name>.sh (with SSH and the tools it calls mocked, like the existing ones) and run bash tests/run_tests.sh; every check runs in its own podman container.
  • Try it on a lab: list it in a test lab and run setup_lab.py <lab.json>; setup_lab.py --debug shows its output live.

What to update with a new add-on

  • A row in the Available addons table, on the English page and every translation.
  • Its fields in the header block or schema, with their descriptions: the web UI, --help and the docs are built from them, and the web UI needs no change of its own.
  • Its schema version, 1.0, recorded with scripts/schema_versions.py record addon:<name> "First recorded version.".
  • A version matrix when it installs a versioned product.
  • Its templates in templates/addons/<name>/, and a check in tests/checks/.
